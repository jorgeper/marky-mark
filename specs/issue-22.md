# Spec: files, folders, workspaces (#22)

## Goal

All acceptance criteria in specs/issue-22.md are satisfied for issue #22, with evidence visible in the session: the app has an explicit three-mode model (initial splash / single-file / workspace) where File → Close File and File → Close Workspace both return to the splash through the unsaved-changes guards; closing or replacing a changed untitled workspace prompts Save / Don't Save / Cancel; folder-view and workspace-only menu items are disabled outside workspace mode; and `npm run validate:quick` passes in the implementer's session.

## Acceptance criteria

- **Three-mode model.** A pure helper in `src/lib` derives the app mode from existing state — `splash` (no document open, `workspace.kind === 'none'`), `file` (a document open, `workspace.kind === 'none'`), `workspace` (`workspace.kind !== 'none'`) — and is what the menu gating below consumes. Unit tests cover all three derivations.
- **Close File exists.** `buildMenuSpec` (both macOS and non-macOS layouts) has a File → Close File command item wired to a new `closeFile` command; invoking it with a file open closes the buffer down to the splash, routing through the existing unsaved-changes guard (a dirty buffer prompts; Cancel aborts and the file stays open).
- **Close Workspace lands on the splash.** After File → Close Workspace completes, `workspace.kind === 'none'`, the sidebar roots/tabs are cleared, the open document is closed (its own dirty guard runs first), and the splash is shown — the document no longer stays open after workspace close.
- **Changed-workspace prompt.** An untitled workspace counts as *changed* when its workspace-scope settings map is non-empty or it holds more than one folder (that state would otherwise be lost). When a changed untitled workspace is about to be discarded — via Close Workspace, via Open Folder… or Open Workspace… replacing it, or via app quit/Close Window — a Save / Don't Save / Cancel prompt appears: Save runs the Save Workspace As… flow (cancelling its dialog aborts the close), Cancel aborts the whole operation, Don't Save proceeds. Named workspaces autosave to their `.marky-workspace` file and never prompt. The changed-rule is a pure function with unit tests.
- **Open Folder is close-then-open.** Open Folder… with a workspace already open runs the changed-workspace prompt first; on proceed the picked folder becomes a fresh single-folder untitled workspace (existing §C8 behavior). From the splash or file mode it opens workspace mode directly, no prompt.
- **Menu gating.** `MenuItemSpec` command items support a disabled flag, the Tauri layer renders it as grayed native items, and the browser shim records it for tests. Gating per mode: Add Folder to Workspace…, Save Workspace As…, and Close Workspace are disabled when `workspace.kind === 'none'`; View → Folders (and Only Open Files) is disabled outside workspace mode and the FolderPanel never renders outside workspace mode; Close File is disabled when no document is open. Open…, Open Folder…, and Open Workspace… stay enabled in every mode. `tests/unit/menu-spec.test.ts` asserts the gating for all three modes.
- **Workspace settings stay gated.** The Settings panel's Workspace scope tab remains enabled only while a workspace is open (already true per PRD 002 §E18 — keep it true; a regression here fails this criterion).
- **Test economy.** Iterate with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code) while developing; baseline an attempt with the quick tier only. Run `npm run validate:quick` ONCE, right before declaring the goal met — not after every small change — and it passes in the implementer's session.
- A summary comment from the implementer exists on issue #22.

# Spec: opening a file in edit mode (#40)

## Goal

All acceptance criteria in issue-specs/issue-40.md are satisfied for issue #40, with evidence visible in the session: edit mode is unreachable when no document is open (hotkey, View menu, and toolbar all leave the splash/empty state in preview with no phantom buffer created), the View → Edit Mode menu item is disabled while no document is open, edit-mode behaviour with a real file or untitled buffer is unchanged, and `npm run validate:quick` passes in the implementer's session.

## Acceptance criteria

- With no document open — the standalone splash AND the workspace-open-but-no-file-active state alike (`docPath === null && !untitled`) — the app cannot enter edit mode: after pressing the toggleEdit hotkey (default `Mod+E`), invoking View → Edit Mode, or clicking the toolbar's mode control, the app is still in preview mode, the splash/empty surface is still visible, no CodeMirror editor is mounted, and no phantom buffer exists (`docPath` still null, `untitled` still false, `dirty` still false). The guard lives in the `toggleMode` command handler (`src/App.tsx:2507`) so every dispatch route — hotkey (`src/App.tsx:3247`), native menu, toolbar (`src/App.tsx:4129`) — is inert through one gate, following the existing in-handler guard pattern of `toggleFolders` (`src/App.tsx:2926`).
- The native View → Edit Mode menu item is grayed out when no document is open: `buildMenuSpec` (`src/lib/menuSpec.ts:187`) passes a `disabled` flag derived from the existing `MenuState.docOpen` field (already threaded from `src/App.tsx:3086`), and `tests/unit/menu-spec.test.ts` has cases asserting the item is disabled with `docOpen: false` and enabled with `docOpen: true`.
- Nothing regresses with a document open: toggling edit mode on a real file works exactly as today, and File → New still swaps in the untitled buffer in edit mode (SPEC22 §1.1 — an untitled buffer counts as an open document for the guard). The existing e2e suites touching mode toggling (`tests/e2e/editor.spec.ts`, `tests/e2e/documents.spec.ts`, `tests/e2e/split-view.spec.ts`) pass unchanged.
- An e2e test exists (numbered with the next free `E<n>`, in `tests/e2e/editor.spec.ts` or `tests/e2e/shell-and-menus.spec.ts`) that, from the no-document state, presses `Mod+E` and asserts the splash (`data-testid="empty-hint"`) is still visible and no editor surface appears.
- New or changed behaviour carries citation comments (`// SPEC<n> §x.y` or issue-citation) per `.sandcastle/CODING_STANDARDS.md`, and `docs/MAP.md` is regenerated via `npm run map` if spec→code coverage changed.
- Iteration used `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code) after each change; the full gate was NOT run per-change and NOT run as a baseline at the start. `npm run validate:quick` has been run exactly once, right before declaring the goal met, and prints `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- A summary comment from the implementer exists on issue #40 describing the fix, the guarded entry points, and the validation evidence.

## Context

The issue is terse ("opening a file in edit mode" / "this should not be allowed when a file is open"); the code pins down the defect it describes. The splash renders only inside the `mode === 'preview'` branch (`src/App.tsx:4222`; the comment at `:4217` states "the splash is preview-only"), but `toggleMode` has no document guard — the only two `setMode('edit')` sites are the toggle (`:2527`) and File → New (`:2603`). So `Mod+E` with nothing open mounts a blank editor over nothing: it looks like the app opened a new file in edit mode, but the buffer is a trap — `saveDoc` returns false for it (`src/App.tsx:2485`, not untitled), `saveDocAs` refuses too (`:2458`), yet typing sets `dirty`, so quit/open guards prompt to save a buffer that cannot be saved. The fix is a guard, not new UI: entering edit mode requires an open document (file or untitled). Every real file open already lands in preview (`openDoc` at `src/App.tsx:1561`), so no open path needs changing. Adjacent splash bugs (#39 empty-state message, #43 logo-over-text) are separate issues — do not fix them here, but don't regress their surfaces either.

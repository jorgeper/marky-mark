# Spec: PRD 026: 409 carries a free-name suggestion and both forms offer a one-click "Use <name>" action (#354)

## Goal

All acceptance criteria in issue-specs/issue-354.md are satisfied for issue #354, with evidence visible in the session: both unique-name 409 refusals in `server/workspaces.ts` (creation and rename) carry a `suggestion` beside `error` — the first free name `dedupeUniqueName` mints from the requested one against the same collision scan (`team-docs` → `team-docs-2`, reserved words and the length clamp respected) — with server unit tests (U1339+) proving both routes; the client threads the suggestion through `lifecycle.create` and `ManifestResult` failures via a pure, unit-tested parser in `src/lib/workspaceLifecycle.ts` that keeps only a string passing `uniqueNameProblem`; the New Workspace dialog (`new-workspace-use-suggestion`) and the settings Names section (`workspace-use-suggestion`) render exactly one `Use <suggestion>` action next to the collision refusal, and clicking it puts the suggestion in the URL-name field (marking it touched in the dialog, edited in settings), clears the refusal message and paint, updates the address preview and does not submit — while a 409 without a suggestion shows the refusal alone with no action; new hosted e2e tests (E606+) drive the taken-name → one-click-fill → successful submit path in both forms; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #354.

## Acceptance criteria

- **Server: both 409s carry a suggestion (PRD 026 Req 12).** The creation route (`server/workspaces.ts:~740`) and the rename route (`:~948`) send `{ error, suggestion }` where `error` is the unchanged `uniqueNameTakenError(name)` string and `suggestion` is `dedupeUniqueName(name, scan.taken)` — the same `scan` each route already holds (creation's deployment-wide scan; rename's `scanUniqueNames(storage, id)` that excludes the workspace being renamed), so the suggestion is free by the exact rule that refused the request, skips reserved words, skips an already-taken `-2` (`team-docs-2` taken → `team-docs-3`) and never exceeds `UNIQUE_NAME_MAX_LENGTH`. The body is built by one shared helper beside `uniqueNameTakenError` (e.g. `uniqueNameTakenBody(name, taken)`) so the two routes cannot drift; the 400 (format/reserved) refusals and every other 409 in the file are untouched. No new endpoint, no availability check, and `src/lib/workspaceNames.ts` gains no parallel minting implementation — `dedupeUniqueName` is the minting rule (a thin named re-export/wrapper is acceptable only if it delegates).
- **Server unit tests.** New tests in `tests/unit/server-workspaces.test.ts` titled `U1339:` upward (U1338 is the highest in use; never reuse a number) prove, using the file's existing `call`/`create`/`seedStoredName`/`readManifest` helpers: a POST with a taken name is a 409 whose body has `suggestion === '<name>-2'`; when `<name>-2` is also held the suggestion is `<name>-3`; a PUT rename onto a taken name is a 409 with the suggestion, and the suggestion is not the renaming workspace's own current name (self is excluded from the scan); a request whose suggestion would exceed the length cap gets a clamped one of exactly `UNIQUE_NAME_MAX_LENGTH` characters. Req 13's minting table (`team-docs` → `team-docs-2`; reserved word skipped, e.g. `scratchpad` → `scratchpad-2`; a taken suffix skipped; the clamp) is added as `U13xx` tests in `tests/unit/workspace-names.test.ts` framed as PRD 026 Req 12 (U1047 stays as is).
- **Client seam carries the suggestion.** `WorkspaceLifecycle.create` (`src/platform/hostedWorkspaces.ts:34`) returns `{ id } | { error: string; suggestion?: string }`, and `ManifestResult`'s failure arm (`src/lib/hostedWorkspace.ts:190`) becomes `{ ok: false; error: string; suggestion?: string }` — optional, so every existing `{ ok: false, error }` construction still typechecks. The `create` implementation and the shared manifest-write helper (`hostedWorkspaces.ts:~200`) read the 409 body through one pure function exported from `src/lib/workspaceLifecycle.ts` (e.g. `suggestionFrom(body: unknown): string | undefined`) that returns the body's `suggestion` only when it is a non-empty string for which `uniqueNameProblem` is null, and `undefined` otherwise (absent, wrong type, or unusable — the field must never be filled with something the form would refuse). Unit tests in `tests/unit/workspace-lifecycle.test.ts` (`U13xx:`) cover: a valid suggestion passes through; a missing field, a non-string, an empty string and a value failing the strict rule all yield `undefined`. `isUniqueNameError` is unchanged and still returns true for the taken message. `src/lib/` stays free of React/DOM imports; no `console.*` in `src/`.
- **New Workspace dialog action (Req 12 + Req 5).** In `src/components/WorkspaceSwitcher.tsx` the dialog keeps a `suggestion` alongside `error` (a single refusal state object or a second `useState` — implementer's choice); every existing `setError('')` site also drops the suggestion, and a failed `lifecycle.create` stores both. When `error` is set AND a suggestion is present, exactly one `Button` (the `./ui/Button` primitive — `variant="quiet"`, `size="sm"` recommended; no raw `<button>`, no new colour/size literal, no per-call-site visual CSS; a spacing-only layout class is fine) with `data-testid="new-workspace-use-suggestion"` and text exactly `Use <suggestion>` renders next to the `new-workspace-error` line. Clicking it: sets the URL-name field (`new-workspace-unique-name`) to the suggestion verbatim, calls `setTouched(true)` so mirroring from the display name stops (the display-name value is untouched), clears `error` and the suggestion (so the `new-workspace-error` line disappears and the field loses its `invalid invalid-value` paint), and does NOT submit — the dialog stays open, no request is sent, and the guidance preview (`new-workspace-url-preview`) now reads `${origin}/<suggestion>`. Because the suggestion passes the strict rule, no `new-workspace-unique-name-error` appears. A 409 whose body has no usable suggestion renders the refusal alone (`new-workspace-use-suggestion` count 0). A subsequent Create with the suggested name succeeds and navigates as today.
- **Settings Names section action (Req 12 + Req 10).** In `src/components/WorkspaceNames.tsx` the same shape: a failed `putManifest` stores `error` and the suggestion; every existing `setError('')` site also drops it; when both are present exactly one `Button` with `data-testid="workspace-use-suggestion"` and text `Use <suggestion>` renders next to `workspace-names-error`. Clicking it sets `uniqueName` to the suggestion (it now differs from `stored`, so the field is `edited` and enters the strict regime, which the suggestion passes), clears the refusal message and paint, leaves the display-name field alone, updates `workspace-url-preview` to `${origin}/<suggestion>`, and does not save — the manifest read back via `GET /api/workspaces/<id>/manifest` is unchanged until the user clicks `workspace-names-save`, after which the tab lands on `/<suggestion>` and `formerNames` records the old name exactly as E602 shows. Without a suggestion the refusal shows alone (`workspace-use-suggestion` count 0). No existing test id is renamed and document order of the existing ids (`workspace-friendly-name`, `workspace-unique-name`, `workspace-url-guidance`, `workspace-url-preview`, `workspace-former-names`) is unchanged, so E572 still passes.
- **Existing tests stand.** E492 and E535 (the taken-name paint tests) keep passing unchanged — the action sits beside the error line without altering its text, size or colour, and editing the field still retires message, paint and action together. U1321/U1322 and the other 409 assertions still pass because `error` is unchanged (they read only `.error`). If any of these fails, fix the product, not the test.

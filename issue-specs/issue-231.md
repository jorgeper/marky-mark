# Spec: Highlights: swatch creation UX and highlight rendering model (#231)

## Goal

All acceptance criteria in issue-specs/issue-231.md are satisfied for issue #231, with evidence visible in the session: the selection affordance is a compact popup of four marker swatches (yellow, green, blue, pink) plus an "add note" action — a swatch click creates a note-less highlight in that color and closes the popup, "add note" creates a highlight in the armed color and opens today's composer attached to it; the last-used marker color is a user-scoped (`U` layer) setting that pre-arms the popup and seeds "add note" and type-to-comment; entries without a `color` field still render in the legacy `--mm-comment-tint`; the four marker colors are CSS tokens in the fenced document-rendering region of `styles.css` with anchoring and the `mark.hl`/`data-cid` painting path unchanged; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #231.

## Acceptance criteria

- **Swatch popup replaces the pill (PRD 022 Req 1).** The selection affordance — today's two "💬 Add comment" buttons in `src/App.tsx` (preview and edit surfaces, gated by `commentAffordanceSurface` in `src/lib/commentAffordance.ts`) — is a compact popup of four marker swatches in the order/vocabulary **yellow, green, blue, pink** (matching `CommentColor` in `src/lib/commentFormat.ts`) plus an "add note" action. Clicking a swatch creates a highlight of that color (a note-less entry: empty `body`, no thread, per format 1.1.0 from #230) and closes the popup with no composer opening. Clicking "add note" creates a highlight in the armed color (Req 4) and opens today's composer attached to it. On the plain-edit surface, both actions still route through the existing SPEC25 selection carry — the edit affordance must not dead-end.
- **Gate predicate unchanged in role.** `commentAffordanceSurface` keeps governing when the popup may appear, same inputs and semantics; its unit tests (`tests/unit/comment-affordance.test.ts`) pass with at most mechanical name adjustments (e.g. doc-comment/test-title wording from "Add comment" to the popup).
- **A comment is a note on a highlight (PRD 022 Req 2).** Submitting the composer yields one object: a colored highlight whose entry carries the note, author, and thread — exactly today's comment plus a `color`. Type-to-comment (printable key over a selection, SPEC7 §3 in `App.tsx`) still opens the composer and now produces a highlight-with-note in the armed color.
- **Legacy entries are noted highlights (PRD 022 Req 3).** An entry without a `color` field renders in the legacy default tint (`--mm-comment-tint`) and behaves as a noted highlight. No sidecar rewrite, no migration pass: opening and re-saving a legacy store must not add `color` to entries the user didn't touch (stamping stays 1.0.0 for colorless stores, per #230).
- **Last-used color is armed (PRD 022 Req 4).** The most recently used marker color is a user-scoped setting in `src/lib/settings.ts` (share level `U`, validated to the four literals, defaulting sensibly — yellow matches the legacy tint family). The popup shows it first/pre-armed so repeat highlighting is one click, and it seeds both "add note" and type-to-comment. Creating or recoloring with a swatch updates it.
- **Marker palette tokens (PRD 022 Req 13).** The four colors are theme-independent defaults defined as CSS custom properties in the document-rendering region of `src/styles.css` (inside the `/* DOCUMENT RENDERING — BEGIN/END (PRD 018 Req 17) */` fences), with optional per-theme override tokens (`--mm-*` naming, consistent with `--mm-comment-tint`). Active/flash states, resolved `.ghost` dimming, and print suppression follow the existing comment-tint rules for all four colors. Body text over every marker color meets WCAG AA contrast in the default light and dark themes (state the checked ratios in the implementer's summary or a test).
- **Anchoring unchanged (PRD 022 Req 14).** Highlights reuse the existing anchor schema and re-anchoring pipeline (`src/lib/anchoring.ts`: exact → context → fuzzy) and the `mark.hl`/`data-cid` painting path (`src/lib/domtext.ts` may gain a color class/attribute on the mark, nothing more); rendered plain text remains byte-identical — no new text-affecting pipeline stages. Existing anchoring/domtext unit tests pass unmodified or with only additive cases.
- **Scope.** This issue is PRD 022 Reqs 1–4, 13, 14 only. Out of scope: card/lifecycle behavior for note-less highlights (Req 8–9, sibling issue), copy-link/fragments (Reqs 10–11), and editor-pane CodeMirror decorations (Req 12). Where the active card is involved (e.g. clicking a highlight), existing comment behavior may remain as-is.
- **Tests.** Unit coverage for the new color setting (validation, `U`-layer merge) and the affordance gate's adjusted naming; e2e coverage in `tests/e2e/comments.spec.ts` (or a new numbered `E<n>` sibling suite) for: swatch-create yields a colored highlight with no composer, add-note creates a highlight and opens the composer, last-used color pre-arms the popup, and a legacy colorless sidecar file renders in the default tint. Existing comment e2e tests pass with only mechanical updates for the new affordance.
- **Test economy.** The implementer iterated with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code, e.g. `npx playwright test -g '<title>'` for one e2e), and ran `npm run validate:quick` exactly once, right before declaring the goal met — not after every small change and not as a full-gate baseline at the start.
- **Gate.** `npm run validate:quick` has been run in the implementer's session and prints `QUICK VALIDATION: ALL PASSED`.
- **Issue trail.** A summary comment from the implementer exists on issue #231.

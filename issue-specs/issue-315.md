# Spec: changes since save doesn't show me deletions in re (#315)

## Goal

All acceptance criteria in issue-specs/issue-315.md are satisfied for issue #315, with evidence visible in the session: with Changes Since Save on, the saved lines that were removed from the buffer are visible in the editor as read-only red blocks at the place they were removed from (including a replaced line's old text next to its green replacement, and a deletion before line 1 above line 1); the red treatment is derived from `--mm-diff-removed` so it stays legible on the bundled dark themes; new `U<n>`/`E<n>` tests cover the removed text carried by the diff seam and the on-screen red blocks while every existing diff test still passes unweakened; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #315.

## Acceptance criteria

- **The removed text is shown, in red.** With the View-menu "Changes Since Save" checkbox on (SPEC16 §2, `toggleDiff`), each run of saved lines that no longer exists in the buffer is rendered in the editor as a block below the line the deletion follows (the same anchor `diffLineSets`' `deletedAfter` names today), containing the removed lines' text. A deletion before the first line (`deletedAfter` 0) renders its block above line 1. Removing a whole fenced block still yields ONE block (one per removed run, not one per line), and it carries all of that run's lines.
- **A replaced line shows its old text too.** Editing a line is a delete+insert; today `diffLineSets` drops the deletion marker when the anchor's next line is changed, so the user sees green and never what the line used to say. After this change the old line(s) are shown in red next to the green changed line(s), git-style. The existing `U30` assertions (`rep.changed` equals `[3]`, the identical case yields empty sets, etc.) still hold as written.
- **The red treatment is a real, theme-safe red.** The block's background and left edge derive from `--mm-diff-removed` (which the app maps to `--mm-danger`), mixed to a tint the way `--mm-diff-changed-bg` tints changed lines and the way issue #318's callouts mix a hue over `--mm-bg`; no hard-coded light-only red. On the bundled dark themes (`github-dark`, `nord`, `one-dark`, `rose-pine`, `vaporwave`) the removed text remains readable on its tint. The existing anchor-line class `mm-diff-deleted-after` and its 3px edge remain (E499/E500 assert the class on the anchor).
- **The block is not document text.** It is a CodeMirror block widget (the `diagramView` `block: true` widget is the precedent), so: the caret cannot enter it, typing never lands in it, it is not selectable as buffer text, the buffer's content and line numbering are unchanged by its presence, and it does not affect the word count, the dirty flag, or what gets saved. Turning the checkbox off removes every block; saving (so buffer equals saved) removes every block.
- **Line placement survives the widgets already on screen.** Blocks land after the LAST raw row of an anchor that is a gridded table row (the `diffMarks` rule), stay out of a rendered diagram fence exactly as today, and E502/E496–E498 keep passing unchanged.
- **The pure seam carries the removed text; no new dependencies.** `editor/src/lib/diffLines.ts` (`diffLineSets`) exposes, for each deleted run, its anchor line and the removed lines' text, taken from the diff-match-patch `-1` ops it already computes (SPEC16 U30: no new dependencies). Keep `changed` and `deletedAfter` so existing callers and tests keep working; if a new field is added to the returned object, the U30 `toEqual` expectations are updated to include it rather than weakened. `tests/unit/editor-boundary.test.ts` still passes.
- **Unit coverage.** New `U<n>` tests (next free number is U1252; check with `grep -rhoE 'U[0-9]+' tests/unit editor/tests | sort -t U -k2 -n | tail -1`) in `editor/tests/diff-lines.test.ts` and/or `editor/tests/diff-marks.test.ts` cover: a middle-line deletion carries that line's text at anchor 2; a multi-line run carries all its lines in order as one run; a deletion before line 1 carries its text at anchor 0; a replaced line carries the old text alongside the changed line; identical inputs carry no removed runs.
- **E2E coverage.** New `E<n>` tests (next free number is E543; check with `grep -rhoE 'E[0-9]+' tests/e2e | sort -t E -k2 -n | tail -1`) in `tests/e2e/diff-overlay.spec.ts`, reusing `openMixWithDiff`, assert at least: deleting a prose line shows exactly one red block whose text is the removed line, positioned directly below its anchor (bounding box top ≥ the anchor's bottom); its computed background is not transparent and its computed edge/background colour resolves from `--mm-diff-removed` (e.g. compare against `getComputedStyle(document.documentElement).getPropertyValue` resolved through a probe element, or assert the red channel dominates); a deletion before line 1 places the block above line 1; clicking the block then typing leaves the buffer text unchanged; toggling the checkbox off removes the block. E501 (unedited document paints nothing) still passes.
- **Citations and docs.** New behaviour carries `// SPEC16 §2 (issue #315): …` citation comments per `.sandcastle/CODING_STANDARDS.md`; the `--mm-diff-removed` row in `editor/THEMING.md` describes the block (not just the "left edge"); if a new theme variable is introduced it is documented there with its fallback; `npm run map` has been run if citation sites moved between files so `docs/MAP.md` matches the generator.
- **Verification economy.** Baseline and iterate with `npm run typecheck` and `npm run test:unit`, and with single Playwright tests targeted at the changed behaviour (`npx playwright test -g 'E<n>'` or `-g 'diff'`) — not the whole e2e suite per change. `npm run validate:quick` has been run ONCE, right before declaring the goal met, and printed `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- **Summary comment.** A summary comment from the implementer exists on issue #315 describing what changed and where the evidence is.

## Context

The issue has no body or comments; the title reads as "Changes Since Save doesn't show me deletions in red." Today SPEC16 §2's overlay tints changed/inserted lines green (`.cm-line.mm-diff-changed`, `editor/styles.css`) and marks a deletion only as a 3px inset red edge (`.cm-line.mm-diff-deleted-after`) on the line ABOVE where saved text vanished — nothing of the removed text is shown, the edge is easy to miss, and `diffLineSets` deliberately drops the marker for replacements (the most common edit), so a user who edits or deletes lines sees green and no red. This spec's reading: show the deleted saved lines themselves, in red, in place — the inline-diff picture GitHub and VS Code draw.

Pointers: the seam is `editor/src/lib/diffLines.ts` (`diffLineSets`, built on diff-match-patch line mode; the `-1` ops already hold the removed text), the canonical→raw line mapping and anchor rules are `editor/src/components/diffMarks.ts` (`diffLineMarks`, issue #264), and the decoration assembly is `diffDecorations`/`lineDeco` near the top of `editor/src/components/Editor.tsx` (grep `SPEC16`), swapped in through `diffComp`. Block-widget precedent: `editor/src/components/diagramView.ts` (`block: true`). Styling lives in `editor/styles.css` (SPEC16 block, "DOCUMENT RENDERING" section) with the tokens in `src/styles.css` lines ~166–169 and the editor's `default-theme.css`; read `docs/STYLE-GUIDE.md` before adding CSS. The app computes the sets over the canonical buffer in `src/App.tsx` (grep `SPEC16`, `showDiff`) — the App side should need no more than passing the richer seam result through. Existing tests to keep green: U30, U1191–U1195 (`editor/tests/`), E496–E502 (`tests/e2e/diff-overlay.spec.ts`), and the menu tests that reference `toggleDiff`.

# Spec: PRD 026: username derivation uses the shared lowercase-dash slugifier (#351)

## Goal

All acceptance criteria in issue-specs/issue-351.md are satisfied for issue #351, with evidence visible in the session: `slugifyUsername` in `src/lib/usernames.ts` delegates to the shared `slugifyWorkspaceName` slugifier from `src/lib/workspaceNames.ts` (PRD 026 Req 2) and supplies `user` only when the slug is empty, so a first-seen `jane.doe@contoso.com` derives `jane-doe`, `j_smith` derives `j-smith`, and `!!!`/`日本語` derive `user`, with dedupe and the reserved route words unchanged; every non-empty username the derivation mints satisfies PRD 026 Req 1; stored usernames are read back unchanged by `ensureUsername` and still resolve through the scratch path helpers; `tests/unit/usernames.test.ts` covers Req 11 through the shared slugifier and `tests/unit/server-usernames.test.ts` shows a stored dot/underscore username reading back untouched; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #351.

## Acceptance criteria

- **Usernames follow the rule (PRD 026 Req 11).** `slugifyUsername` in `src/lib/usernames.ts` is implemented as the shared slugifier `slugifyWorkspaceName` (exported from `src/lib/workspaceNames.ts` by #350) with `user` substituted only when that slugifier returns the empty string. There is no second copy of the slugify regex in `usernames.ts`. Observable results: `jane.doe` → `jane-doe`, `j_smith` → `j-smith`, `Ada.Lovelace` → `ada-lovelace`, `jane_gmail.com#EXT#` → `jane-gmail-com-ext` (no trailing dash), `grace hopper (guest)` → `grace-hopper-guest`, `数学` → `user`, `!!!` → `user`, `''` → `user`, and a local part longer than 100 usable characters clamps to 100 with no trailing dash. Every non-empty output satisfies PRD 026 Req 1 (`uniqueNameFormatProblem` returns `null` for it).
- **Derivation end to end.** `deriveUsername` still composes `identityLocalPart` → `slugifyUsername` → `dedupeUniqueName`, so `jane.doe@contoso.com` against an empty taken set derives `jane-doe`, against `{jane-doe}` derives `jane-doe-2`, and a guest identity (`Jane_gmail.com#EXT#@…` with email `Jane@Gmail.com`) still derives from the email local part. `identityLocalPart`, `dedupeUniqueName`, the reserved words (`api`, `assets`, `scratch`, `scratchpad` still land on `<word>-2`) and `UNIQUE_NAME_MAX_LENGTH` are unchanged; no dedupe or reserved-word behaviour moves.
- **Stored usernames untouched.** `ensureUsername` in `server/usernames.ts` keeps its read-record-first contract: a `users/<id>/username.json` record holding a legacy-charset username such as `jane.doe` or `j_smith` is returned as is, never re-derived or normalised, and `resolveUsernameOwner` / `usernameClaimBlob` keep resolving such a username through `uniqueNameKey` exactly as today. `server/usernames.ts` needs no behaviour change; it changes only if the `user` fallback wiring genuinely requires it, and any change there is citation-commented.
- **Scratch path helpers unaffected.** `buildScratchPath`, `isOwnScratch` and `scratchBootsFresh` in `src/lib/hostedPaths.ts`, and the `/api/scratchpad/<username>` resolution in `server/app.ts`, are not modified; the existing hosted e2e tests (`tests/e2e/hosted.spec.ts`, e.g. `/grace/scratchpad/...`, `/ada/scratchpad/...`) pass unchanged. No hosted UI, dialog, settings or workspace-name work from PRD 026 Req 4–10, 12 lands here (#352–#354 own it).
- **Unit coverage (PRD 026 Req 13, usernames part).** `tests/unit/usernames.test.ts` has tests, each titled with the next unused `U<n>:` id (U1323 upward; never reuse a number), that prove through the public functions: the `jane.doe` → `jane-doe` and `j_smith` → `j-smith` examples; the `user` fallback for a local part with nothing usable (`数学`, `!!!`, `''`); dedupe (`jane-doe`, `jane-doe-2`, `jane-doe-3`) and the reserved route words unchanged; and that every derived username passes `uniqueNameFormatProblem`. `tests/unit/server-usernames.test.ts` has a test (next unused `U<n>:` id) seeding a `username.json` record with a legacy dot/underscore username straight into the storage fake and showing `ensureUsername` returns it unchanged and `resolveUsernameOwner` still maps it to its owner through a seeded claim blob.
- **Existing tests updated to the amended contract, not weakened.** U1065 is rewritten in place under its id to assert the PRD 026 outputs (`ada-lovelace`, `jane-gmail-com-ext`, `grace-hopper-guest`, `user` for `数学`), and its title/comments cite PRD 026 Req 11 instead of describing the old `[a-z0-9._-]` charset. U1064, U1066 and U1067–U1071 keep passing (their inputs already derive lowercase-dash names) and are touched only if a comment or citation would otherwise be false. No test is deleted, skipped or renumbered.
- **Citations and module header.** The `src/lib/usernames.ts` module header and `slugifyUsername` doc comment cite `PRD 026 Req 11` (amending PRD 020 Req 12) per `.sandcastle/CODING_STANDARDS.md`; the `issue #351` forward reference in the `slugifyWorkspaceName` comment in `workspaceNames.ts` is updated to name PRD 026 Req 11 / `usernames.ts` rather than a pending issue. No `console.*` in `src/`; `src/lib/` stays import-free of React/Tauri; `npm run typecheck` is clean.
- **Verification economy.** The implementer iterates with `npm run typecheck` and `npm run test:unit` (or `npx vitest run tests/unit/usernames.test.ts tests/unit/server-usernames.test.ts tests/unit/workspace-names.test.ts`) after each change, and does not run the full gate as a baseline at the start of an attempt.
- **Gate.** `npm run validate:quick` has been run once in the implementer's session, right before declaring the goal met, and prints `QUICK VALIDATION: ALL PASSED`.
- **Summary comment.** A summary comment from the implementer exists on issue #351 describing what changed, the tests added/updated, and the gate result.

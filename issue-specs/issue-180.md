# Spec: Directory provider: on-behalf-of Graph token exchange, guest badges, member display-name snapshots (#180)

## Goal

All acceptance criteria in issue-specs/issue-180.md are satisfied for issue #180, with evidence visible in the session: the azure-mode Graph directory provider obtains its token via the OAuth2 on-behalf-of exchange (delegated `User.ReadBasic.All`, tokens cached per user for their validity window) instead of forwarding the session id_token; directory entries carry Graph `userType` so the People section badges guests; the workspace manifest snapshots each member's display name at add time and `resolveMembers` falls back to that snapshot (then the plain id) when Graph cannot answer; the new confidential-client config is validated fail-fast, documented in both hosting guides, and the Known-limitations bullets about directory search/avatars are gone; `npm run validate:quick` passes and a summary comment from the implementer exists on issue #180.

## Acceptance criteria

- **OBO exchange exists in the Entra/Graph seam.** In `MM_MODE=azure`, the server exchanges the caller's incoming session bearer (the id_token assertion) at the tenant token endpoint (`https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`, grant `urn:ietf:params:oauth:grant-type:jwt-bearer`, scope `https://graph.microsoft.com/User.ReadBasic.All` — delegated only, no application permissions) for a Graph access token, and `server/providers/azure/graph.ts`'s three calls (user search, user lookup, photo) send that Graph token, not the session bearer. The token-endpoint fetch is injected the same way the Graph fetch already is, so unit tests pin the exchange with no network.
- **Per-user server-side token cache.** Exchanged Graph tokens are cached per user for their validity window (respecting `expires_in`, with a sensible safety margin), so repeated directory calls do not repeat the exchange. The session bearer contract for every other route is unchanged: id_token in, iss/aud pinned as `server/providers/azure/entra.ts` does today.
- **Confidential-client config, fail-fast.** The registration change (a client secret — or certificate — added to the existing app registration) is expressed as a new required env var in azure mode (e.g. `ENTRA_CLIENT_SECRET`), added to `AZURE_REQUIRED` in `server/config.ts` and to the `azure` config section, with the same all-gaps-at-once refusal style `loadConfig` already uses. The secret's value never appears in any log line, error message, or HTTP response (same rule `MM_LLM_API_KEY` follows).
- **Guest badges.** `DirectoryUser` / `DirectoryEntry` carry whether the user is a guest (Graph `userType === 'Guest'`, via `$select`), the directory API routes pass it through, and the People section (`src/components/WorkspaceMembers.tsx`) renders a visible guest badge on guest members and picker results.
- **Display-name snapshots.** `WorkspaceMember` in `src/lib/hostedWorkspace.ts` gains an optional snapshotted `displayName`, populated at member-add time (creation and `POST .../members` in `server/workspaces.ts`) from the directory when available; manifest parsing round-trips it and old manifests without it still parse. `resolveMembers` in `src/lib/membership.ts` prefers the live Graph answer, falls back to the snapshot when the lookup returns null or fails, and only then to the plain id.
- **Docs updated.** HOSTING-AZURE.md (§ 1 registration / § 4 app settings) and HOSTING-AZURE-PORTAL.md (§ 3 / § 5) document the added registration step (creating the client credential) and the new env var; the Known-limitations bullets about directory search/avatars failing — and the matching troubleshooting rows and the pointer in docs/AUTHENTICATION.md — are removed or rewritten to reflect that OBO now works.
- **Local mode untouched.** `MM_MODE=local` (mock directory) starts and behaves exactly as before, with no new required config.
- **Unit tests** cover the OBO exchange decision logic (token request shape, caching/expiry, error paths) and the snapshot fallback ordering in `resolveMembers`, plus the config validation for the new variable.
- The implementer iterated with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code) during development, and ran `npm run validate:quick` ONCE at the end, right before declaring the goal met — it passes with `QUICK VALIDATION: ALL PASSED` in the implementer's session (baseline with the quick tier only; no full-suite runs mid-loop).
- A summary comment from the implementer exists on issue #180.

## Context

The bug: `server/providers/azure/graph.ts` sends the caller's session id_token (audience = the app's own client id) to Graph, which answers 401 `InvalidAuthenticationToken`; live symptoms are member-search errors and members rendered as raw oid GUIDs. The fix is the standard Entra OBO flow. Key constraint from PRD 007 (`prd/007-azure-hosted-workspaces.md`): the current registration is a public client with no secret — `server/config.ts` has nowhere to hold one — so this issue introduces the confidential-client credential and its env var. Follow the citation-comment convention (`docs/COMMENT-FORMAT.md`, `.sandcastle/CODING_STANDARDS.md`); `docs/MAP.md` locates the directory/membership code, and `npm run map` regenerates it if spec-cited files change. The People UI is `src/components/WorkspaceMembers.tsx` over the pure logic in `src/lib/membership.ts`; membership routes and manifest handling live in `server/workspaces.ts` + `src/lib/hostedWorkspace.ts`. E2e suites run against local mode, so azure-mode behaviour is pinned by unit tests (injected fetch), as `graph.ts` already does.

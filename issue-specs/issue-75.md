# Spec: Workspace lifecycle flows: create, open, delete (#75)

## Goal

All acceptance criteria in issue-specs/issue-75.md are satisfied for issue #75, with evidence visible in the session: a hosted New Workspace flow names a workspace, grants initial members roles (or everyone-access), creates it server-side and opens it with the creator as Owner; an Open Workspace dialog lists every workspace in the deployment (name + last-modified) with fuzzy search-as-you-type, opens the ones the signed-in user can access and shows a no-access message naming that workspace's Owners otherwise, while the server still refuses file contents to non-members; Workspace settings shows holders of `workspace.delete` a destructive delete action gated on typing the workspace's exact name that removes all server-side data and returns to the start page; the new behaviour is pinned by unit tests (U277+) and offline hosted e2e tests (E179+); and `npm run validate:quick` has been run once at the end in the implementer's session and prints `QUICK VALIDATION: ALL PASSED`.

## Acceptance criteria

- **(PRD 007 Req 10 — create)** A New Workspace flow in the hosted app asks for a workspace name and initial members with roles, or an everyone-in-tenant access toggle with a default role, and on submit creates the workspace server-side and opens it with the creator recorded as Owner. Member selection reuses the existing `src/components/MembershipPicker.tsx` + `src/lib/membership.ts` (issue #74) unchanged rather than a second picker. `POST /api/workspaces` accepts the initial members and everyone-access alongside `name` (existing name-only callers, including `tests/e2e/hosted.spec.ts`'s `createWorkspace` helper, keep working), validates roles against the built-in and custom role names in `src/lib/hostedWorkspace.ts`, rejects an unknown role with 400, and always retains the creator as Owner regardless of what the body asks for.
- **(PRD 007 Req 11 — open)** An Open Workspace dialog lists **all** workspaces in the deployment — name and last-modified — sourced from `GET /api/workspaces`, with fuzzy search-as-you-type over the name (reuse `fuzzyFilter` in `src/lib/fuzzy.ts`; no per-keystroke server round trip). Choosing a workspace the signed-in user can access opens it in the app; choosing one they cannot shows an in-dialog no-access message naming that workspace's Owners by display name (resolved through the existing directory endpoints / `resolveMembers`), with unresolvable owners falling back to their plain identifier. The list payload carries whatever the dialog needs to distinguish these two cases (e.g. an access flag plus owner ids) — it must not require the client to attempt a forbidden read to find out.
- **(PRD 007 Req 11 — server-side boundary)** Workspace list metadata stays readable to any signed-in user while file contents remain unreachable without access: for a workspace with no everyone-access, a signed-in non-member sees it in `GET /api/workspaces` (name, last-modified, owners) yet gets 403 from `GET /api/workspaces/<id>/manifest` and from `GET /api/workspaces/<id>/files/...`. The list response never includes file contents or workspace-scoped settings.
- **(PRD 007 Req 12 — delete)** Workspace settings shows holders of `workspace.delete` a destructive-styled delete action (hidden or disabled for everyone else, per PRD Req 17) that stays inert until the user types the workspace's exact name — exact match, no trimming-away of a wrong name — and then deletes the workspace's server-side data and returns the app to the start page with no workspace bound. `DELETE /api/workspaces/<id>` exists, requires exactly the `workspace.delete` permission (403 otherwise, 404 for an unknown id), and removes **all** blobs under the workspace prefix — manifest, `files/`, comment sidecars and pasted images alike — so a later `GET /api/workspaces` no longer lists it and its blobs are gone from storage.
- **Pure logic is unit-tested (U277+).** The confirm-name match rule, the open-dialog list/search/access-classification mapping, the create-flow form validation (empty/whitespace name, role validation, everyone-access defaulting to Viewer per PRD Req 16), and any owner-name formatting live as pure functions in `src/lib/` (extend `hostedWorkspace.ts`/`membership.ts` or add a sibling module) with vitest tests under `tests/unit/`, per `.sandcastle/CODING_STANDARDS.md`.
- **E2e coverage runs offline (E179+).** New Playwright tests in `tests/e2e/hosted.spec.ts`, numbered from E179 (the current ceiling is E178; note the file already reuses E172–E174 — do not add more collisions), run against the local hosted server on port 4924 with seeded mock users and Azurite only, and observably verify at least: creating a workspace through the UI with an initial member opens it with the creator as Owner and the member in the manifest; the Open dialog lists workspaces, filters as you type, opens an accessible one, and shows the no-access message naming the Owners for an inaccessible one; and the delete flow (name-confirm gate included) removes the workspace so it no longer lists and its files 404/403. Existing tests are not weakened, renumbered, or skipped.
- **Flavor containment and reachability.** The flows are reachable in the running hosted app (e.g. File-menu entries and/or a workspace switcher in the shell) without waiting on issue #78's start-page work, and hosted-only branching stays inside `src/platform/` and hosted-specific components/libs — app code outside `src/platform/` must not branch on the hosted flavor except through the existing platform capability checks (PRD 007 Req 2). Opening or leaving a workspace may be a same-origin navigation that rebinds `?workspace=<id>` (the binding `src/platform/hosted.ts` already reads).
- **Standards, docs, map.** New behaviour carries citation comments (`// PRD 007 Req 10/11/12: …`) per `docs/COMMENT-FORMAT.md`; new or changed endpoints are reflected in `server/README.md`'s endpoint→permission table; `docs/MAP.md` is regenerated via `npm run map` if the citation set changed (the quick gate diffs it). The no-`console.*` rule applies to `src/`.
- **Scope guard.** No membership-management or custom-roles settings UI (#77), no folder/file management, upload/download or ETag conflict UX (#76), no start-page action list (#78), no permission-enforcement sweep beyond the endpoints this issue adds or extends (#79).
- Iteration used `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code), with single hosted e2e tests run via `npx playwright test -g '<title>'` while debugging — the full e2e suite was not used as an inner loop, and any starting baseline used the quick tier only.
- `npm run validate:quick` has been run **once**, at the end, in the implementer's session, and prints `QUICK VALIDATION: ALL PASSED`.
- A summary comment from the implementer exists on issue #75.

# Spec: Editor: pin the content column to the left, not centered (#272)

## Goal

All acceptance criteria in issue-specs/issue-272.md are satisfied for issue #272, with evidence visible in the session: in edit mode — full-screen and split alike, in every theme and in both the desktop and hosted builds — the editor's text column is pinned to the left edge of the editor area with all leftover horizontal space on the right, the line-number gutter sits flush at that left edge with nothing (rule, spacer or centring slack) to its left; the `gutter-inset` left rule together with its measurement machinery and the split slide's centred-column nudge are removed rather than left dead; SPEC6 §1 and `docs/ARCHITECTURE.md` are amended in place to record the new contract; e2e coverage pins the flush geometry with E31 and E136 amended (never weakened or deleted); and `npm run validate:quick` passes.

## Acceptance criteria

### The column pins left

- In edit mode the editor's content column starts at the **left edge of the editor area**: the leftover width between the column's right edge and the pane's right edge is all of the slack, and there is none on the left. Concretely, `.editor-wrap .cm-editor .cm-scroller` no longer centres its flex children — `justify-content: center` at `editor/styles.css:511` becomes the flush-left behaviour that split mode already has, and the now-redundant split-only override (`src/styles.css:1070`, `.workspace.split .split-editor .editor-wrap .cm-editor .cm-scroller { justify-content: flex-start }`) is collapsed rather than left as a duplicate of the base.
- This holds in **full-screen edit** and in **split view's edit half** identically — the split half's geometry (issue #7: hugging the folder seam) is unchanged and is now simply what plain edit does too.
- Any `max-width` cap on the column stays: `.editor-wrap .cm-editor .cm-content` keeps `max-width: var(--mm-content-width, 46rem)`, its `width: 100%`, and its `padding: 56px 32px 96px`. Line length is unchanged; only the anchor moves. The margins presets (narrow / medium / wide / Default) still resize the column, and now spend the whole difference on the right.
- **With line numbers on, the gutter is at the far left**: `.cm-gutters` sits flush against the editor pane's left edge (within ~2px), with the text column immediately to its right. With line numbers off, `.cm-content`'s own left padding is what meets the pane edge. Neither state leaves editor background to the left of the gutter.
- The reading preview (`.doc` / `.docwrap`, `editor/styles.css:27–44`) is **out of scope and unchanged** — it stays centred. Preview mode, the split preview half, and print output are untouched.
- Behaviour is identical in the desktop (Tauri) shim and the hosted/web build, and is not gated on `platform.kind` (the issue's "both builds" line). It is theme-independent: no theme, and no `--mm-*` token, re-centres the column.

### Nothing sits to the left of the line numbers

- The `gutter-inset` left rule is **gone**: `.editor-wrap.gutter-inset .cm-editor .cm-gutters { border-left: … }` (`editor/styles.css:525`) is removed, and no other rule, spacer element or padding is drawn to the left of the gutter. The gutter's **right** rule (issue #63, ungated, reading `--mm-border` rather than CodeMirror's hardcoded `#ddd`) and its themed surface/digit colours (issue #52) **stay exactly as they are** — this criterion removes the left side only.
- The machinery that existed solely to decide when that left rule applied is removed with it, not left dead: `measureGutterInset` / `scheduleGutterInset` / the `paneResize` `ResizeObserver` on the host and on `view.contentDOM`, the `measureGutterInsetRef` and its re-run from the line-numbers toggle effect (`editor/src/components/Editor.tsx:1018–1021, ~1942–1985`), and every `gutter-inset` class reference across `src/`, `editor/`, `tests/` and `docs/`. `rg 'gutter-inset|gutterInset'` returns nothing but, at most, a historical mention inside an amendment note. If any part of that observer is found to serve a second purpose, keep only that part and say so in a citation comment.
- The split slide's centred-column glide (issue #165) is resolved, not left to fight the new anchor: the column no longer moves between plain edit and split, so the transform nudge must not shift it mid-slide. Remove `--mm-split-text-nudge` (`src/styles.css:163`), the two `.cm-scroller > *` transform rules and their `prefers-reduced-motion` carve-out entries (`src/styles.css:1114–1120`, `~1153–1157`), the inline style at `src/App.tsx:7984`, `splitNudgeRef` / `measureSplitNudge` (`src/App.tsx:3060–3085`) and its call sites, and `centeredColumnOffset` from `src/lib/paneSlide.ts` — or, if some of it is still load-bearing, keep only what is and justify it in a citation comment. The rest of issue #165 is untouched: the editor instance still survives the split toggle (`display: contents` on `.split-editor` outside split, the `.preview-pre` first-frame skip), the pane's own width/transform slide still runs on the 180ms curve, and reduced motion still switches instantly.
- The gutter affordances that live in that margin keep working and stay correctly placed at the new anchor: the SPEC43 §3 cursor-line Smart Edit button (`.smart-edit-anchor` / `.smart-edit-btn`, which hangs left into `.cm-content`'s 32px padding — verify it is not clipped now that the padding meets the pane edge) and the PRD 020 Req 18 heading copy-link gutter (`.cm-heading-link-gutter`, `data-testid="heading-copy-link-gutter"`, hosted). Editor chrome that measures live rects — SPEC37 table chips, the image-resize overlay, the find bar, the word-count chip, comment/highlight marks and the comments pane — still lands on the right geometry.

## Context

The centring lives in one declaration: `.editor-wrap .cm-editor .cm-scroller { justify-content: center }` at `editor/styles.css:511`, with `.cm-content` capped at `--mm-content-width` just below. Split mode already overrides it to `flex-start` (`src/styles.css:1070`, issue #7 / issue #165), so split's editor half is the behaviour the whole editor should now have — read those two comment blocks first; they explain why the split case went flush and what the folder seam does to the left edge.

Three things exist only because the column was centred. (1) The `gutter-inset` left rule (`editor/styles.css:514–527`) plus the rAF-scheduled measurement and `ResizeObserver` in `editor/src/components/Editor.tsx` (~1942–1985, ref plumbing at 1018–1021) that decides when there is centring slack either side. (2) The split slide's text-column glide from centred to flush — `--mm-split-text-nudge`, the `.cm-scroller > *` transform rules in `src/styles.css` (~1114–1157), `measureSplitNudge` / `splitNudgeRef` in `src/App.tsx` (3060–3085, applied at 7984), and `centeredColumnOffset` in `src/lib/paneSlide.ts:71–87`. (3) The SPEC6 §1 promise that the edit column sits exactly where preview's does. All three resolve with the anchor change; leaving the nudge in place would actively shift the column right mid-slide.

Grep by citation rather than reading `src/App.tsx` whole: `rg 'gutter-inset' src editor tests docs`, `rg 'mm-split-text-nudge|centeredColumnOffset' src tests`, `rg 'SPEC6 §1' src editor tests`. The amendment pattern for a spec whose contract an issue supersedes is commit `d40f9551` (issue #278 on SPEC23 §1.3) — a dated `> **Amendment (issue #272, …)**` block under the original text, with the "What ships" summary line adjusted. Read `.sandcastle/CODING_STANDARDS.md` (citations, test-id rules, "an existing test is never weakened") and `docs/STYLE-GUIDE.md` before writing code.

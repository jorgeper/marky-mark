# Spec: Remote MCP endpoint (/api/mcp) with workspace file tools (#365)

## Goal

All acceptance criteria in issue-specs/issue-365.md are satisfied for issue #365, with evidence visible in the session: the hosted server exposes a stateless streamable-HTTP MCP endpoint at `POST /api/mcp` that exists only under `MM_AGENT_BRIDGE=1` (ordinary 404 otherwise), authenticates every request with an `Authorization: Bearer <agent token>` header through `resolveAgentToken` / `checkAgentTokenScope` from `server/agentTokens.ts` (401 with the stable authorization error for a missing, unknown or revoked token; no second auth path) and derives the workspace from the token so no tool takes a workspace parameter; it registers exactly the five file tools `get_workspace`, `list_files`, `read_file`, `create_file` (fails on an existing path; base64 binary content follows the upload route's allowlist/size/409 rules) and `write_file` (existing files only; carries the read ETag and inherits the PRD 016 If-Match + three-way merge semantics) over the same functions the `/api/workspaces/<id>/files*` and `upload` routes call, and no session tools; unit tests drive it through `createApp` and hosted e2e tests drive the real endpoint with raw streamable-HTTP calls (mint, list/read/create/write round trip, create-on-existing fails, stale ETag follows PRD 016, revoked token is refused); `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #365.

## Acceptance criteria

### Gating and mounting (PRD 027 Req 2, Req 5)

- `createApp` in `server/app.ts` dispatches `/api/mcp` to a new module (e.g. `server/mcp.ts`) **only when its `agentBridge` parameter is true**. With the flag off (the default), every method on `/api/mcp` answers the API's ordinary 404 `{error: 'no such endpoint'}` before any bridge code runs (no token lookup, no body read). `server/index.ts` needs no change beyond what #364 wired; `npm run server:local` with `MM_AGENT_BRIDGE=1` serves the endpoint, so local mode (mock auth + Azurite) is e2e-testable.
- The endpoint is **stateless** streamable HTTP: `POST /api/mcp` carries one JSON-RPC 2.0 message per request and the answer is a JSON body (`Content-Type: application/json`), never a required SSE stream; no `Mcp-Session-Id` is required (one sent by a client is tolerated). `GET` and `DELETE` on `/api/mcp` answer 405 with an `Allow: POST` header. A body that is not JSON answers JSON-RPC error `-32700`; an unknown method answers `-32601`; a request with a malformed or unknown tool name / params answers `-32602` or a tool error result (see below), never a 500.
- The implementer may build the handler on the official `@modelcontextprotocol/sdk` (`StreamableHTTPServerTransport` in stateless mode with `enableJsonResponse: true`, wired to the existing plain `node:http` request/response; the dependency added to `package.json` with `THIRD-PARTY-NOTICES.md` regenerated by `npm run licenses`, and U798's plain-node boot still passing) **or** as a small in-repo JSON-RPC handler that implements the methods below. Either way the wire behaviour in this section is what tests and the judge observe.
- JSON-RPC methods that work as the MCP spec requires: `initialize` answers `{protocolVersion, capabilities: {tools: {}}, serverInfo: {name, version}}` (the client's requested `protocolVersion` is echoed when it is one the server supports, otherwise the server's latest supported version, e.g. `2025-06-18`); the `notifications/initialized` notification answers HTTP 202 with an empty body; `ping` answers `{}`; `tools/list` answers the five tools with `name`, `description` and a JSON-Schema `inputSchema` each; `tools/call` answers `{content: [{type: 'text', text: <JSON>}], structuredContent?, isError?}`.
- After this lands, `claude mcp add --transport http <name> <origin>/api/mcp --header "Authorization: Bearer <token>"` connects with no local server install. `server/README.md` states that invocation.

### Auth: one path, token identifies the workspace (PRD 027 Req 4, Req 5)

- Every `POST /api/mcp` request (including `initialize`) reads `Authorization: Bearer <token>` and resolves it with `resolveAgentToken` from `server/agentTokens.ts`. A missing header, malformed, unknown or revoked token answers **HTTP 401** with header `WWW-Authenticate: Bearer` and a JSON body carrying the explicit authorization error as a stable `{error: {code, message}}` whose constant lives in `server/agentTokens.ts` (reuse `AGENT_TOKEN_SCOPE_ERROR` or add one sibling constant of the same shape there, e.g. `AGENT_TOKEN_UNAUTHORIZED_ERROR`). Revocation is honoured by the very next request (the helper has no cache; the endpoint adds none).
- The workspace is the resolved token's `workspaceId`. **No tool's `inputSchema` has a workspace property**, and no tool reads one. Every blob path a tool touches is checked with `checkAgentTokenScope(resolved, workspaceId, blobPath)` before any storage access; a refusal (e.g. a `read_file` path containing `..`, or one that escapes `workspaces/<id>/files/`) surfaces as a tool error result with `AGENT_TOKEN_SCOPE_ERROR.code` (`agent_token_out_of_scope`) and its message. The endpoint adds no second token lookup, hash scheme or scope rule (the doc comment in `server/agentTokens.ts` is honoured).
- Agent tokens never appear in any log line or in any response body after mint: no `console.*` in the new module prints a header, a token or a hash.

### File tools (PRD 027 Req 6)

- `tools/list` returns **exactly** these five names and nothing else (no session tools: `get_editor_state`, `open_file`, … arrive with issue #367): `get_workspace`, `list_files`, `read_file`, `create_file`, `write_file`. Every `inputSchema` is `type: 'object'` with `additionalProperties: false` and an explicit `required` list.
- `get_workspace` (no params) answers the workspace's `{id, name, created, modified}` from its manifest; a deleted/absent workspace answers a tool error (`not found`).
- `list_files` (no params) answers `{files: [{path, size, lastModified, etag}]}` — the same rows, workspace-relative paths, as `GET /api/workspaces/<id>/files`.
- `read_file` `{path}` answers `{path, content, etag}` exactly as `GET /api/workspaces/<id>/files/<path>` does (utf-8 text); an absent path answers a tool error `not found`; an invalid path (`cleanRelativePath` refuses it) answers a tool error `invalid file path`.
- `create_file` `{path, content?: string, contentBase64?: string}` (exactly one of `content` / `contentBase64`; both or neither is a params error) creates a file that does not exist yet and answers `{path, etag, size}`. **A path that already holds a blob answers a tool error (`already exists`) and stores nothing.** Text `content` lands as the files `PUT` create does (`storage.write`, then no If-Match). `contentBase64` is decoded and lands as `PUT /api/workspaces/<id>/upload/<path>` does: `uploadTypeRejection` (415 rule → tool error), `uploadRejection` size cap (413 rule → tool error), `contentTypeFor(path)` as the stored media type, `storage.writeBytes`. An invalid base64 string is a params error.
- `write_file` `{path, content, etag, base?}` updates an **existing** file only (an absent path answers a tool error `not found` that names `create_file`). `etag` is required and carries the ETag from `read_file`/`create_file`. Behaviour is byte-identical to `PUT /api/workspaces/<id>/files/<path>` with `If-Match: <etag>` and a JSON `{content, base?}` body (PRD 007 Req 20 + PRD 016 Reqs 7–8): a matching ETag writes and answers `{path, etag}`; a stale ETag with a `base` that merges cleanly (through `mergeStaleSave`, structured-file guard and retry cap included) answers `{path, etag, merged: true, content}`; a stale ETag with no `base`, a conflicting merge, a guard refusal or exhausted retries answers a tool error `conflict` with the PRD 016 message (`the file changed on the server since it was loaded`) and the path, **with the stored content untouched**. The error may additionally carry the current `etag` and `content` so an agent can re-read and retry.
- Tool errors are `tools/call` results with `isError: true` whose text is JSON `{error: {code, message, path?, …}}` with a stable `code` per case above (`not_found`, `already_exists`, `conflict`, `invalid_path`, `invalid_params`, `unsupported_type`, `too_large`, `agent_token_out_of_scope`); they are never JSON-RPC protocol errors and never 500s.

### Never a parallel storage path

- The list/read/create/write/upload semantics exist **once**: the storage-touching logic is factored into exported functions in `server/workspaces.ts` (or a sibling such as `server/workspaceFiles.ts` that `workspaces.ts` imports) and both `handleWorkspaceApi` and the MCP tools call those functions. After the change, `mergeStaleSave`, `writeIfMatch`, `uploadTypeRejection`, `uploadRejection` and `contentTypeFor` are each called from one place on the file-write path (grep-verifiable), and the existing route tests (`tests/unit/server-workspaces.test.ts`, `server-merge-save.test.ts`, the hosted e2e suite) pass unchanged. Permission checks (`requirePermission`) stay in the route layer; the MCP layer authorizes with the token instead, which is the PRD 027 Req 4 model.
- The new module imports nothing from `server/providers/azure/*` and reaches storage only through the `StorageProvider` seam it is handed (the same `providers.storage` the routes use). `server/agentBridge.ts` (the session broker) is **not** wired in here.

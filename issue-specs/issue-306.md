# Spec: marky mark button in preview mode (#306)

## Goal

All acceptance criteria in issue-specs/issue-306.md are satisfied for issue #306, with evidence visible in the session: the preview selection button (`data-testid="smart-edit-selection"`, PRD 023 §13) no longer renders over the document text — it sits in the `.doc` left padding column like the edit-mode gutter glyph, its right edge at or left of the doc's content-left edge whatever column the selection starts in; it is vertically level with the selection's FIRST line box rather than the centre of the whole selection rect; both preview surfaces (full preview and the split-edit preview pane) derive the position through the same function; the existing E465–E469/E474 tests still pass and a new e2e test proves the margin placement for a mid-line selection; `npm run validate:quick` has been run in the implementer's session and passed; and a summary comment from the implementer exists on issue #306.

## Acceptance criteria

- **The button lives in the doc's left margin, never over the words.** With text selected in the full preview, the button's bounding box satisfies `btn.x + btn.width <= contentLeft`, where `contentLeft = doc.getBoundingClientRect().left + parseFloat(getComputedStyle(doc).paddingLeft)` for the `[data-testid="doc"]` element hosting the selection — i.e. the box lies inside the `.doc` 32px padding column (`editor/styles.css` `.doc { padding: 40px 32px 96px }`), mirroring the edit-mode glyph, which hangs in `.cm-content`'s 32px left padding with a 4px gap to the line start (SPEC43 §3, `editor/styles.css` `.smart-edit-btn`). This must hold for a selection that starts mid-line (today `previewButtonPos` in `src/App.tsx` puts the 24px glyph one 6px gap left of the selection rect's left edge, so a mid-line selection lands it on top of the preceding words — the issue's screenshot). Use the same 24px size and a 4px gap to the content edge (24 + 4 = 28 ≤ 32, so it fits the column); `btn.x >= doc.getBoundingClientRect().left` in the default centered layout.
- **Level with the selection's first line.** The button is vertically centred on the selection's first line box — the first non-empty rect of `range.getClientRects()` — not on the centre of the whole `getBoundingClientRect()`. For a single-line selection this is indistinguishable from today; for a selection spanning several lines or blocks the button stays beside the line where the selection starts (the edit-mode glyph likewise rides one line). Assert: `btn.y < firstRect.bottom && btn.y + btn.height > firstRect.top`.
- **Clamping is preserved.** The button still never rises above the issue #18 toolbar floor (`toolbarFloor: 46` in `PREVIEW_BTN`; E465 asserts `y >= 42`) and is clamped inside the viewport on the right/bottom edges; it still re-measures on scroll and resize and rides the selection (the existing `onSelection` listener set). Whatever is needed to compute the margin position (the host doc's rect and padding) is measured in that same handler or in `previewButtonPos`, so scroll never leaves it detached.
- **Both preview surfaces share the placement.** The full preview (`docRef`) and the split-edit preview pane (`splitDocRef`, E466) derive the position through the one function (`previewButtonPos` or its successor), each fed its own doc element's rect — no second copy of the arithmetic. The split editor half still never grows the button.
- **Nothing else about the button changes.** Same `icon-btn smart-edit-btn preview-sel-btn` classes and test id, same `title`, same mousedown-with-preventDefault opening of the annotation-only menu (E467–E469), same commentsEnabled/frozen/`mayComment` gate (absent, not disabled), same `position: fixed; z-index: 80` in `src/styles.css`, still hidden in print, still never inside `.doc`'s text space (no text nodes added to the preview root — `getDocText()` byte-identical).
- **Existing tests pass unchanged.** E465, E466, E467, E468, E469 (`tests/e2e/comments.spec.ts`) and E474 (`tests/e2e/hosted.spec.ts`) pass without edits. E465's `box.x + box.width <= rect.left` still holds because the content-left edge is at or left of any selection inside the doc.
- **A new e2e test proves the margin placement.** In `tests/e2e/comments.spec.ts` beside E465, a new test with the next free E-number (E565 at time of writing; confirm with `grep -rhoE "test\('E[0-9]+" tests/e2e | sed 's/.*E//' | sort -n | tail -1`) selects a phrase that starts mid-line (assert the selection's first rect `left` is materially right of `contentLeft`, so the test would have failed before the fix), then asserts the button box is inside the padding column (`x + width <= contentLeft`, `x >= docLeft`) and vertically intersects the selection's first line rect. Also cover a selection spanning two paragraphs (a `Range` from one text node to a later block's text node built in `page.evaluate`) and assert the button intersects the FIRST paragraph's first line rect, not the second's. Use `stableBox` from `helpers.ts` before measuring.
- **Citations and docs.** Changed code carries the repo citation format naming PRD 023 §13 and issue #306 per `.sandcastle/CODING_STANDARDS.md`; the JSDoc on `previewButtonPos` / `PREVIEW_BTN` and the render-site comment near `data-testid="smart-edit-selection"` in `src/App.tsx` (both currently say "one gap LEFT of the selection rect") are updated to describe the margin placement; `docs/MAP.md` is regenerated with `npm run map` if the spec→code table changes.
- **Iteration and the gate.** The implementer iterates with `npm run typecheck` and `npm run test:unit` (plus `npx playwright test -g '<title>'` for the touched e2e tests), baselines with the quick tier only, and runs `npm run validate:quick` ONCE right before declaring the goal met; it prints `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- **A summary comment from the implementer exists on issue #306** describing what changed, the placement rule, and the gate evidence.

## Context

The issue body: "its rendering over the text i dont want this, i want it to be on the left margin like it is in the edit mode, as aligned as posible with the selection", with a screenshot (not downloadable here) of the preview showing the blue hash glyph drawn across a paragraph's words. The "marky mark button" is the preview selection button from PRD 023 §13 (issue #287, `prd/023-comments-highlights-split.md`): `src/App.tsx` renders it at the `PRD 023 §13` citation near `data-testid="smart-edit-selection"`, positioned by `previewButtonPos(selInfo)` (defined beside `PREVIEW_BTN` near the top of `App.tsx`), where `selInfo.x/y/h` come from `range.getBoundingClientRect()` in the preview selection tracking effect (grep `preview selection tracking`). Styling is `.smart-edit-btn.preview-sel-btn` in `src/styles.css` (fixed, 24px, z-index 80).

The edit-mode reference: `SmartEditWidget` in `editor/src/components/Editor.tsx` (SPEC43 §3) parks a zero-size anchor at the line start and hangs the 24px button left into `.cm-content`'s 32px padding with `right: 4px` (`editor/styles.css` `.smart-edit-btn`). The preview `.doc` has the same 32px side padding and is centred inside `.docwrap` (`editor/styles.css`), so the equivalent is `left = docRect.left + paddingLeft - 24 - 4`, then the existing viewport/toolbar clamps. Suggested approach (implementer's call): extend `selInfo` with the host doc's content-left edge (measured in the same `onSelection` handler, which already has `doc`) and the first line rect's top/height, and let `previewButtonPos` use those; the handler already re-runs on scroll/resize so the values stay fresh. Test models: E465 in `tests/e2e/comments.spec.ts` (`selectPhrase`, `stableBox`, `PHRASE` from `helpers.ts`), E466 for the split pane. Real commands: `npm run typecheck`, `npm run test:unit`, `npm run test:e2e`, `npm run validate:quick`, `npm run map`.

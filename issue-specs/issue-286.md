# Spec: Editor authoring: kill the selection popup, add Marky Mark menu Comment/Highlight entries and their hotkeys (#286)

## Goal

All acceptance criteria in issue-specs/issue-286.md are satisfied for issue #286, with evidence visible in the session: the selection popup is gone from both surfaces (no `marker-popup`, no `marker-popup-edit`, no SPEC25 comment carry, no type-to-comment) and the Marky Mark smart-edit menu carries **Comment** and **Highlight** below **Diagram** in both builds — Comment offering Insert Comment (showing its hotkey) and Delete Comment by caret context, Highlight offering the four marker colors plus Remove Highlight, with a selection always winning over caret context and the word under the caret as the no-selection anchor; Insert Comment creates the record, auto-opens the comments pane and focuses the composer without ever switching modes; two rebindable hotkeys default `Mod+Alt+M` and `Mod+Alt+H` ship in the hotkey map, the Settings → Hotkeys recorder and the menu rows, and work in the editor (word fallback) and in the preview (selection required); editor-side authoring maps selection/caret to rendered-text anchors and disables the entries rather than mis-anchoring where the mapping is ambiguous; unit coverage for the menu context model and e2e coverage for insert/delete/recolor/remove plus both hotkeys land with the popup-based suites rewritten to the new UX; and `npm run validate:quick` passes.

## Acceptance criteria

### Killing the popup (PRD 023 Req 6)

- No selection popup exists in any mode or build: `marker-popup`, `marker-popup-edit`, `add-note-btn` and the `marker-swatch-*` buttons are gone from `src/App.tsx` (the `markerPopupButtons` helper with them), and their rules are gone from `src/styles.css` — except any swatch/tint rule the new menu genuinely reuses, which keeps its rule and gains a citation saying so. Selecting text in the preview, in the split live preview and in plain edit produces **no** floating affordance.
- The SPEC25 **comment carry** is gone: `carryActionRef`, the carry-consuming effect and the edit-mode affordance's `toggleMode()` route are removed. SPEC25's ordinary selection/caret carry across a mode switch (`pendingEditorSelRef` / `pendingPreviewSelRef` / `lastEditorSelRef`) is untouched — authoring never switches modes again, but Mod+E still lands the caret where it always did.
- **Type-to-comment is removed** end to end: the printable-key effect in `src/App.tsx`, the `typeToComment` setting (`src/lib/settings.ts` field, default, scope-map entry and parser entry), its Settings → General row and scope note in `src/components/SettingsPanel.tsx`, and the unit assertions that pin it (`tests/unit/settings.test.ts`, `tests/unit/settings-resolver.test.ts`) are gone or rewritten. A persisted settings file that still carries `typeToComment` parses without throwing and without resurrecting the behaviour, and the vim-nav "a live selection belongs to type-to-comment" guard in `src/App.tsx` is either dropped or re-justified in its comment.
- `src/lib/commentAffordance.ts` and `tests/unit/comment-affordance.test.ts` are either deleted with the popup or repurposed into the new authoring gate below — no dead module, no dead exports, and no `affordanceSurface`/`editHasSelection` state left computing something nothing renders.
- The `selInfo` selection tracking that preview authoring still needs (hotkeys here, the selection button in issue #287) survives the removal, and the word-count chip's selection-aware path (`src/App.tsx` ~5759) keeps working.

### The menu entries (PRD 023 Req 7)

- `buildSmartMenu` (`editor/src/lib/smartEdit.ts`) emits two new top-level submenu items, **Comment** then **Highlight**, immediately below **Diagram** and above the separator that precedes Bold — the Table/Image/Code Block/Diagram idiom (`item(id, label, { submenu })`), with ids that collide with nothing existing.
- Both entries are present in the desktop shim **and** the hosted build — the menu is build-agnostic and nothing gates them on `platform.kind`.
- They are gated by the same authoring conditions as today's affordance: with `commentsEnabled` off, with an unreadable/frozen store (`authoringFrozen`, PRD 004 Req 15) or without `comment.write` for the document (`docGrants.commentWrite`, PRD 007 Req 17), **neither entry appears at all** — matching the popup's all-or-nothing gate. Which way the gate is expressed (absent vs. present-disabled) is pinned in a citation comment and in a unit test; absence is the default this spec asks for.
- The entries reach the package through a **seam**, never a reverse import: a new field on `SmartMenuCtx` carrying the app's annotation context plus a callback prop for invocation (the `onToggleDiagramView` / `onInsertImage` precedent). `editor/` imports nothing from `src/`; the editor-package-boundary check in `scripts/validate.mjs` passes.

### Comment ▸ (PRD 023 Req 8)

- The Comment submenu lists **Insert Comment** (with its hotkey rendered through `displayCombo`, like every other hotkeyed row) and **Delete Comment**, both rows always listed and each enabled by its own condition — the Table submenu's Insert/Delete idiom, so the submenu is never empty.
- **Insert Comment** is enabled when there is a selection, or (no selection) a word under the caret; it creates a `kind: "comment"` 2.0.0 record over that range, **opens it in the comments pane with the composer focused and empty, ready to type**, and **never switches modes** — invoking it in plain edit leaves the user in plain edit, with the pane auto-opened by the existing `pending` effect (PRD 023 §15).
- Cancelling the composer removes the freshly created empty record (the existing no-abandoned-entry rule); submitting lands the body on it and makes it the active card.
- **Delete Comment** is enabled when the caret sits inside an existing **comment**'s painted range (not a highlight's); invoking it removes that record, its card and its marks in both surfaces. With several comments overlapping the caret the record is picked by the existing kind-aware rule (`pickHitRecord`, `src/lib/markHit.ts`) rather than a second, divergent rule.
- A selection always wins over caret context here too: a selection that overlaps an existing comment offers Insert Comment on the selection, and inserts a new record rather than touching the old one.

### Highlight ▸ (PRD 023 Reqs 9–11)

- The Highlight submenu lists the four marker colors in the fixed `MARKER_COLORS` vocabulary order (yellow, green, orange, pink) — rows never reorder by last-used, though the armed color may carry a cue — plus **Remove Highlight**.
- **With a selection** (selection always wins over caret context), picking a color inserts a `kind: "highlight"` record in that color over the selection, even when the selection overlaps an existing highlight, and updates the last-used marker color.
- **With no selection and the caret on an existing highlight**, the same color rows **recolor that record** in place (same id, same anchor, new `color` — no second record) and **Remove Highlight** is enabled and deletes it. Recolor also updates the last-used color; Remove Highlight is disabled in every other context.
- **With no selection and no existing highlight at the caret**, the color rows insert a highlight over the **word under the caret** (`wordAt`, SPEC44 §1, with its left affinity).
- **With no selection and no word** (empty line, a caret in a whitespace/punctuation run), the color rows and Insert Comment are **disabled** — present, greyed, invoking nothing.
- The last-used marker color stays the user-scoped `lastMarkerColor` setting with PRD 022 Req 4 semantics; **no per-color hotkeys and no custom colors** are added (PRD non-goals).
- Comment records still carry no color and highlight records no body — the 2.0.0 schema from issue #283 is unchanged, and every record this slice authors round-trips through the existing writer.

### Editor → rendered-text anchoring (PRD 023 Req 19)

- Editor-side authoring produces anchors in **rendered-plain-text space** — the same space `createAnchor` / `reanchor` / the preview use — so a comment or highlight authored in plain edit paints on the same words when the document is opened in preview, and vice versa.
- Where the mapping is ambiguous — the selection's visible text is absent from the rendered text, or occurs several times with no confident winner, or the selection crosses markdown syntax that renders away — the affected entries are **disabled rather than mis-anchored** (the PRD 022 Req 12 skip rule extended to authoring). No entry ever writes a guessed anchor.
- The mapping and the enabled/disabled decision are **pure logic in `src/lib/`** (a new small module, or an addition to an existing one) with a matching `tests/unit/<kebab-case>.test.ts`: unique hit, zero hits, several hits with and without a context winner, a selection crossing inline markup, a caret in a fenced code block, an empty-line caret.
- Plain edit renders no HTML today (the render effect at `src/App.tsx` ~6001 returns early when `mode !== 'preview' && !settings.splitEdit`), so the implementer supplies rendered text for edit-mode authoring — a debounced cache alongside the existing editor-highlights effect, or an equivalent — and states in a citation how it stays off the keystroke path. Menu open stays synchronous: no `await` between the click and the entries appearing.

### Hotkeys (PRD 023 Req 12)

- Two new rebindable actions land in `HotkeyMap` / `DEFAULT_HOTKEYS` (`editor/src/lib/hotkeys.ts`) with defaults **`Mod+Alt+M`** (Insert Comment) and **`Mod+Alt+H`** (Highlight in the last-used color), each with a `CommandId` in `src/lib/commands.ts` and a binding in the App's keydown listener, dispatched through the registry like every other hotkey (never a second handler path).
- Neither default collides with a shipped combo (`combosConflict` over `DEFAULT_HOTKEYS` stays clean), and both appear in Settings → Hotkeys with a `HOTKEY_LABELS` entry, a working recorder, conflict detection against existing bindings and a restore-default button.
- Both combos render in their menu rows through `displayCombo`; **rebinding one updates the row it shows on** the next menu open.
- In the **editor** they act on the selection, else the word under the caret, else do nothing (the Req 10 disable, as a silent no-op); in the **preview** they require a selection and are silent no-ops without one. `Mod+Alt+H` applies the last-used color through the **same context model as the menu's color rows** (selection inserts; no selection with the caret on an existing highlight recolors it to the last-used color; otherwise the word under the caret).
- Both are inert under the same gate as the menu entries (comments disabled, frozen store, no `comment.write`) and never steal the combo while a dialog, the settings recorder or a text input has focus (the existing guard at `src/App.tsx` ~4427).

### Scope boundaries

- The **preview selection button** (PRD 023 Req 13, issue #287) is out of scope: preview authoring in this slice is the two hotkeys only. Nothing here pre-builds the button, and the annotation menu model is left shaped so #287 can reuse it.
- No change to the comment format (#283), the comments pane's geometry/slide/persistence (#284), the dual-surface rendering and two-way sync (#285), or comment copy-link (#288). Cards keep the behaviour #284 left them with — in particular they grow no recolor swatches back.

## Context

The popup lives in `src/App.tsx` at the JSX tail (~7925–7970: the `marker-popup` preview block and the `marker-popup-edit` block), fed by `markerPopupButtons` / `createHighlight` / `startComposer` (~6580–6670), the SPEC25 carry effect (~6677–6692) and the type-to-comment effect (~6694–6725); the gate is `commentAffordanceSurface` (`src/lib/commentAffordance.ts`, called at ~6888) over `mayComment` = `!authoringFrozen && docGrants.commentWrite` (~549). CSS: `src/styles.css:861–910`.

The menu is the editor package: `buildSmartMenu` + `SmartMenuCtx` in `editor/src/lib/smartEdit.ts:344–472` (Diagram is the last submenu before the separator), rendered by `editor/src/components/SmartEditMenu.tsx` — rows get `data-testid="smart-edit-<id>"` and flyouts `smart-edit-flyout-<id>`, which is what e2e should select on. Context is computed fresh at open time in `openMenuAt` (`editor/src/components/Editor.tsx:1060`) and invocation is `invokeMenuItem` (~1198), whose early-return blocks are the pattern for routing new ids back to the app through a prop.

The app already receives everything the context model needs: `onEditState` reports `{ canonHead, head, headLine, selFrom, selTo, selText, focused }` on every selection change (`handleEditState`, `src/App.tsx:1414`), `wordAt` (`editor/src/lib/activePosition.ts`) gives the word under the caret, and the debounced `editorHighlights` effect (~5729) already holds every painted record as **source** ranges via `mapHighlightsToSource` (`src/lib/anchoring.ts:253`) — the natural way to ask "is the caret on a comment / a highlight". `pickHitRecord` (`src/lib/markHit.ts`) is the kind-aware picker. For the authoring direction, `visibleTextForRange` / `findNormalized` / `countNormalized` / `renderedOffsetForSource` in `editor/src/lib/selectionMap.ts` are the existing source↔rendered tools, and the split mirror at `src/App.tsx:1439–1463` shows the "locate the visible text, fall back when it is not unique" shape. Anchors are built by `createAnchor(docTextRef.current, start, end)` — note `docTextRef` is only filled from a rendered DOM (`reanchorAndHighlight`, ~6066), which plain edit does not have.

Hotkeys: the map and `displayCombo` are `editor/src/lib/hotkeys.ts`; the app's listener and the Smart Edit `fmt` table are `src/App.tsx:5820–5930`; the command ids are `src/lib/commands.ts`; the recorder rows are `HOTKEY_LABELS` / `SMART_EDIT_KEYS` in `src/components/SettingsPanel.tsx:113–175` and the render at ~985. The composer and pane are `panelInner` (~6940, `composer-input` already `autoFocus`) with the auto-open effect at ~6784.

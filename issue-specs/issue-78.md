# Spec: Unified start pages: hosted start page and client start-page parity (#78)

## Goal

All acceptance criteria in issue-specs/issue-78.md are satisfied for issue #78, with evidence visible in the session: the hosted start page offers exactly drag-a-file, Open File, New Workspace and Open Workspace — no Open Folder — and opening or dropping a local file there opens it fully client-side with nothing uploaded and no workspace required; the desktop/web start page and File menu carry the same capability-gated action list (drag a file, Open File, Open Folder, New Workspace, Open Workspace — the PRD 002 local kind), so the four flavors present one consistent entry surface; the list is produced by one shared capability-driven surface with no `kind === 'hosted'` branching in app code; the new behaviour is pinned by unit tests (U311+) and offline e2e tests (E199+); and `npm run validate:quick` has been run once at the end in the implementer's session and prints `QUICK VALIDATION: ALL PASSED`.

## Acceptance criteria

- **(PRD 007 Req 21 — the hosted start page's action list)** Signed in to the hosted flavor with no workspace bound (`lifecycle.currentId()` is null — the state `navigateTo(null)` lands on), the start page shows exactly four affordances: a drop target reading as "drag a file here", **Open File**, **New Workspace…** and **Open Workspace…**. **No Open Folder** appears — note the trap: `src/platform/hosted.ts` *does* define `openFolderDialog` (it answers the bound workspace's blob root so the sidebar renders at all), so "the platform has `openFolderDialog`" is the wrong derivation. The action list must be derived from what the platform declares about *local* folder opening (e.g. a new explicit optional capability/flag on the seam in `src/platform/types.ts`, in the style of `permanentDelete`), never from `kind === 'hosted'` (PRD 007 Req 2). New Workspace… / Open Workspace… on the hosted start page drive the hosted lifecycle flows that already exist (`NewWorkspaceDialog` / `OpenWorkspaceDialog` in `src/components/WorkspaceSwitcher.tsx`, `platform.workspaces`), and choosing a workspace lands in that workspace exactly as the switcher chip does today.
- **(PRD 007 Req 21 — hosted local-file mode, fully client-side)** In the hosted flavor, **Open File** opens the browser's file picker and a Markdown file dragged onto the start page opens too — both while no workspace is open, and neither requires one. Today `hosted.ts` `openFileDialog()` returns null and `onFileDrop()` is a deliberate no-op; both gain real implementations modelled on the web build (`src/platform/web.ts` — `pickViaInput` / `showOpenFilePicker`, the in-memory `docs` map, write-through to an `FSFileHandle` when the browser grants one, otherwise a download on save). The opened document is editable, renders, and is **never uploaded**: no `PUT`/`POST` to `/api/workspaces/...` results from opening, editing or saving it, and the doc's path does not resolve to a workspace target (`parseHostedPath`). Prefer extracting the web build's local-doc machinery into a module both `web.ts` and `hosted.ts` use over copy-pasting it; keep the bundle-scan/no-`console.*` rules satisfied.
- **(Hosted drop targets stay disjoint)** With a hosted workspace open, dropping an OS file on the folder sidebar is still the #76 **upload** (`FolderPanel`'s upload drop, `file.upload`, 20 MB + type allowlist) — this issue must not regress it. The new window/start-page drop only opens a local Markdown file client-side, and the two must not both fire for one drop. State which surface owns which drop in the citation comment.
- **(PRD 007 Req 22 — the client start page)** The desktop and web start pages (the splash at `src/App.tsx` § SPEC27 §3, `data-testid="empty-hint"` — keep that testid, ~14 existing e2e assertions depend on it) gain the same action list, each row present only where the flavor can honour it: **Open File** always; **Open Folder…** where the platform can pick a real local folder; **New Workspace…** and **Open Workspace…** where local workspaces apply (`openWorkspaceDialog` + `readDirEntries`, per PRD 002 §D14); plus the existing drag-a-file hint. Consequences to verify, not to special-case: desktop/shim shows all five, the single-file **web build shows only the drag hint and Open File** (it has no folder or workspace seam), and hosted shows the Req 21 four. The splash keeps its identity (badge, version, alpha line, developer/licence/repo lines) — the action list is added to it, not a replacement screen.
- **(PRD 007 Req 22 — the File menu carries the equivalent entries)** `src/lib/menuSpec.ts` gains **New Workspace…** beside the existing **Open Workspace…** in *both* the mac and non-mac File submenus, and both entries — plus **Open Folder…** — are present only when the flavor supports them, so the hosted File menu shows New/Open Workspace but **no Open Folder…**, and the web build shows neither. The items route to the flavor's own flow: hosted → the hosted lifecycle dialogs; local → the PRD 002 dialogs. Start page and File menu must not diverge: whatever the start page offers, the File menu offers, and vice versa.
- **(PRD 007 Req 22 — local New Workspace… exists)** There is no local "new workspace" command today (a local workspace is only reachable via Open Folder + Save Workspace As…). Add one whose observable end state is: the user names/places a new `.marky-workspace` file (`saveFileDialog(…, 'workspace')`), the file exists on disk as valid PRD 002 workspace JSON, the app is in the **named workspace** state bound to it (title/switcher reflect it, `Save Workspace As…`/`Add Folder to Workspace…`/`Close Workspace` enabled), it joins recent workspaces, and the sidebar shows the workspace with no roots yet plus a way to add one. Whether the flow also asks for a first folder up front is the implementer's call as long as that end state holds and cancelling at any step changes nothing. The unsaved/untitled-workspace discard guard (`guardWorkspaceDiscard`) runs before an open workspace is replaced, exactly like Open Workspace… does.
- **(One surface, no flavor branching)** The action list is one shared component (e.g. `src/components/StartPage.tsx`) fed by a **pure** function in `src/lib/` that maps platform capabilities → the ordered list of actions to show. App code outside `src/platform/` must not branch on `kind === 'hosted'` (PRD 007 Req 2); hosted-specific transport stays in `src/platform/hosted.ts`. Rows are keyboard-reachable buttons with stable `data-testid`s, styled from theme variables in `src/styles.css` (no hard-coded colours), and the start page stays pointer-interactive despite `.empty-center`'s `pointer-events: none`.
- **Pure logic is unit-tested (U311+; the current ceiling is U310).** The capability→action-list mapping (all four flavors, including the hosted "has `openFolderDialog` but must not offer Open Folder" case), the File-menu item gating in `menuSpec.ts`, and any new-local-workspace decision helper are pure functions covered by vitest tests under `tests/unit/`, per `.sandcastle/CODING_STANDARDS.md`.
- **E2e coverage runs offline (E199+; the current ceiling is E198 — do not renumber, weaken or skip existing tests).** New Playwright tests (`tests/e2e/hosted.spec.ts` for the hosted flavor against the local server on 4924 with Azurite + seeded mock users, `tests/e2e/shell-and-menus.spec.ts` / `tests/e2e/tabs-and-workspace.spec.ts` for the shim, `tests/e2e/web.spec.ts` for the single-file build) observably verify at least: the hosted start page showing exactly the four actions with no Open Folder anywhere (start page or File menu); a local file opened on the hosted start page rendering in the editor with **no upload request** and no workspace bound; the hosted New/Open Workspace actions landing in a workspace; the shim start page showing all five actions with Open Folder… and Open Workspace… actually opening a folder/workspace; local New Workspace… producing a named workspace whose `.marky-workspace` file exists; and the web build showing only the drag hint + Open File. No test may require Azure or external network.
- **Standards, docs, map.** New behaviour carries citation comments (`// PRD 007 Req 21/22: …`) per `docs/COMMENT-FORMAT.md` and `.sandcastle/CODING_STANDARDS.md`; `docs/MAP.md` is regenerated via `npm run map` if the citation set changed (the quick gate diffs it); no `console.*` in `src/`.
- **Scope guard.** No new hosted endpoints or permission changes (#79 owns the enforcement sweep), no changes to upload/download or ETag behaviour (#76), no membership/roles UI changes (#77), no multi-file open, no recent-workspaces redesign, no reworking of the sign-in gate.
- Iteration used `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code), with single e2e tests run via `npx playwright test -g '<title>'` while debugging — the full e2e suite was not used as an inner loop, and any starting baseline used the quick tier only.
- `npm run validate:quick` has been run **once**, at the end, in the implementer's session, and prints `QUICK VALIDATION: ALL PASSED`.
- A summary comment from the implementer exists on issue #78.

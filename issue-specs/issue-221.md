# Spec: Scratch rename, usernames, and /scratch shortcut (PRD 020 Reqs 10–13) (#221)

## Goal

All acceptance criteria in issue-specs/issue-221.md are satisfied for issue #221, with evidence visible in the session: the scratchpad feature is renamed to scratch — friendly name "My scratch", canonical URL `/<username>/scratch` with `scratch` reserved as a second path segment and the old `/scratchpad` route replaced, not kept; visiting `/scratch` signed-in lands on the visitor's own `/<username>/scratch`, creating the workspace on first use per PRD 019 Reqs 5–7; each user's URL segment is derived once at first sign-in (identity local part, lowercased and slugified, deduped deployment-wide), stored in per-user storage, never re-derived, and shown to the user where the signed-in identity is displayed; files saved in a scratch workspace get canonical URLs under `/<username>/scratch/…` that a caller with access can follow; and `npm run validate:quick` passes in the implementer's session.

## Acceptance criteria

- **Username derivation (Req 12).** A pure, unit-tested module derives a user's URL segment: the local part of their identity (AAD alias for members, email local part for guests — the part before `@`), lowercased and slugified to Req 1's charset (the #219 migration slugify in `src/lib/workspaceNames.ts` / `server/workspaces.ts` is the precedent), deduped deployment-wide with `-2`, `-3`… suffixes. Reserved words (`RESERVED_WORKSPACE_NAMES` — `scratch`, `scratchpad`, `api`, `assets` — plus any other top-level route words in use) count as taken during dedupe, so no username ever shadows `/api/…` or the reserved routes. Unit tests cover slugify, dedupe, reserved avoidance, and guest-style identities.
- **Assigned once, stored, never re-derived (Req 12).** The server assigns the username at the user's first authenticated touch and persists it: a record in their per-user storage (the `scratchpadPointerBlob` precedent, `server/workspaces.ts` ~461) plus whatever deployment-wide claim makes dedupe and username→user resolution possible (there is no database — one blob per claim with the `writeIfAbsent` race pattern from `handleScratchpadResolve`, ~535, so two concurrent first sign-ins mint exactly one username each and a contested slug goes to exactly one user). Later sign-ins read the stored value even if the underlying identity string changes. Unit tests cover idempotency and the concurrent-claim race.
- **Username visible (Req 12).** `GET /api/me` (`server/app.ts` ~112) returns the assigned segment under a field distinct from the existing `username` (which is the UPN — `AuthUser` in `server/providers/types.ts`, `SessionMe` in `src/lib/deploymentSettings.ts`); the UI shows the signed-in user their username and thus their scratch URL wherever the signed-in identity is displayed. No chrome surface currently shows the user their own identity, so the implementer adds at least one discoverable signed-in-identity surface (placement is their design choice; styled per `docs/STYLE-GUIDE.md`) showing display name, username, and the `/<username>/scratch` URL.
- **Rename (Req 10).** The feature's user-facing name is scratch: newly created per-user workspaces get the friendly name "My scratch" (`SCRATCHPAD_NAME`, `server/workspaces.ts` ~453), the Open-dialog badge reads "My scratch" (`src/lib/workspaceLifecycle.ts` ~157), and a pre-existing scratch workspace also displays as "My scratch" (migration or display-time mapping — implementer's choice, idempotent either way).
- **Routing (Req 10).** `parseAppPath` (`src/lib/hostedPaths.ts`) treats `scratch` as a reserved second segment: `/<seg1>/scratch[/<file…>]` always addresses user seg1's scratch workspace (and optionally a file in it), never a folder named `scratch` inside workspace seg1 (the documented shadowing, PRD 020 Non-goals). The old `/scratchpad` recognition (`SCRATCHPAD_PATH`, `isScratchpadPath`) is removed — `/scratchpad` falls through to normal workspace-name resolution and, the name being reserved, renders the Req 8 not-found page. Unit tests cover the reserved segment, files beneath it, and `/scratchpad`'s fall-through.
- **Canonical address bar (Req 10 + 13).** With a scratch workspace open the address bar shows `/<username>/scratch` (no longer the workspace's own unique-name path — today's rewrite in `src/components/HostedSignIn.tsx` ~120 changes); with a scratch file open it shows `/<username>/scratch/<segments…>`, percent-encoded per segment, `#fragment` preserved (scroll-to-heading stays Req 19, out of scope). A reload of either URL boots back into the same place.
- **`/scratch` shortcut (Req 11).** Visiting `/scratch` signed-in resolves-or-creates the caller's own scratch workspace (the idempotent `POST /api/me/scratchpad` semantics, PRD 019 Reqs 5–7) and lands on `/<username>/scratch`. An unauthenticated visit to `/scratch` — or to any `/<username>/scratch[/…]` URL — goes through hosted sign-in and continues to the requested target (the #220 deep-link intent machinery in `src/lib/hostedGate.ts`). `scratch` and `scratchpad` remain rejected as workspace names (already in `RESERVED_WORKSPACE_NAMES`; coverage stays green).
- **Visitor resolution is possible and leak-free (Req 13).** A signed-in caller other than the owner can open `/<username>/scratch[/<file>]` if the workspace's normal access model admits them (a member the owner added); scratch workspaces are never listed to non-owners (PRD 019 Req 8 stands), so resolution needs server support rather than the listing — and whatever the mechanism, an unknown username and an existing-but-inaccessible scratch behave identically for the caller (the Req 8 not-found / existing no-access semantics; no probe can distinguish them).
- **Tests.** New pure logic is unit-tested as above. Existing `/scratchpad` e2e coverage in `tests/e2e/hosted.spec.ts` is migrated to the new routes, and new `E<n>`-numbered coverage exercises at least: the `/scratch` redirect landing on `/<username>/scratch`, a file saved in scratch showing its `/<username>/scratch/…` URL and reopening from it, and `/scratchpad` rendering not-found — as far as the local-mode harness drives them.
- **Citations.** New behaviour carries `// PRD 020 Req <n>:` citation comments per `.sandcastle/CODING_STANDARDS.md`, and `docs/MAP.md` is regenerated (`npm run map`) if citations moved.
- **Test economy.** The implementer iterated with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code), and ran `npm run validate:quick` ONCE right before declaring the goal met — not after every small change and not as a full-suite baseline. `npm run validate:quick` passes in the implementer's session (`QUICK VALIDATION: ALL PASSED`).
- A summary comment from the implementer exists on issue #221.

## Context

Scope is PRD 020 Reqs 10–13 only (`prd/020-shareable-links.md`). Share affordances (Reqs 14–18) and heading landing (Req 19) are later issues — Req 13's "share affordances once those land" clause means only the URLs must exist here. Hosted-only: Tauri, dev-shim, and single-file builds are untouched.

Blockers #219 (unique names, reserved list) and #220 (path router, canonical bar, not-found page, sign-in intent) are merged on this branch — read `issue-specs/issue-219.md` and `issue-specs/issue-220.md` for what exists. Key wrinkle: `AuthUser` carries `id`, `username` (UPN), `displayName` but no guest email field; the derivation source for guests may need the auth provider to surface the email local part (see `server/providers/` — `DirectoryUser`/guest types carry `email`). Naming collision to avoid: `SessionMe.username` already means the UPN, so pick a distinct field for the URL segment. The scratch workspace keeps its own unique name (`scratchpad-2`-style from birth/migration) in the manifest; only its *canonical URL* becomes `/<username>/scratch` — the implementer decides whether the old unique-name path for a scratch workspace still resolves or canonicalizes away, but the bar must show the `/<username>/scratch` form.

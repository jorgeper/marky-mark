# Spec: Names section: unique-name collision gets the same red error treatment as #245 (#250)

## Goal

All acceptance criteria in issue-specs/issue-250.md are satisfied for issue #250, with evidence visible in the session: the Names section of workspace settings renders its unique-name refusals through the same shared `.form-error` rule the New Workspace dialog uses (body text size in `--mm-danger`, never the 11px muted `.hotkey-hint` or a hand-rolled copy), the `workspace-unique-name` input carries the error border and error-coloured typed value while the name is what was refused and clears as soon as the name is edited, a new hosted e2e test drives the real rename-collision path and asserts the computed size/colour and the clear-on-edit, `npm run validate:quick` passes in the implementer's session, and a summary comment from the implementer exists on issue #250.

## Acceptance criteria

- Both unique-name error lines in `src/components/WorkspaceNames.tsx` — the type-time problem (`workspace-unique-name-problem`, today `.hotkey-hint`) and the save-time refusal (`workspace-names-error`, today `.workspace-settings-error` at `--mm-text-small`) — render through the existing shared `.form-error` rule in `src/styles.css` (`font-size: var(--mm-text-body)`, `color: var(--mm-danger)`), the same rule `.picker-error` and the New Workspace dialog already share. No second rule is added that restates that font-size/colour pair, and `.dialog .hotkey-hint` keeps being the small muted hint it names.
- While the unique name is what was refused, the `workspace-unique-name` input carries the `.invalid` error border and the `.invalid-value` error-coloured text added by #245 (`src/styles.css` ~1205–1220; the settings panel is a `.dialog settings-modal`, so those `.dialog input.…` selectors already reach it). No new border/colour rule is written for this field.
- Whether a save failure is the name's fault is decided by the existing exported `isUniqueNameError` in `src/lib/workspaceLifecycle.ts` — reused, not re-implemented — so a permission/network refusal from the manifest PUT still shows its message with the field unpainted. A type-time problem (`uniqueNameProblem`) paints the field the same way.
- Editing the unique name retires the refusal immediately: the message disappears and the field's border and value return to normal without waiting for another Save, matching `WorkspaceSwitcher.tsx`'s onChange behaviour.
- Scope stays the Names section: `workspace-members-error` and `workspace-roles-error` (`WorkspaceMembers.tsx`, `WorkspaceRoles.tsx`) and the `.workspace-settings-error` rule itself are left alone, the display-name field is unchanged, and no theme file changes (the 18 `--mm-danger` contrast overrides from #245 already ship). Hosted (cloud) only — no desktop/Tauri or single-file behaviour change.
- A new E-numbered Playwright test in `tests/e2e/hosted.spec.ts` (next free number — E534 is the current maximum) drives the real path: two workspaces exist, workspace settings → Names renames one to the other's unique name, the server's 409 `The unique name "…" is already taken.` lands inline, and the test asserts the message's computed font-size and colour equal `--mm-text-body`/`--mm-danger` **resolved from the live page** (the probe-element technique E492 uses, not hard-coded px/hex), the input's border and text colour equal the danger colour, and that editing the name clears message and paint. A type-time problem (e.g. `has spaces`) is asserted to read identically.
- If Chromium logs the deliberate rename 409 as a console error, the exemption is added to the single `{message, url}` list in `tests/e2e/fixtures.ts`, scoped to that status on the manifest route — the shape the reviewer consolidated to in #245, not a second mechanism.
- Unit coverage lands as new U-numbered tests (U1233 is the current maximum): the CSS pin in `tests/unit/danger-token.test.ts` covers the Names section's use of the shared rule, and any pure decision logic added is unit-tested. The WCAG contrast helper stays imported from `tests/unit/css-contrast.ts` — it is not copied.
- Changed and added code carries `// SPEC<n> §x.y:` / PRD-and-issue citation comments per `.sandcastle/CODING_STANDARDS.md`, in the style the surrounding PRD 020 Req 2/Req 4 comments already use; `docs/MAP.md` is regenerated with `npm run map` if citations changed (the gate diffs it).
- The style lint stays green: no raw colour literal, no app-specific class declaring colour or font-size (`docs/STYLE-GUIDE.md` Do/Don't).
- The implementer iterated with `npm run typecheck` and `npm run test:unit` (or `npx playwright test -g '<title>'` for the one new e2e test), and ran the full gate `npm run validate:quick` ONCE, right before declaring the goal met — not after every change and not as a start-of-attempt baseline — and it printed `QUICK VALIDATION: ALL PASSED`.
- A summary comment from the implementer exists on issue #250 recording what changed, the decisions taken, and the gate evidence.

# Spec: Invitations: copy-invite-link actions — per pending guest, and beside Send in the invite form (#195)

## Goal

All acceptance criteria in issue-specs/issue-195.md are satisfied for issue #195, with evidence visible in the session: the invitation surface on `POST /api/admin/invitations` supports creating (or re-creating) an invitation without sending Microsoft's email and returns the Graph `inviteRedeemUrl` (never logged) behind `deployment.admin` with the non-pending 409 refusal, Management → People offers **Copy invite link** on every Pending row and the invite form offers **Get invite link** beside Send (with Send also surfacing the link it created), both with inline "Copied" feedback and a visible manual-copy fallback, the flows (row copy, form get-link, non-admin 403, non-pending refusal) are e2e-tested offline against a mock directory that returns a deterministic fake redeem URL, and `npm run validate:quick` passes in the implementer's session.

## Acceptance criteria

- The server's invitation surface is extended so an admin can obtain a redeem URL: either `sendEmail?: boolean` on the existing `POST /api/admin/invitations` body (default `true`) with the success response gaining `redeemUrl`, or a dedicated link route — implementer's call, but either way it sits behind the same `deployment.admin` guard as the existing invite route in `server/admin.ts`, rides the same OBO exchange (`server/providers/azure/obo.ts`) and existing delegated `User.Invite.All` permission (no new consent, no hosting-guide permission changes), and maps Graph refusals through the existing 502-with-`error.code` pathway.
- When the email is suppressed, the Graph call (`server/providers/azure/graph.ts`) sends `sendInvitationMessage: false`; a normal Send still sends the email but the response now also carries the `inviteRedeemUrl` Graph returns at creation. The redeem URL never appears in a server log line.
- The per-row action re-POSTs the invitation for the guest's email with the email suppressed (Graph cannot read a redeem URL back for an existing guest; a re-POST returns a fresh valid URL without disturbing the pending user). It refuses for a non-pending target via the 409 eligibility pathway issue #193 introduced (accepted guests, members, and admins never get a link from a row).
- Management → People (`src/components/ManagementPanel.tsx`): every row with the Pending badge offers a **Copy invite link** action that puts the redeem URL on the clipboard, shows brief inline "Copied" feedback, and — when the clipboard API is unavailable or fails — shows the URL itself in a visible element for manual copy. Non-pending rows never offer it. The client call lives beside the invite/rescind calls in `src/platform/hostedAdmin.ts`.
- The invite form in the same panel gains a **Get invite link** action beside Send: it creates (or refreshes) the invitation for the typed email without sending Microsoft's email and shows the redeem URL to copy, with the same feedback/fallback behaviour. A successful normal **Send** additionally shows the link of the invitation it just created. The workspace People picker's invite row is untouched.
- The mock directory (`server/providers/mock/directory.ts`) returns a deterministic fake redeem URL on invitation creation, and re-inviting an address that is a *pending* invited guest succeeds with a URL again (mirroring real Graph for pending guests) while inviting a seeded/accepted address keeps today's `invitedUserAlreadyExists` refusal lane. Desktop-shim e2e tests (numbered `E<n>`, in the relevant `tests/e2e/` suite) cover offline: copy from a Pending row, get-link from the form (email suppressed), a non-admin gets 403, and a non-pending target is refused.
- Request/response parsing changes go through the shared parser in `src/lib/invitations.ts` with `vitest` coverage in the existing unit lanes, and new behaviour carries `// SPEC<n> §x.y:`-style citations consistent with `.sandcastle/CODING_STANDARDS.md`.
- Docs: `docs/AUTHENTICATION.md` § "Adding people" notes the copy-link path as the reliable alternative when Microsoft's invitation email doesn't arrive; the route table in `server/README.md` documents the route change (body/response fields or the new route).
- If the collected desktop-shim e2e count grew, `E2E_TEST_FLOOR` in `scripts/validate.mjs` is re-pinned to the new count.
- Iteration used `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code, e.g. `npx playwright test -g '<title>'`) after each change; the full gate `npm run validate:quick` was run **once**, right before declaring the goal met — not after every small change and not as a starting baseline — and passed, printing `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- A summary comment from the implementer exists on issue #195.

## Context

Born from live testing: Graph answered `sent: true` but Microsoft's invitation emails to Gmail never arrived; the redeem URL works without any email, so the UI surfaces it. The invite flow to extend is issue #190's `POST /api/admin/invitations` (`server/admin.ts` ~line 104: guard, shared parser, Graph-as-caller via OBO, 502 mapping); the 409 non-pending eligibility gate and Pending-row action pattern come from issue #193's rescind flow in the same file and `ManagementPanel.tsx` (grep `#193` and `Req 33`). Graph only returns `inviteRedeemUrl` at creation — the mock's current duplicate-address refusal (`server/providers/mock/directory.ts` `invite()`) must learn to distinguish pending invited guests (re-POST succeeds with a URL) from seeded/accepted users (refusal stays, it drives the 502 lane offline). Clipboard-with-fallback patterns already exist in the app (e.g. `src/lib/codeCopy.ts`) — match them. Test hooks under `/api/directory/invitations/` in `server/app.ts` are local-mock-only; the new behaviour is a real route change that must also work on Azure.

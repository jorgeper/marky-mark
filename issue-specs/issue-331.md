# Spec: Centered max-width page: side panes hug it, page shadow replaces the seam, flat tab strip (#331)

## Goal

All acceptance criteria in issue-specs/issue-331.md are satisfied for issue #331, with evidence visible in the session: the page (`.workspace-stack`: tab strip + editor + preview) is a horizontally centered, max-width `--mm-bg` surface on a `--mm-bg-elevated` ground, its inner width `max(var(--mm-content-width), var(--mm-pane-min))` editor-only and `2 ×` that plus the divider with the preview open, tracking the Margins setting live, shrinking first with no new breakpoints and no transitions (PRD 025 Reqs 1–5, 9); the sidebar and the 300 px comments column hug the page with the surplus split equally as ground outside the cluster, one pane open following the same rule (Reqs 2, 8, 10–11); with any pane open the page has `--mm-radius-small` top corners and casts `--mm-panel-shadow` with the `.workspace-stack::after` seam overlay gone, and with both panes closed or absent it spans the full width with no radius or shadow (Reqs 6–7); the tab strip is flat on the ground, the active tab joined to the page and inactive tabs `--mm-border`-outlined pills, the `--mm-lift-tab*` tokens removed (Reqs 17–18, 21, 28); PRD 013 Reqs 10–12, SPEC36 §4.1 and PRD 023 §14–15 carry amendment notes, E353/E306 are rewritten and new tests cover centering, Margins tracking and the full-width form (Req 30); `npm run validate:quick` has been run once at the end and prints `QUICK VALIDATION: ALL PASSED`; and a summary comment from the implementer exists on issue #331.

## Acceptance criteria

- **The page is one surface on a ground (PRD 025 Req 1).** `.workspace-stack` in `src/styles.css` is the page: it paints `background: var(--mm-bg)` and contains the file tab strip (when shown), the `.workspace` (editor / preview / split), and nothing else. `.body-row` paints `background: var(--mm-bg-elevated)` (the ground). The folder panel (`.folder-panel`) and the comments pane (`.comments-pane`) keep their existing `--mm-bg-elevated` background, so from computed styles the body row, the folder panel and the comments pane report the same `backgroundColor` and the page reports the theme root's `--mm-bg`. The `.workspace` element itself stays transparent over the page (E353's "the theme root's `--mm-bg` — `.workspace` itself is transparent over it" observation still holds, now against `.workspace-stack`).
- **Centered cluster, surplus outside (PRD 025 Reqs 2, 8).** With the folder sidebar and the comments column both open and a viewport wider than the cluster (e.g. 1800 px wide in Playwright with the default 260 px `--mm-folders` and the 300 px comments column), the folder wrapper's left edge minus the body row's left edge equals the body row's right edge minus the comments wrapper's right edge, within 1 px, and both are > 0. The folder wrapper's right edge equals the page's left edge and the page's right edge equals the comments wrapper's left edge (no ground between a pane and the page). With exactly one pane open the same holds with that pane and the page as the two-member cluster: ground of equal width on both sides of the pair, the pane touching the page, no special-case rule in CSS (one `.body-row` centering rule serves all three states).
- **Editor-only max width tracks Margins (PRD 025 Req 3).** In edit mode with the split preview closed and the window wide enough, the page's inner width (its `clientWidth` less its own horizontal padding, if any) equals `max(var(--mm-content-width), var(--mm-pane-min))` resolved to px. `--mm-content-width` is written inline on the theme root by `src/App.tsx` (grep `MARGIN_WIDTHS`; `default` removes the property so the CSS fallback `46rem` applies — the page rule must use the same `var(--mm-content-width, 46rem)` fallback the text column uses in `editor/styles.css` and `src/styles.css`, so the page and its column agree). Changing Settings ▸ Margins (`settings-margins`) between `wide` (38rem) and `super-narrow` (76rem) changes the page's measured width in the same frame the setting applies, with the pane-min floor (`--mm-pane-min`, 768 px default) winning when the content width is smaller. The Margins values, the text column's max width and `paneMinWidth`'s meaning are unchanged.
- **Preview-open max width (PRD 025 Req 4).** With the split preview open (`splitEdit` on, edit mode), the page's inner width equals `2 × max(var(--mm-content-width), var(--mm-pane-min))` plus the divider's layout width (the `.split-divider` box in `editor/styles.css` is 16 px with `margin: 0 -4px`, so 8 px of flow width today — measure it, do not hardcode). Each half still floors at `--mm-pane-min` and dragging `split-divider` moves only the split point (`--mm-split`), never the page's width. The existing split tests (`tests/e2e/split-view.spec.ts`: E39, E40, E134, E438, E441, E577 and siblings) pass unmodified.
- **Shrinking without breakpoints (PRD 025 Req 5).** When the viewport is narrower than the cluster at the page's max width, the sidebar keeps `--mm-folders` and the comments column keeps 300 px, and the page takes the remainder. The page's flex sizing lets it shrink freely (`min-width: 0` on `.workspace-stack` stays); the existing pane-min behaviour is untouched — the content inside the page floors at `--mm-pane-min` (or `2 × --mm-pane-min` + divider with the preview open) and `.workspace` scrolls horizontally past that exactly as today. No media query, container query or JS resize logic is added for this.
- **Radius and shadow when a pane is open; flat and edge-to-edge when none (PRD 025 Reqs 6–7).** With at least one side pane mounted, `.workspace-stack` has `border-top-left-radius` and `border-top-right-radius` of `var(--mm-radius-small)` and `box-shadow: var(--mm-panel-shadow)`. With both panes unmounted (`sidebarMounted` false and `commentsPaneMounted` false in `src/App.tsx` — or absent, as in the static web build), the page's bounding box spans the body row's full width, `border-radius` is `0` on every corner and `box-shadow` is `none`; the `.doc` / `.cm-content` text column stays centered at `--mm-content-width` inside it as today. The state is expressed as a class on `.body-row` or `.workspace-stack` (name at the implementer's discretion, e.g. `panes-none`) driven by those two predicates — not by `:has()` on siblings alone — so tests can key on it. The `.workspace-stack::after` rule, the `.workspace-stack.with-tabs::after` rule and the `.theme-root.toolbar-static .workspace-stack.with-tabs::after` rule are deleted (no `::after` on the stack remains); the `--mm-panel-shadow` token definition stays. The shadow must not be clipped by `.body-row` or `.workspace-stack` (neither gains `overflow: hidden`).
- **Instant, transition-free (PRD 025 Req 9).** `getComputedStyle` on `.workspace-stack`, `.body-row`, `.folder-slide`, `.comments-slide`, `.split-editor` and `.split-preview` reports `transition-duration: 0s`, `transform: none` and `will-change: auto` in every state; toggling a pane or the preview changes the page's bounding width within two `requestAnimationFrame`s, and a viewport resize (`page.setViewportSize`) re-centers it without a settle wait. No new `transition` is added anywhere in this issue.
- **Sidebar hugs the page (PRD 025 Req 10).** `.folder-slide` (all three views: folders, outline, search) is the cluster's left member: its right edge equals the page's left edge, its width is still `var(--mm-folders)` and `paneWidthDrag` (`src/components/FolderPanel.tsx`) still resizes it 160–480 px with the page absorbing the difference. The folder header row therefore renders immediately left of the page, not at the window's left edge, whenever the cluster is narrower than the window. The print rules listing `.folder-slide` / `.folder-panel` are unchanged.
- **Comments column hugs the page and always reserves its width (PRD 025 Req 11).** `.comments-slide` is the cluster's right member: its left edge equals the page's right edge, it stays 300 px, and it is mounted whenever `commentsPaneOpen(...)` is true (`src/lib/commentsPane.ts`, unchanged) regardless of how many comments the document has — a document with zero comments and `showComments` on shows the column and the page does not move when the first comment is added. Cards keep their line anchoring (`tests/e2e/comments.spec.ts` passes unmodified except for any plane-wording comment near line 1745, which is reworded).
- **Flat tab strip joined to the page (PRD 025 Reqs 17–18).** `.file-tab-strip` keeps `background: var(--mm-bg-elevated)` and sits inside `.workspace-stack` above the workspace, so it is left-aligned to the page's left edge and exactly the page's width in every state (both panes closed included, where it simply spans the full width — mockups 4 and 5). Because the strip is a `--mm-bg-elevated` band at the top of a `--mm-bg` page, the page's radius and shadow apply to the strip's top corners when the strip is shown and to the workspace's top corners when it is hidden; the implementer chooses the structure that keeps the strip clipped to the page's rounded corners without clipping the shadow (e.g. `border-radius` on the stack with `overflow: clip` only on the strip band, or matching radii on the strip). `.file-tab.active` paints `background: var(--mm-bg)`, `box-shadow: none`, and has no bottom edge between it and the workspace (no border, no hairline: an active tab's bottom pixel row and the workspace's top pixel row are the same colour). `.file-tab:not(.active)` paints `background: var(--mm-bg-elevated)`, `border: 1px solid var(--mm-border)` with `border-bottom: none` (or a transparent bottom) so it reads as a pill on the ground, `box-shadow: none`, and keeps its rounded top corners, `--mm-fg-muted` colour, hover colour and ellipsis. Hover on an inactive tab may tint through `var(--mm-hover)`; the active tab does not flicker on hover. `z-index` on tabs is `auto` (no plane stacking). `--mm-lift-tab` and `--mm-lift-tab-active` are deleted from the token block (`src/styles.css` ~line 161) along with every `var()` reader and the comment describing them; the style lint (every `var(--mm-…)` names a defined property; no literal colours in chrome rules; shadows/radii through scale tokens) stays green. The strip's height (`--mm-tabstrip-h`, 38 px), its `.file-tab-rail` overflow scrolling, end arrows, end slots, tab order, per-tab ellipsis, slot / dirty / close behaviour and the tab menu are unchanged (the existing `tests/e2e/file-tabs.spec.ts` tests other than E353/E306 pass unmodified); the rail's negative-margin headroom comments that justify themselves by the lift shadow are reworded, and the headroom itself may stay to keep the strip's height.
- **Reopen chevrons stay reachable (PRD 025 Req 21).** With the strip shown, `folder-expand` and `comments-expand` keep riding the strip's lead / trail slots; with the strip hidden, `.edge-cluster-left` / `.edge-cluster` keep overlaying the page's top corners (they anchor to `.workspace-stack`, which stays `position: relative`). In the both-panes-closed state the two chevrons sit at the window's edges (the page's edges), exactly as today; E-tests that click them (`shell-and-menus.spec.ts` E133, `comments.spec.ts` E435, `folder-tree.spec.ts` near line 256) pass unmodified.
- **Static-toolbar mode and print unchanged.** In `toolbar-static` mode (the shim's static mode and the web build) the strip's `margin-top: 42px` / workspace `padding-top` clearance still applies so the page's top edge, radius and shadow begin below the toolbar and the folder / comments panes keep their `padding-top: 42px`. The `@media print` block gains nothing but, if needed, rules that neutralise the ground, radius and shadow on paper; `tests/e2e/reading-and-export.spec.ts` passes unmodified. The corner stack (`.corner-stack`) stays window-fixed.
- **Tokens only; every theme renders it (PRD 025 Req 28).** No new colour literal outside a token definition; every colour, radius and shadow in the changed rules is `--mm-bg`, `--mm-bg-elevated`, `--mm-border`, `--mm-hover`, `--mm-radius-small` or `--mm-panel-shadow`. All 27 files in `themes/` already define `--mm-bg-elevated`, so no theme file changes; the rewritten E306 proves the ground / page contrast under One Dark.
- **Spec amendments and citations.** `prd/013-tabs-on-top.md` Reqs 10–12 carry a `> **Amended (issue #331, 2026-09-07):** …` note in the repo's existing style stating that the three-plane strip and the L-shaped seam are retired: the strip is a flat band on the page, the active tab joined to the page and inactive tabs flat outlined pills, depth coming from the page's own radius and shadow (PRD 025 Reqs 6, 17–18). `docs/specs/SPEC36.md` §4.1 gains an amendment note (alongside #329's) stating that the panel/workspace seam overlay is gone and the page's shadow replaces it (PRD 025 Req 6). `prd/023-comments-highlights-split.md` §14–15 carry an amendment note stating the column is the cluster's right member hugging the page, always reserving its 300 px while `showComments` is on, with no seam shadow of its own (PRD 025 Req 11). Changed CSS and TSX carry `/* PRD 025 Req n (issue #331): … */` citations per `.sandcastle/CODING_STANDARDS.md`; comments in `src/styles.css`, `src/App.tsx` and `src/components/FileTabStrip.tsx` that describe the seam, the L-shaped backdrop, the three planes or "sibling #331" are rewritten (the `.folder-header` preamble's "still painted ONCE by `.workspace-stack::after`" sentence included).

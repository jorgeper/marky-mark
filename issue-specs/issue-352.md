# Spec: PRD 026: New Workspace dialog — display name leads, URL name auto-fills and normalises, guidance and address preview (#352)

## Goal

All acceptance criteria in issue-specs/issue-352.md are satisfied for issue #352, with evidence visible in the session: the New Workspace dialog (`src/components/WorkspaceSwitcher.tsx`) leads with a required, autofocused **Display name** field (test id `new-workspace-name`) followed by **URL name** (`new-workspace-unique-name`), and `validateNewWorkspaceForm` in `src/lib/workspaceLifecycle.ts` refuses an empty trimmed display name with `A display name is required.` and an empty URL name with `A URL name is required.`, sending the trimmed display name as the manifest `name` with no fallback; while the URL-name field is untouched every display-name change re-derives it through `slugifyWorkspaceName`, the first edit in the URL field stops mirroring and clearing it to empty resumes it; URL-field input is normalised as typed (`Foo Bar`→`foo-bar`, `foo--bar`→`foo-bar`, one trailing dash kept while typing and stripped on blur and submit); beneath the URL field a muted-caption sentence `Lowercase letters, numbers and dashes. This is the workspace's address.` and a live preview `<origin>` + `buildAppPath(<url-name>)` (or `<origin>/…` when empty) are always visible via a reusable component; the #245 error paint is unchanged; unit tests (U1323+) and hosted e2e tests (E596+) cover the new behaviour with E182/E203/E492 updated to the new field order; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #352.

## Acceptance criteria

- **Display name leads (PRD 026 Req 4).** In `NewWorkspaceDialog` the first `.field` is labelled **Display name** (no "(optional)"), its input keeps `id`/`data-testid` `new-workspace-name` and carries `autoFocus`; the second `.field` is labelled **URL name** and its input keeps `id`/`data-testid` `new-workspace-unique-name` (no `autoFocus`). The People, role rows, everyone-access checkbox, its role select, the submit error line (`new-workspace-error`) and the Cancel/Create actions follow unchanged. `NewWorkspaceForm`'s shape (`uniqueName`, `name`, `members`, `everyoneEnabled`, `everyoneRole`) and `emptyNewWorkspaceForm()` are unchanged so App.tsx and the platform layer need no edit.
- **Pure validation (Req 4 + Req 6 empty cases).** `validateNewWorkspaceForm(form)` checks in this order and stops at the first failure: (1) `form.name.trim() === ''` → `{ ok: false, error: 'A display name is required.' }`; (2) the URL name with one trailing dash removed (`foo-`→`foo`) is `''` → `{ ok: false, error: 'A URL name is required.' }`; (3) `uniqueNameProblem(settled)` non-null → its message (reserved-word and strict-charset refusals exactly as #350 left them). On success `request.uniqueName` is the settled (dash-stripped) value and `request.name` is the trimmed display name — the old "blank display name means the unique name" fallback is gone from the form (the server's `buildNewWorkspaceManifest` fallback for API callers is untouched). Members and everyone-access are shaped exactly as today.
- **Auto-fill until touched (Req 5).** The dialog holds a `touched` flag for the URL-name field, false at open. While untouched, every display-name `onChange` sets `uniqueName` to `slugifyWorkspaceName(displayName)` (`Team Docs`→`team-docs`, `日本語`→`''`; the dialog adds no fallback word). Any input event in the URL-name field whose normalised value is non-empty sets `touched = true`, and from then on display-name changes leave the URL name alone. An input event in the URL-name field whose normalised value is `''` sets `touched = false` and immediately sets `uniqueName` to `slugifyWorkspaceName(currentDisplayName)` — mirroring resumes from the current display name at once, not only on the next display-name keystroke. (Req 12's "Use <suggestion>" action is issue #354 and is not built here, but the `touched` flag must be a plain state value it can set.)
- **Normalise as you type (Req 6).** `src/lib/workspaceLifecycle.ts` exports a pure, unit-tested typing normaliser (name the implementer's choice) applied to every URL-name `onChange` value before it reaches state: it is `slugifyWorkspaceName(raw)` plus one trailing dash when `raw` ends in a character outside `[a-z0-9]` (case-insensitive), the slug is non-empty, and the slug is shorter than `UNIQUE_NAME_MAX_LENGTH`. Observable examples: `Foo Bar`→`foo-bar`, `foo--bar`→`foo-bar`, `foo-`→`foo-`, `foo `→`foo-`, `foo--`→`foo-`, `foo!`→`foo-`, `-foo`→`foo`, `-`→`''`, `!!!`→`''`, `Team_Docs`→`team-docs`. The field's `onBlur` replaces the value with the settled form (trailing dash stripped) and submit validates the settled form (previous criterion). Consequently the type-time problem line (`new-workspace-unique-name-error`, still `uniqueNameProblem` on a non-empty value) can only ever show the reserved-word refusal in practice; it stays wired exactly as today.
- **Guidance and preview (Req 7).** A new reusable component in `src/components/` (e.g. `UrlNameGuidance.tsx`; props: the current URL name and the test ids or a test-id prefix, so issue #353's settings Names section can mount the same thing) renders, directly beneath the URL-name field and its problem line, two always-visible lines in the muted caption treatment (`var(--mm-text-caption)` size, `var(--mm-fg-muted)` colour — the `.dialog .hotkey-hint` tokens; a new class in `src/styles.css` is fine, `.form-error` is not): the exact sentence `Lowercase letters, numbers and dashes. This is the workspace's address.` (`data-testid="new-workspace-url-guidance"`) and a preview (`data-testid="new-workspace-url-preview"`) whose text is `${origin}${buildAppPath(settled)}` from `src/lib/hostedPaths.ts` when the settled URL name is non-empty and `${origin}/…` (U+2026 ellipsis) when it is empty, where `origin` is `window.location.origin` supplied by the caller. The string builder is a pure exported function in `src/lib/workspaceLifecycle.ts` (or `hostedPaths.ts`) so it is unit-testable: `('https://docs.example', 'team-docs')`→`https://docs.example/team-docs`, `('https://docs.example', '')`→`https://docs.example/…`. The preview updates on every keystroke in either field.
- **Error paint unchanged (Req 8).** The URL-name field wears `field invalid invalid-value` exactly while `typedProblem !== null` or the submit error satisfies `isUniqueNameError`; `isUniqueNameError` is extended so `A URL name is required.` (and the reserved/charset/409 messages as today) return true and `A display name is required.` returns false. The display-name input wears the same `invalid invalid-value` classes exactly while the submit error is `A display name is required.`. Any edit in the display-name field or the URL-name field calls `setError('')` first, so editing either field retires its own refusal (message and paint) without a second submit. The error line keeps `.form-error` and `role="alert"`.
- **Citations and comments.** Every changed behaviour carries a `PRD 026 Req <n>` citation per `.sandcastle/CODING_STANDARDS.md`; the `PRD 020 Req 2` comments in `WorkspaceSwitcher.tsx` and `workspaceLifecycle.ts` that say the unique name comes first or that a blank display name falls back are rewritten to the amended contract. No `console.*` in `src/`; `src/lib/` stays free of React/DOM imports (the origin is passed in). No test id is renamed. `docs/MAP.md` is regenerated with `npm run map` only if the gate's map check reports drift.
- **Unit coverage (Req 13, form part).** In `tests/unit/workspace-lifecycle.test.ts`, existing tests are updated in place under their ids, not weakened: U284 now shows a form with a valid display name and empty URL name earns `A URL name is required.`, and the charset refusals still surface with a display name present; U285 is unchanged in substance; U1043 is rewritten to show a blank display name is refused with `A display name is required.` even with a valid URL name, and keeps the reserved-word refusal; U1186 adds `A URL name is required.` → true and `A display name is required.` → false. New tests titled `U1323:` upward (never reuse a number) cover: the validation order (empty display name wins over an empty URL name); `foo-` submitting as `foo`; the typing-normaliser example table above including the trailing-dash and length-clamp cases; the preview builder for a non-empty and an empty name. `tests/unit/workspace-names.test.ts` needs no change.
- **End-to-end coverage (Req 14, dialog part).** In `tests/e2e/hosted.spec.ts`: E182 and E203 fill `new-workspace-name` first and `new-workspace-unique-name` second and still create and open the workspace; E492 fills a display name before submitting the taken name (otherwise Req 4 refuses the submit before the 409), and its type-time refusal uses a reserved word such as `scratchpad` instead of `has spaces` (which now normalises to `has-spaces`); their assertions are otherwise unchanged. New tests titled `E596:` upward cover at least: typing a display name (`pressSequentially`) fills the URL name live and the preview reads `${origin}/<slug>` (with the empty-name preview `${origin}/…` checked before typing); editing the URL name stops mirroring on the next display-name change, and clearing it resumes mirroring from the current display name; typing `Foo Bar` keystroke by keystroke into the URL name shows `foo-` after the space and `foo-bar` at the end, and `foo--bar` shows `foo-bar`; submitting with an empty display name shows `A display name is required.` with the display-name field in the #245 paint (reuse `fieldPaint`/`errorTokens`), and typing in it clears both; the guidance sentence is visible with the caption size and muted colour. Every created name is timestamped per worker as the existing tests do.
- **Verification economy.** The implementer iterates with `npm run typecheck` and `npm run test:unit` (or `npx vitest run tests/unit/workspace-lifecycle.test.ts`) after each change, uses `npx playwright test -g 'E182|E203|E492|E596'`-style targeted runs while debugging the dialog, and does not run the full gate as a baseline at the start of an attempt.
- **Gate.** `npm run validate:quick` has been run once in the implementer's session, right before declaring the goal met, and prints `QUICK VALIDATION: ALL PASSED` (the quick tier's e2e step runs `tests/e2e/hosted.spec.ts` through the local hosted server, so the new E tests are part of it).
- **Summary comment.** A summary comment from the implementer exists on issue #352 describing what changed, the tests added/updated, and the gate result.

# Spec: Editor: smart link rendering (Show Raw/Rendered Links), Link submenu in the Smart Edit menu, and open-link via modifier-click / hotkey / menu (#270)

## Goal

All acceptance criteria in issue-specs/issue-270.md are satisfied for issue #270, with evidence visible in the session: the Smart Edit menu carries a **Link ▸** submenu (after Diagram) whose rows are Show Raw Links / Show Rendered Links, Create Link (the moved ⌘⇧K item, gone from the top-level inline group) and Open Link showing its hotkey; the rendered view collapses `[text](url)` to styled link text in the edit pane, is persisted in a user-scoped `linkView` setting like its four sibling views, and reveals raw when the cursor/selection enters the link; a link opens through ONE command reached three ways — modifier-click, the new rebindable `openLink` hotkey, and the menu row — routed through the editor's existing open seam under the preview's managed-link rule (http(s) hands off externally, `#anchor` jumps, anything else inert); unit (U1153+) and e2e (E476+) coverage lands, existing menu-order tests are updated, `docs/MAP.md` is regenerated and the contract is recorded in a SPEC section; and `npm run validate:quick` passes.

## Acceptance criteria

### The Link submenu (SPEC43 §4 menu model)

- `buildSmartMenu` (`editor/src/lib/smartEdit.ts:463`) emits a **`Link`** submenu in the smart-construct group, placed **after `Diagram`** and before the annotation entries (`Table`, `Image`, `Code Block`, `Diagram`, `Link`, [`Comment`, `Highlight`], separator, `Bold` …). Its id is a new one that collides with nothing existing — `link-view`, following the `code-block-view` precedent that kept clear of the taken `code-block` id — so its row is `smart-edit-link-view`.
- Its rows, in order:
  1. **`toggle-links`** — labelled `Show Raw Links` when the rendered view is on and `Show Rendered Links` when it is off, exactly mirroring the `toggle-grid` / `toggle-images` / `toggle-code-blocks` / `toggle-diagrams` label rule. Always enabled.
  2. **`link`** — `Create Link`, carrying `hk(h.link)` (⌘⇧K / Ctrl+Shift+K). **The id stays `link`**, so `runFormat`'s `wrapLink` branch (`editor/src/components/Editor.tsx:1190`), the `SmartFormatOp` union, the `fmtLink` command and the `hk.link` binding are untouched — only the row's location in the menu tree changes. Enabled exactly as today (always).
  3. **`open-link`** — `Open Link`, rendering its hotkey through `displayCombo` so the menu documents the binding. **Enabled only when the caret/selection head sits inside a link that has a URL**; disabled (not absent) otherwise.
- The top-level inline-formatting group loses its `link` row: after the separator the group reads `Bold`, `Italic`, `Strikethrough`, `Inline Code`, then the `Heading` submenu — no `Link` between `Inline Code` and `Heading`.
- "Caret is inside a link" is resolved by **pure logic**, not by the view: `detectContext` (`editor/src/lib/smartEdit.ts:324`) gains a `link` flag alongside `table` / `image` (or a sibling exported helper returns the link at an offset), and `Editor.tsx`'s menu-open site passes it into `SmartMenuCtx` beside `gridView`/`imageView`/`codeView`/`diagramView`. An image reference (`![alt](src)`) is **not** a link and never enables Open Link.
- The preview selection button's annotation-only menu (PRD 023 §13, issue #287) is unaffected: it still carries exactly `Comment ▸` and `Highlight ▸`, and the absence assertion in `tests/e2e/comments.spec.ts:2297` is extended to cover the new `link-view` id.

### The rendered-links view

- A new user-facing setting **`linkView: boolean`** lands in `src/lib/settings.ts` beside its four view kin: declared with a citation comment, **defaulting to `true`** (rendered — the same "ships rendered" choice `tableGridView` / `inlineImages` / `codeBlockView` / `diagramView` all make), scoped **`'U'`** in the scope map (a reader's preference, like `codeBlockView` / `diagramView`), and validated with `bool` so a hand-edited non-boolean falls back to the default.
- `App.tsx` gains a `toggleLinkView` callback in the shape of `toggleCodeBlockView` / `toggleDiagramView` (`src/App.tsx:892–903`), passed to the Editor as the seam the `toggle-links` row invokes; `Editor.tsx`'s `invokeMenuItem` routes `toggle-links` to it and refocuses the view, exactly as the other three toggles do (`editor/src/components/Editor.tsx:1285–1306`).
- `SettingsPanel.tsx` gains the matching checkbox under its own `Links` section beside the Tables/Images/Code/Diagrams rows (`settings-link-view` testid, `id`/`htmlFor` pair, `scopeNote('linkView')`), so the view is reachable from Settings as well as the menu — the invariant every sibling view holds.
- With the view **on**, an inline link renders as **just its link text**, styled as a link (the `--mm-link` token the editor already resolves, `editor/styles.css:473`), with the `[`, `](`, the URL, any title and the `)` hidden by `Decoration.replace`. Nothing here ever changes document text, history, the dirty state or the canonical text — decoration only, like the SPEC41 image view and the issue #157 card view.
- **Reveal on cursor**: when the caret or any part of the selection is inside the link node, the whole construct shows raw and stays editable in place — the same `revealed` rule `codeBlockSpans.ts` / `livePreview.ts` use (`overlapsRevealed`). Moving the caret out re-collapses it.
- With the view **off**, the edit pane shows links exactly as it does today (markdown highlighting only, `mm-md-link`) — no decoration at all.
- Scope of what collapses: inline links with a URL (Lezer `Link` nodes carrying a `URL` child). Reference-style links (`[text][ref]`), bare/autolinked URLs, image references and anything inside a fenced code block stay raw — there is no URL on the node to render or open. State this boundary in the citation.
- **No double-decoration**: the experimental whole-document live preview (PRD 006 §5) already collapses the same ranges. With `livePreview` on, exactly one of the two paints the link (the standalone view stands down, or the two are proven to hide identical ranges) — text never shifts, and no range is hidden twice. Likewise the view paints nothing inside the table-mode display region, the guard `codeBlockView` already applies via `tableModeField`.
- The decoration core is **pure and unit-testable**, in the established two-file shape: a spans module under `editor/src/lib/` (e.g. `linkSpans.ts`, returning hide-spans + the link-text span + its URL for a given state/visible range, with a `revealed` flag) and a thin view wiring module under `editor/src/components/` (e.g. `linkView.ts`) that Editor.tsx includes in a compartment while the setting is on. Reuse the live preview's `Link` decoration rule (`editor/src/lib/livePreview.ts:243–258`) rather than writing a second, divergent one.

### Opening a link — one command, three entry points

- **One resolution path.** A single pure helper (in `editor/src/lib/`, next to the spans core) maps a document offset to the link under it and yields its raw href; the menu row, the hotkey and the modifier-click all call it. There is no second, view-only parse.
- **Modifier-click.** ⌘-click (macOS) / Ctrl-click on a link's text opens it, in **both** raw and rendered views — so the resolution goes through the document offset under the pointer (`posAtCoords`), not through a DOM attribute that only exists when the view is on. A plain click still just places the caret (and still toggles a live-preview task checkbox where that handler owns the event). The existing `livePreviewMousedown` factory (`editor/src/components/livePreview.ts:174`) is the model — extend/share it rather than copying it, and keep the factory shape so the callback and URL are assertable in a unit test without a browser.
- Holding the modifier over a link shows a **pointer cursor**, and the link text carries the URL as a `title` tooltip. The cursor rule resolves through a class toggled on modifier keydown/keyup and released on blur/window-blur (it must not stick after the modifier is let go or focus leaves), and its CSS lives in `editor/styles.css` with the other editor chrome.
- **Hotkey.** A new rebindable `openLink` entry lands in `HotkeyMap` and `DEFAULT_HOTKEYS` (`editor/src/lib/hotkeys.ts`), in the `Mod+Alt+<letter>` family its `codeBlock` / `insertComment` / `applyHighlight` neighbours use: **`Mod+Alt+O`** (O for Open; `Mod+Shift+O` is taken by `toggleOpenOnly`). It must be conflict-free under `combosConflict` across the whole default map — the existing conflict test (`editor/tests/smart-edit.test.ts:459`) is the check; if `Mod+Alt+O` turns out to collide with anything shipped, pick another free combo in the same family and say so in the citation.
- The binding is dispatched the way every Smart Edit binding is: a new `openLink` `CommandId` in `src/lib/commands.ts`, an entry in App's `fmt` table (`src/App.tsx:5981–5999`) and a handler that reaches the editor through its handle/seam. With the caret inside a link it opens it; outside a link it is a no-op (never an error, never a text change).
- It is listed and rebindable in **Settings ▸ Hotkeys** under the Smart Edit group: added to `SMART_EDIT_KEYS` and to the action-label map (`src/components/SettingsPanel.tsx:161`, `:142`) with a label in the neighbours' voice (e.g. `Open link`), and restored by `Reset hotkeys` like every other row.
- **Menu.** `Link ▸ Open Link` invokes the same command; invoking it closes the menu and returns focus to the editor, like the other rows.
- **Routing and the managed-link rule.** The href leaves the editor package through its existing host seam (`onOpenExternal`, `editor/src/components/Editor.tsx:320`) — the editor never learns about workspaces, files or the preview. The host applies **exactly** the preview pane's managed-link rule (SPEC11 §4, `src/App.tsx:7942–7952`): `http(s)` hands off to `platform.openExternal`; a `#anchor` jumps to that heading as a preview click does; **any other href is inert**. To guarantee the two surfaces can never drift, that rule becomes one pure helper in `src/lib/` that both the preview's click handler and the editor hand-off call.
  - **Scope note (deliberate reading of the issue's third bullet):** the preview does *not* open relative in-workspace files today (`./other.md` is inert there), so parity is the contract and this issue adds **no** new file-opening behaviour to either pane. If relative-`.md` navigation is wanted, it is a separate issue that must change the preview and the editor together. Record this in the citation so the next reader does not mistake it for an oversight.
- Both builds: nothing here is gated on `platform.kind` — the desktop shim and the hosted build get the submenu, the view, the hotkey and the modifier-click alike.

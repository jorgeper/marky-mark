# Spec: Generate docs/MAP.md from in-tree SPEC citations and gate it in validate.mjs (#35)

## Goal

All acceptance criteria in specs/issue-35.md are satisfied for issue #35, with
evidence visible in the session: a committed generator script derives
`docs/MAP.md` from the `SPEC<n>` citations already in `src/` and in the
E-numbered e2e tests, covering all 45 files in `docs/specs/`; `docs/MAP.md` is
committed, states in its own header that it is generated and never hand-edited,
and names the single `npm run` command that regenerates it; re-running that
command on a clean tree produces no diff; `scripts/validate.mjs` fails — in the
`--quick` tier as well as the full gate — when `docs/MAP.md` differs from what
the generator produces from the current tree, demonstrated by adding a citation
and then reverting; `docs/ARCHITECTURE.md` gains a header line pointing readers
who want "which file do I edit" at `docs/MAP.md` and is not otherwise
reorganised; new numbered unit tests cover the generator's pure core;
`npm run validate:quick` has been run and printed `QUICK VALIDATION: ALL
PASSED`; and a summary comment from the implementer exists on issue #35.

## Acceptance criteria

### The generator

- A new script under `scripts/` (e.g. `scripts/map.mjs`) generates
  `docs/MAP.md` from citations already in the tree. It reads, and does not
  invent, its inputs: `docs/specs/*.md` for the spec list, and `SPEC<n>`
  citation sites in `src/` and `tests/` for the rows.
- It follows the pattern the repo's other scripts already use: a pure,
  exported core plus a guarded CLI entry, with a `.d.mts` sidecar declaring the
  exported surface for the unit suite (see `scripts/licenses.mjs` +
  `scripts/licenses.d.mts`, and `scripts/release-prepare.mjs`). Parsing and
  rendering must be callable from a unit test without touching the filesystem.
- Every one of the **45** files in `docs/specs/` gets a row, including specs
  with zero citations (SPEC31 is spec-only today). A spec with no citing files
  is listed with an explicit "none" marker, not omitted — an absent row and an
  uncited spec must not look the same.
- Each row carries: the spec key and number (`SPEC.md` → the unnumbered base
  spec), the spec's **own title taken from its first `# ` heading** in
  `docs/specs/SPEC<n>.md`, the `src/` files that cite it, and the E-numbers of
  the e2e tests that cite it.
- Citation matching is **word-boundary exact**: `SPEC3` must not match `SPEC30`
  or `SPEC34`, and a bare `SPEC` citation (e.g. `src/platform/types.ts`) must
  bucket to `SPEC.md`, not to `SPEC2`. A unit test pins both cases.
- E-number attribution is derived from the test titles, not from file names:
  within an e2e spec file a citation is attributed to the E-numbered `test(...)`
  whose body encloses it, and citations before the first test (file header,
  shared setup) are attributed to the file rather than dropped. The generator
  must work whether `tests/e2e/` holds one spec file or a dozen (issue #36
  splits `app.spec.ts`), so it must not hardcode `app.spec.ts` or any file list.
- Output is **deterministic**: stable sort order, no timestamps, no absolute
  paths, no counts that depend on machine state; running the generator twice
  produces byte-identical files. `scripts/licenses.mjs` states the same
  constraint — match it.
- Citations to a spec number with no file in `docs/specs/` (SPEC28 was
  withdrawn; SPEC47/SPEC48 were removed) must not crash the generator and must
  not silently become rows. There are none in `src`/`tests` today; the
  behaviour is still defined and unit-tested.

### The generated file

- `docs/MAP.md` is committed, and its header states in plain words that it is
  generated from in-tree citations, is never hand-edited, and is regenerated by
  the one `npm run` command below. The header also names the generator's path.
- The file is usable as an answer to "which file do I edit": a reader looking
  for a feature can find the spec row and read off the `src/` files.
- Regenerating `docs/MAP.md` on a clean tree produces **no diff** (PRD 005
  requirement 48). Demonstrated in the session by running the command on a
  clean tree and showing `git status`/`git diff` empty for it.

### The gate

- `scripts/validate.mjs` fails when `docs/MAP.md` differs from what the
  generator produces from the current tree, so a citation added without
  regenerating fails the gate.
- The check runs in the `--quick` tier as well as the full gate. `npm run
  validate:quick` is this repo's configured verify command
  (`.sandcastle/config.mts`), so a check that only ran in the full gate would
  not be exercised by the acceptance evidence. It is a file comparison, not a
  spawned build — place it so it fails fast rather than after the e2e step.
- The failure output names the offending file, tells the reader to run the
  regeneration command, and follows the existing
  `VALIDATION FAILED at step: <name>` convention used by every other step in
  that file.
- The gate is **demonstrated**: with a `SPEC<n>` citation added to a `src/`
  file (or a line edited into `docs/MAP.md`), `npm run validate:quick` fails on
  this step with the message shown in the transcript; the change is then
  reverted and the gate passes. Both halves are in the session.

### Wiring

- `package.json` gains a script so regenerating is exactly one command
  (e.g. `npm run map`). It must be a single command with no arguments — PRD 005
  requirement 34. The implementer's summary comment states the script name.
- `AGENTS.md` does **not** exist yet and is **not** created here. Requirements
  34 (the `AGENTS.md` half) and 35 land in the `AGENTS.md` sub-issue, which is
  blocked by this one. Landing here means the script exists, is a single
  `npm run` command, and the comment names it.

### ARCHITECTURE.md

- `docs/ARCHITECTURE.md` gains a header line near the top directing readers who
  want "which file do I edit" to `docs/MAP.md`.
- It is **not** reorganised, split, or renarrated: `git diff docs/ARCHITECTURE.md`
  shows only that addition.

### Regression guards

- New numbered unit tests (**U155** onward — U154 is the current maximum;
  numbers are never reused, per `CONTRIBUTING.md`) cover the generator's pure
  core: title extraction from a spec heading, word-boundary citation matching
  (`SPEC3` vs `SPEC30`/`SPEC34`, bare `SPEC` vs `SPEC2`), E-number attribution
  including a citation outside any test, an uncited spec rendering as "none",
  and rendering being byte-identical for identical input. Reading repo files
  from a unit test follows `tests/unit/licenses.test.ts` (U16) and
  `tests/unit/readme-version.test.ts`; vitest runs in the `node` environment.
- Existing tests are not weakened, skipped, renumbered, or deleted.

### Scope

- In scope: the new generator + its `.d.mts`, `docs/MAP.md`, the
  `scripts/validate.mjs` check, the `package.json` script, the new unit tests,
  and the one-line `docs/ARCHITECTURE.md` pointer.
- Out of scope, and untouched: `docs/specs/*` (755 citations point at those
  paths — do not edit or move them), the `tests/e2e/app.spec.ts` split,
  `AGENTS.md`/`CLAUDE.md`/`.claude/settings.json`, the `archive/` move, the
  `specs/` → `issue-specs/` rename, `.sandcastle/CODING_STANDARDS.md`, and any
  version bump. This issue is independently landable.

### Gate

- The implementer iterated with `npm run typecheck` and a tight unit loop
  (`npx vitest run tests/unit/<new>.test.ts`), not the full suite after every
  change. Any baseline at the start of the attempt used the quick tier only.
- `npm run validate:quick` has been run **once**, in the implementer's session,
  right before declaring the goal met, and printed
  `QUICK VALIDATION: ALL PASSED`. The full `npm run validate` is welcome as
  extra evidence but is not required.
- A summary comment from the implementer exists on issue #35, naming the files
  changed, the regeneration script name, the demonstrated gate failure and its
  revert, and the gate output.

## Context

The inputs already exist and are dense: `rg -o 'SPEC[0-9]*' src` returns 619
citation sites and `tests/` another 142, across the 45 files in `docs/specs/`
(`SPEC.md`, then `SPEC2`–`SPEC46` with `SPEC28` absent). The convention is
`// SPEC34 §2.3: <what and why>` — see `src/platform/types.ts` for a bare
`SPEC` citation and `tests/e2e/app.spec.ts:41` for a test-body one. E-numbered
titles look like `test('E12: …')` in `tests/e2e/app.spec.ts`; `tests/e2e/web.spec.ts`
carries W-numbers and contributes nothing here.

`scripts/validate.mjs` is 141 lines. The version lock-step check at the top
(lines ~39–56) is the model for a cheap pre-step check that runs in both tiers:
it executes before the `steps` array and before the `QUICK` early-exit at line
~84. `FETCH_ALLOWLIST` (line ~113) is the repo's pattern for a committed
constant with a justifying comment.

`scripts/licenses.mjs` is the closest precedent for the generator: it
regenerates a committed markdown file deterministically ("sorted by
name@version, no timestamps, byte-identical on rerun") and pairs a pure
exported helper with a `.d.mts` sidecar consumed by `tests/unit/licenses.test.ts`.
Follow it rather than inventing a new shape.

PRD `prd/005-agent-context-hygiene.md` section E (requirements 30–34) and
evidence item 48 are the source of these criteria; parent issue is #23. The
PRD's measurement of why this matters — `docs/ARCHITECTURE.md` is 1,038 lines
with 18 total mentions of any `src/` path — is the reason the map is derived
rather than written.

# Spec: Dual-surface annotation rendering: independent comment/highlight layers and two-way pane sync (#285)

## Goal

All acceptance criteria in issue-specs/issue-285.md are satisfied for issue #285, with evidence visible in the session: a comment and a highlight over the same or intersecting ranges render as two independent layers in both the editor and the preview — both painted, each reachable, and activating, resolving or deleting one never mutating the other; commented ranges carry the fixed blue comment tint and highlight ranges their marker color in **both** surfaces; clicking a comment mark in either surface opens the comments pane if it is closed and activates that card, while clicking a highlight has no pane effect; activating a card scrolls the text to that comment's anchor with the SPEC14 §1.3 centre-and-flash feel in whichever surface shows the text — in plain edit that is the editor, not a preview; overlap rendering and both directions of the sync are covered by new e2e tests; and `npm run validate:quick` passes.

## Acceptance criteria

### Independent layers (PRD 023 Req 5)

- A comment record and a highlight record whose anchors are **identical**, and a pair whose anchors merely **intersect** (partial overlap), both paint in the preview: every text run carries the mark(s) of every record covering it, the comment run reads as the comment tint and the highlight run as its marker hue, and the overlapped run reads as the stacked/stronger treatment the existing `mark.hl mark.hl` rules already define. No painted run is lost, and no record's paint replaces another's.
- The same pair paints in the **editor** decorations: `.mm-hl[data-cid]` decorations for both records cover the overlapping source range (a comment decoration with no `data-color`, a highlight decoration with its color), subject to the existing "skip what the source cannot place confidently" rule (`mapHighlightsToSource`, PRD 022 Req 12 / PRD 023 Req 19) — a pair the source can place paints as two decorations, never as one.
- **Activating one never mutates the other.** Concretely, and each covered: activating (clicking) the comment adds the active treatment to the comment's marks only; resolving the comment ghosts the comment's marks only and leaves the highlight painted at full strength; deleting the comment leaves the highlight record on disk and painted; deleting the highlight leaves the comment record, its card, its thread and its paint untouched. No path rewrites the other record's `kind`, `color`, `body`, `resolved` or anchor.
- Where marks nest, a click in the **overlapped** run resolves to the record the pane can host: the comment wins over the highlight, in both surfaces (the preview's innermost-`closest('mark.hl')` lookup and the editor's `docHighlightRanges(...).find(...)` position hit-test both pick by record kind, not by DOM depth or array order). A click in a run covered by the highlight alone still resolves to the highlight.
- The rule that picks the hit record from a set of candidate ids is **pure logic in `src/lib/`** (a small module, or an addition to an existing one such as `src/lib/commentsPane.ts`/`src/lib/anchoring.ts`) with a matching `tests/unit/<kebab-case>.test.ts` covering: comment-over-highlight, highlight alone, several comments overlapping (position order or innermost — whichever is chosen is stated in the citation and pinned), and an id set with nothing hostable.

### Both surfaces render both kinds (PRD 023 Req 18, rendering half)

- Commented ranges render the **fixed blue comment tint** and highlight ranges their **marker color** in both the preview (`mark.hl` / `mark.hl[data-color]`, `src/styles.css`) and the editor (`.editor-wrap .cm-content .mm-hl` / `[data-color]`, `editor/styles.css`), through the `--mm-comment-tint` / `--mm-marker-*` token contract landed in issue #283 — no new hue literals, no aliasing the comment tint to a marker hue. Any gap between the two surfaces found while implementing (a state one surface paints and the other does not: active, ghosted-resolved, orphaned) is either closed or stated as deliberate in a citation comment.
- The editor paints in **plain edit and split edit**; the preview paints in **full preview and the split preview pane**. Painting is gated only by the `commentsEnabled` master switch and (for resolved comments) `showResolved` — never by the pane's open/closed setting, which issue #284 already established.
- The activation cue exists on the editor side too: with a card active in plain edit, its editor decoration is visibly distinguishable (the active/flash treatment, expressed through the existing token contract and the package's decoration seam — not a raw color literal, and `docs/STYLE-GUIDE.md` + the style lint in `scripts/validate.mjs` pass over any new rule).

### Text → pane: clicking a mark (PRD 023 Req 18)

- Clicking a **comment** mark in the full preview, in the split preview, in the plain-edit editor, or in the split-edit editor: opens the comments pane if it was closed (the persisted `showComments` setting flips, so the pane stays open afterwards), makes that comment the active card, and scrolls the card into view inside the pane. The scroll survives the pane having to mount and slide first (a single `requestAnimationFrame` fired before the pane exists is not enough) — after the click the card is on screen and marked active.
- Editor mark clicks are no longer split-only: `onHighlightClick` is wired in plain edit as well (today `settings.splitEdit ? handleMarkClick : undefined` in `src/App.tsx`), and the CodeMirror handler still returns `false`, so the click also places the caret exactly as it does now.
- Clicking a **highlight** mark has **no pane effect** in either surface: it never opens the pane, never creates or activates a card, and the pane's contents are unchanged (E420/E421's "a highlight has no card at all" contract still holds). Its effect stays confined to the text surface's own mark treatment.
- With `commentsEnabled` off there are no marks and no route opens the pane (E438's contract holds). A read-only role, a frozen (newer-MAJOR) store and an orphaned-anchor card keep exactly the gates they have today — sync is read behaviour and stays available where cards are readable; a card whose anchor is orphaned activates without scrolling anywhere and without throwing.

### Pane → text: activating a card (PRD 023 Req 18)

- Activating a card — by clicking it, and by the navigator (`Mod+Alt+ArrowUp/ArrowDown` and the pill) — scrolls the **text surface currently showing the document** to that comment's anchor and gives it the SPEC14 §1.3 activation feel (centre the first painted fragment, flash it): the `.doc` preview in full preview, the split preview in split, and **the editor in plain edit**, which today does nothing because `centerAndFlashMarks` only ever reads `docRef`/`splitDocRef`.
- The editor scroll goes through a **package seam** — a prop or an `EditorSyncHandle` method on `editor/src/components/Editor.tsx` — because the canonical-offset → editor-doc mapping lives inside the package (`docHighlightRanges`, the table-grid span machinery). The app does not re-derive that mapping, does not reach into CodeMirror, and does not repurpose `selectRangeRef` in a way that moves the user's selection or caret as a side effect of activating a card. The new seam is documented in the package's prop contract like its neighbours, and `editor/AGENTS.md`'s boundary rules hold (the package imports nothing from the app; the editor-boundary unit check passes).
- A comment the editor cannot place (the skip rule above) or that is off-screen-unpainted degrades to a no-op scroll: the card still activates, nothing throws, and no console noise appears.
- Cards in the collapsed **Resolved** section activate through the same path as flow cards, or the difference is deliberate and carries a citation saying why (today they call a bare `setActiveId`).
- Both directions agree on one active id: clicking a mark and clicking its card leave the same card active and the same marks tinted, in every mode.

### Scope boundaries

- This slice ships **no new authoring UX**: PRD 023 Reqs 6–13 (killing the selection popup, the Marky Mark menu Comment/Highlight entries, the new hotkeys, the preview selection button), Req 19's authoring-side anchor mapping, and Req 20's comment copy-link parity are **out of scope**. The existing popup / edit-mode affordance / SPEC25 carry keep working unchanged.
- No change to the pane's width, slide, persistence or chevron (issue #284's slice), and no change to the comment format (issue #283's slice).

### Citations, docs, hygiene

- Behaviour added or changed carries a citation comment in the repo's format (`PRD 023 §5` / `PRD 023 §18`, or `SPEC<n> §x.y` where a SPEC section is amended — SPEC6 §2, SPEC14 §1.3 and PRD 022 Req 12 are the ones this slice touches), per `.sandcastle/CODING_STANDARDS.md`.
- `docs/MAP.md` is regenerated with `npm run map` if any citation moved (the validation gate diffs it).
- No `console.*` in `src/`; `src/lib/` modules stay pure (no React, no component imports); any new CSS resolves through `--mm-*` tokens and scale tokens.

### Verification

- Unit coverage lands with the slice in `tests/unit/*.test.ts` for the pure hit-resolution logic (and for any other pure helper extracted), with `U<n>:` ids and a `describe` naming the contract.
- e2e coverage lands in `tests/e2e/comments.spec.ts` (and `tests/e2e/split-view.spec.ts` if a split-only behaviour needs its own home) with new `E<n>` ids taking the next unused numbers — E438 is the highest in the suite today, so start at E439; numbers are never reused or renumbered. It covers at least: an identical-range and an intersecting comment+highlight pair painting as two layers in the preview and as two decorations in the editor; deleting or resolving one leaving the other's paint and record intact; clicking a comment mark with the pane closed opening the pane and activating + revealing its card, in the preview **and** in the plain-edit editor; clicking a highlight mark opening nothing; and activating a card in plain edit scrolling the editor to the anchor (an off-screen anchor becomes visible).
- Existing suites are **updated** to the new contract rather than deleted or skipped — in particular E427 ("plain edit is paint-only: a click just places the caret") and E425 (split-edit painted-range click) now assert the Req 18 behaviour, each rewrite carrying a comment naming issue #285; E419–E424, E428, E435–E438 keep passing as written or are updated with the same kind of comment.

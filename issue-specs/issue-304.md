# Spec: Settings → Names: list previous names read-only under the unique-name field (#304)

## Goal

All acceptance criteria in issue-specs/issue-304.md are satisfied for issue #304, with evidence visible in the session: the hosted settings → Names section shows a read-only "Previous names: a, b. Links to these still open this workspace." line under the unique-name field exactly when the workspace manifest carries former names, the line is absent when there are none and updates in place right after a rename in the same dialog with no control to remove an entry, a new e2e test in `tests/e2e/hosted.spec.ts` drives it, `npm run validate:quick` passes in the implementer's session, and a summary comment from the implementer exists on issue #304.

## Acceptance criteria

- **Former names render read-only under the unique-name field (PRD 024 Req 16).** In `src/components/WorkspaceNames.tsx`, when `manifest.formerNames` is non-empty, a line reading exactly `Previous names: <a>, <b>. Links to these still open this workspace.` (names joined with `, `, in the manifest's order, oldest first) appears inside the Names section directly below the unique-name `.field` (after its optional problem line) and above the display-name field. It carries `data-testid="workspace-former-names"`. It is plain text: no input, no button, no per-name remove control, and nothing about it is interactive.
- **Absent when there is no history.** When `formerNames` is undefined or empty, the element is not rendered at all (not hidden, not an empty paragraph), so a workspace that has never been renamed shows the Names section exactly as it does today.
- **Updates immediately after a rename in the same dialog.** The line is derived from the `manifest` prop, not from local state copied at mount. Because `save()` already hands the server-returned manifest (which carries the server-computed `formerNames`, PRD 024 Req 1–3) to `onManifest`, and `WorkspaceAccessSettings` passes that manifest straight back down, a successful unique-name save makes the previous name appear (or the reclaimed name disappear, for `A → B → A`) without closing or reopening the dialog. A display-name-only save and a refused save change the line's content not at all.
- **Styling follows the style guide and the section's existing chrome.** The line uses the theme's muted secondary text through existing tokens/rules (the section's `.hotkey-hint` treatment is the natural fit: `--mm-text-caption`, `--mm-fg-muted`); it is visually distinct from the `.form-error` line of issue #250 and never uses the danger colour. No raw colour literals, no literal `fontSize`/`color` inline styles, no new hand-rolled header; any new CSS rule in `src/styles.css` resolves through scale tokens so the style lint in the quick gate stays green.
- **Hosted only.** The change is confined to the hosted Names section (`WorkspaceNames.tsx` and, if needed, `src/styles.css`); desktop, dev-shim and single-file builds are untouched. Nothing about the manifest PUT payload changes, and the client still never sends `formerNames` as an intent (the server discards it anyway).
- **Citations.** Every new or changed behaviour carries a `// PRD 024 Req 16 (issue #304): …` citation comment per `.sandcastle/CODING_STANDARDS.md`.
- **End-to-end coverage (PRD 024 Req 19).** A new test in `tests/e2e/hosted.spec.ts`, taking the next unused E-number (E569 at spec time — re-check with `grep -rhoE "test\('E[0-9]+" tests/e2e | sort` before committing, since parallel branches merge), drives the flow with existing helpers (`signIn`, `pathWorkspace`, `signInTo`, `openWorkspaceSettings` — the E536/E537 pattern): the Names section of a never-renamed workspace has no `workspace-former-names` element; renaming via the `workspace-unique-name` field and `workspace-names-save` makes the element appear in the same open dialog with the text `Previous names: <old>. Links to these still open this workspace.`; a second rename lists both former names in order; and the element contains no button or input. Existing tests (E535, E536, E537 and the rest) are not weakened, renamed or renumbered.
- **Existing coverage still passes.** No existing e2e or unit test is modified except where a collision after a parallel merge requires bumping the newer test's number per CODING_STANDARDS.
- **Iteration economy.** The implementer iterates with `npm run typecheck` and `npm run test:unit` (plus the single targeted test via `npx playwright test -g 'E569'` or whichever number it takes) after each change, and baselines an attempt with the quick tier only.
- **Full gate.** `npm run validate:quick` has been run ONCE in the implementer's session, right before declaring the goal met (not after every small change and not as a baseline at the start), and prints `QUICK VALIDATION: ALL PASSED`. If `npm run map` output changes because of the new citations, the regenerated `docs/MAP.md` is committed alongside.
- **Summary comment.** A summary comment from the implementer exists on issue #304 describing what changed, the new test number, and the validate:quick result.

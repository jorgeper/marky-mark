# Spec: most recent workspaces (#312)

## Goal

All acceptance criteria in issue-specs/issue-312.md are satisfied for issue #312, with evidence visible in the session: the hosted Open Workspace dialog (`data-testid="open-workspace-dialog"`) lists the signed-in user's most recently *used* workspaces on top, most-recently-used first, taken from the per-user `recent-workspaces.json` store that hosted opens already write, with every other workspace following in today's newest-modified order; a workspace that was just opened sits in the first row the next time the dialog opens, and opening another moves that one above it (LRU touch on every open, deduped); the ordering is a pure seam in `src/lib/workspaceLifecycle.ts` that, given no recency data, behaves exactly as today so U286/U287/U1196 pass unmodified; new U- and E-numbered tests pin the recency-first order; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #312.

## Acceptance criteria

- **Most-recently-used on top.** In the hosted flavor, with an empty query, the Open Workspace dialog's rows are ordered: first every listed workspace the signed-in user has opened, most-recently-used first (the order of `recent-workspaces.json`, which `rememberRecent` in src/lib/recentFiles.ts already keeps as an MRU list — the path moves to the front on every open, deduped, capped at `RECENT_CAP`); then every remaining listed workspace in today's order, most recently *modified* first. The row cap (`OPEN_WORKSPACE_ROW_CAP`, 5) still applies after ordering, so recently used workspaces fill the visible rows before merely recently modified ones. Today the dialog ignores use entirely and sorts by server `modified`, so a workspace the user opens daily can be invisible behind five workspaces other people edited.
- **LRU touch on every open.** Opening a hosted workspace by any route — the dialog, a `/<unique-name>` URL, a path deep link, the scratchpad — records it at the front of the user's recent list, so the next dialog shows it first. This already happens: hosted boot lands the bound workspace's virtual `/w/<id>/workspace.marky-workspace` path through `openWorkspaceFromPath` (src/App.tsx ~3074 → ~3478), which calls `commitRecentWs(rememberRecent(...))`, and the hosted platform persists `/config/recent-workspaces.json` through `/api/me/files` (per-user blob, PRD 007 Req 9). The implementer verifies this chain rather than adding a second recorder; if some route turns out not to touch the store, it is fixed to go through the same `commitRecentWs`.
- **Recency data reaches the dialog from the existing store.** `OpenWorkspaceDialog` (src/components/WorkspaceSwitcher.tsx) receives the user's recent workspace *ids*, most-recent-first, derived in App.tsx from the `recentWs` state (`RecentStore` of virtual paths) by a pure helper — e.g. `recentWorkspaceIds(store)` in src/lib/hostedPaths.ts or workspaceLifecycle.ts — that maps each entry through `parseHostedPath` and keeps only `kind === 'manifest'` ids, in order. Ids absent from the fetched listing (deleted workspaces, or ones the PRD 017 Req 11 listing policy no longer lists) are skipped silently; they never produce a row and never break the ordering. No new fetch, no new storage format, no `localStorage`.
- **A pure, backwards-compatible seam.** The ordering lives in src/lib/workspaceLifecycle.ts, next to `filterWorkspaces` / `visibleWorkspaces` — e.g. an optional trailing `recentIds: readonly string[] = []` parameter on both, or a separate `orderByRecentUse(items, recentIds)` they compose. With no recency data the output is byte-for-byte today's (newest-modified first), so the existing U286, U287, U1196 and every call site that does not pass ids pass unmodified. With a query, the match set is unchanged from today; ordering is fuzzy score first (as `fuzzyFilter` sorts), then recent use, then modified — achieved by feeding `fuzzyFilter` the recency-ordered list, since it is stable on input position. `src/lib/` stays React-free and platform-free; no `console.*`.
- **Desktop unchanged.** The desktop File → Open Recent workspaces section (PRD 002 §D15, `recentMenuEntries`) is already most-recently-used first and is not touched; E88 and every existing recent-file/-workspace test pass unmodified. Nothing in this issue changes the native `Open Workspace…` file dialog.
- **Unit tests.** In tests/unit/workspace-lifecycle.test.ts (and tests/unit/hosted-paths.test.ts if the id helper lands in hostedPaths.ts), new `it('U<n>: …')` cases numbered from the next unused U ID (U1265 at spec time; confirm with `grep -rhoE "it\('U[0-9]+" tests/unit | sort -t U -k2 -n | tail -1`) pin: (a) recently used ids come first in the given order, the rest newest-modified after them; (b) an id not in the listing is ignored; (c) recency-first ordering survives the row cap (a used-but-old workspace is visible, a newer-modified unused one drops off); (d) with a query the match set equals today's and among equal-score matches recent use precedes modified; (e) `recentWorkspaceIds` keeps manifest paths only, in order, and drops non-workspace paths. `describe` blocks name the contract (`PRD 007 Req 11 (issue #312): …`).
- **E2E test.** A new test in tests/e2e/hosted.spec.ts numbered from the next unused E ID (E550 at spec time; confirm with `grep -rhoE "test\('E[0-9]+" tests/e2e | sort -t E -k2 -n | tail -1`) creates `OPEN_WORKSPACE_ROW_CAP + 2` workspaces under a worker-unique prefix (E504's pattern), opens the OLDEST-created one by URL (`signInTo(page, user, id)`), then opens the Open Workspace dialog (`menu-open-workspace` via `openAppMenu`), types the prefix so only this test's rows show, and asserts the first row is the workspace just opened and the following rows are the others newest-modified first; then opens a second one and asserts it now precedes the first. The hosted lane shares one Azurite store and the seeded users across parallel workers, and the per-user recent store is a read-modify-write blob — so the test must not depend on other workers' opens (filter by prefix; prefer asserting in the page that performed the open rather than after a cold reload, or use a seeded user the suite otherwise rarely opens workspaces as). No existing test is weakened, renamed, skipped or renumbered.
- **Citations and map.** Changed behaviour carries `PRD 007 Req 11 (issue #312): …` citation comments (the dialog's doc comment and `visibleWorkspaces`' JSDoc updated to say most-recently-used first, then modified); `docs/MAP.md` is regenerated with `npm run map` if the spec→code table changes.
- **Verification economy.** The implementer iterates with `npm run typecheck` and `npm run test:unit` (or one targeted e2e via `npx playwright test -g '<title>'`), baselining with the quick tier only; the full gate `npm run validate:quick` (typecheck, unit, desktop-shim e2e including the hosted lane, file checks) has been run ONCE, right before declaring the goal met, and prints `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- A summary comment from the implementer exists on issue #312 describing what ordered the dialog before, what orders it now, where the recency data comes from, and how it was verified.

## Context

"The open workspace" in the issue is the hosted **Open Workspace** dialog (PRD 007 Req 11; `OpenWorkspaceDialog` in src/components/WorkspaceSwitcher.tsx, mounted from src/App.tsx ~8693 with `lifecycle={platform.workspaces}` and `me`). Its rows come from `visibleWorkspaces(query, all)` in src/lib/workspaceLifecycle.ts (~135–155), which is `fuzzyFilter` over `[...items].sort(newestFirst)` cut to `OPEN_WORKSPACE_ROW_CAP`; `newestFirst` compares the server's `modified` stamp, i.e. who last edited, not who last opened. The desktop app already has the LRU the issue asks for: PRD 002 §D15 keeps `recent-workspaces.json` via `rememberRecent` (src/lib/recentFiles.ts, MRU insert, dedupe, `RECENT_CAP` 10) and shows it in File → Open Recent (src/lib/menuSpec.ts ~310). In hosted, that same store is per-user: `configDir()` is `/config`, `parseHostedPath` maps `/config/…` to `/api/me/files/…` (src/lib/hostedPaths.ts ~76–95, server/userFiles.ts), hosted defines `readDirEntries` so `commitRecentWs` writes it (App.tsx ~1857–1864), boot reads it back (~3026–3035), and `openWorkspaceFromPath` touches it with the virtual manifest path `hostedWorkspaceFilePath(id)` = `/w/<id>/workspace.marky-workspace` (App.tsx ~3478; hosted boot enters that path at ~3074 via `isWorkspaceFilePath`). So the work is: extract ids from `recentWs`, pass them to the dialog, and order by them ahead of `modified` inside the pure seam. `fuzzyFilter` (src/lib/fuzzy.ts) returns input order for an empty query and sorts score-desc, stable by input index, otherwise — pre-ordering the input is enough. Existing tests: U286/U287/U1196 (tests/unit/workspace-lifecycle.test.ts ~197–240) pin the no-recency order; E183/E503/E504 (tests/e2e/hosted.spec.ts ~1212–1370) cover the dialog and assert counts, not order. The hosted e2e lane boots `npm run server:local` (Azurite from node_modules, mock auth; users `ada`, `grace`, `alan`, …) as the second Playwright `webServer` and runs inside `npm run test:e2e` / `validate:quick`; helpers `signIn`, `signInTo(page, user, workspaceId?)`, `createWorkspace`, `uniqueNameOf`, `openAppMenu`, `workspaceRows` live at the top of hosted.spec.ts. The row shows `timeAgo(workspace.modified)`; changing that label is out of scope.

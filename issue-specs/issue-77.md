# Spec: Workspace settings: membership management and custom roles editor (#77)

## Goal

All acceptance criteria in issue-specs/issue-77.md are satisfied for issue #77, with evidence visible in the session: the Workspace scope of Settings shows a holder of `workspace.members` a people section that adds members through the existing Graph search picker, removes them, changes a member's role and toggles everyone-in-tenant access with a default role (Viewer), never leaving the workspace without an Owner; it shows a holder of `workspace.roles` a custom-roles editor that creates, renames, edits and deletes named subsets of the permission catalog persisted in the manifest, refusing to delete a role still in use and refusing built-in names; both sections are hidden for users lacking the verb and are backed by server endpoints that each check exactly one permission and answer 403 (naming the verb) otherwise; the new behaviour is pinned by unit tests (U295+) and offline hosted e2e tests (E193+); and `npm run validate:quick` has been run once at the end in the implementer's session and prints `QUICK VALIDATION: ALL PASSED`.

## Acceptance criteria

- **(PRD 007 Req 16 — membership management)** The Workspace scope of Settings (`src/components/SettingsPanel.tsx`) shows holders of `workspace.members` a people section that: lists current members with their resolved display names (unresolvable ids fall back to plain identifiers, via `resolveMembers` in `src/lib/membership.ts`); adds members through the existing `src/components/MembershipPicker.tsx` mounted against the live `/api/directory/*` endpoints (no second picker, no fork of it); removes a member; changes a member's role through a control offering the five built-ins **and** the workspace's own custom roles; and toggles everyone-in-tenant access with an Owner-chosen default role that starts at `DEFAULT_EVERYONE_ROLE` (Viewer). Changes persist in the manifest and survive a reload.
- **(PRD 007 Req 16 — invariants)** Explicit membership continues to override the everyone-role (already `resolvePermissions`; keep it pinned by a test), and a workspace always retains at least one Owner: removing the last Owner, or changing the last Owner's role to anything else, is refused with a visible message in the UI **and** rejected by the server (400) rather than merely disabled in the client. "Owner" here means the built-in `Owner` role by name.
- **(PRD 007 Req 15 — custom roles editor)** The same settings surface shows holders of `workspace.roles` a custom-roles editor that creates a named role as a subset of the fourteen-verb catalog (`PERMISSIONS` in `src/lib/hostedWorkspace.ts`, rendered as checkable verbs), renames an existing custom role, edits its permission set, and deletes it — all persisted in the manifest's `roles[]`. Built-in roles are listed read-only (or not listed as editable at all): creating, renaming, editing or deleting a built-in, and creating a custom role that shadows a built-in name or a duplicate custom name, is refused in both the UI and the server. A rename of a role that members hold carries those members over to the new name in the same update, so nobody silently drops to no permissions.
- **(PRD 007 Req 15 — in-use deletion)** A custom role held by any member cannot be deleted: `removeCustomRole` in `src/lib/hostedWorkspace.ts` (which today refuses only built-in names) gains the in-use refusal with an error naming the role, the server returns 400 for such a request, and the UI disables or explains the refusal instead of silently doing nothing. A role used as the everyone-access role while everyone-access is enabled counts as in use for the same reason — deleting it would silently strip a live grant.
- **(PRD 007 Req 13+17 — server endpoints)** The mutations are server-side endpoints under `server/workspaces.ts`, each declaring and checking **exactly one** required permission: membership + everyone-access edits require `workspace.members`, custom-role edits require `workspace.roles`. A caller without the verb gets 403 naming it, an unknown workspace id 404, and invalid input (unknown role name, unknown permission verb, built-in shadowing, last-Owner removal, in-use role deletion) 400 with a named error. The server owns `created`/`modified` on every write as the manifest PUT already does. The endpoint→permission table in `server/README.md` gains the new rows (and its "finer-grained member/role endpoints are #77" note is updated).
- **Existing manifest PUT contract is untouched.** `PUT /api/workspaces/<id>/manifest` keeps its documented `workspace.settings` gate and whole-manifest semantics; U264–U266 and E173 plus the `sharedWorkspace` helper in `tests/e2e/hosted.spec.ts` keep passing unchanged. Narrowing that endpoint so a `workspace.settings`-only custom role cannot edit members through it belongs to the #79 enforcement sweep, not here.
- **UI gating and flavor containment.** Each section renders only when the signed-in user's resolved permissions include its verb (the pattern `src/components/WorkspaceDangerZone.tsx` already uses via `lifecycle.permissions(id)`), so a Viewer opening Workspace settings sees neither. `SettingsPanel.tsx` gains no hosted-flavor branching and no hosted imports: the sections arrive as host-supplied `ReactNode` slot(s) alongside the existing `workspaceActions` prop, mounted from `src/App.tsx` on the `platform.workspaces` capability check (PRD 007 Req 2). New components live in `src/components/`; new REST calls live in `src/platform/hostedWorkspaces.ts` behind the `WorkspaceLifecycle` seam. New CSS uses the existing theme variables like the `.membership-*` / `.workspace-danger` rules in `src/styles.css` — no hard-coded colors.
- **Pure logic is unit-tested (U295+).** The decisions — member add/remove/role-change with the last-Owner invariant, everyone-access toggle and default role, custom-role create/rename/edit/delete with built-in, duplicate and in-use refusals, and the role list a member picker may offer — are pure functions in `src/lib/` (extend `hostedWorkspace.ts` / `workspaceLifecycle.ts` or add a sibling module), with vitest tests under `tests/unit/` numbered from U295 (current ceiling U294). Server-side behaviour gets HTTP-level tests in `tests/unit/server-workspaces.test.ts` against the in-memory storage seam, in the same style as U263–U268.
- **E2e coverage runs offline (E193+).** New Playwright tests in `tests/e2e/hosted.spec.ts`, numbered from E193 (renumbered on merge: issue #76 took E187–E192), run against the local hosted server on port 4924 with seeded mock users and Azurite only, and observably verify at least: an Owner adds a member through the settings picker and that member (in a second session) can then open the workspace; changing a member's role changes what they can do; the last-Owner refusal is visible; enabling everyone-access with a default role lets a non-member in while an explicit member keeps their own role; a custom role created in the roles editor is grantable to a member and cannot be deleted while held; and a member without `workspace.members`/`workspace.roles` sees neither section. Existing tests are not weakened, renumbered, or skipped, and no new number collides (the file already reuses E172–E174 — do not add more).
- **Standards, docs, map.** New behaviour carries citation comments (`// PRD 007 Req 15/16: …`) per `docs/COMMENT-FORMAT.md` and `.sandcastle/CODING_STANDARDS.md`; `docs/MAP.md` is regenerated via `npm run map` if the citation set changed (the quick gate diffs it); the no-`console.*` rule applies to `src/`.
- **Scope guard.** No folder/file management, upload/download or ETag conflict UX (#76), no start-page action list (#78), no broader permission-enforcement sweep beyond the endpoints this issue adds (#79), no changes to the create/open/delete lifecycle flows beyond what reusing their seam requires.
- Iteration used `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code), with single hosted e2e tests run via `npx playwright test -g '<title>'` while debugging — the full e2e suite was not used as an inner loop, and any starting baseline used the quick tier only.
- `npm run validate:quick` has been run **once**, at the end, in the implementer's session, and prints `QUICK VALIDATION: ALL PASSED`.
- A summary comment from the implementer exists on issue #77.

# Spec: Chrome token layer in styles.css + THEMES.md chrome-token docs (PRD 018 Reqs 1–6) (#202)

## Goal

All acceptance criteria in issue-specs/issue-202.md are satisfied for issue #202, with evidence visible in the session: `src/styles.css` defines a delimited chrome token layer on `.theme-root` (spacing/radius/shadow/type scales plus the state colours, colour tokens derived from the theme contract) with every `var(--mm-…)` the stylesheet uses now declared and stale fallbacks removed, the `--mm-bg-elev` typo in `.start-action` is fixed to `--mm-bg-elevated`, `THEMES.md` documents a "Chrome tokens (optional)" section, and `npm run validate:quick` has printed `QUICK VALIDATION: ALL PASSED` in the implementer's session.

## Acceptance criteria

- (Req 1) `src/styles.css` defines a chrome token layer as custom properties on `.theme-root` (the same scope the theme contract uses), in one clearly delimited block near the top of the file, with a citation comment naming PRD 018. It contains at least: a spacing scale (`--mm-space-1` … `--mm-space-6` or equivalent), a radius scale (small / medium / pill — exactly three values, no more), a shadow scale (`--mm-shadow-card`, `--mm-shadow-panel` or equivalent — two values), a UI type scale (four sizes at most), and the state colours `--mm-danger`, `--mm-danger-fg`, `--mm-hover`, `--mm-muted`, `--mm-focus-ring`.
- (Req 2) Every colour-involving chrome token has a default derived from the theme contract (e.g. `--mm-hover` from `--mm-accent` or `--mm-border` via `color-mix()`, `--mm-muted` from `--mm-fg-muted`), so switching any of the 27 bundled themes changes the chrome with no theme defining a chrome token. The 27 files in `themes/` are unmodified. Non-colour tokens (spacing, radius, shadow, type scale) have literal defaults.
- (Req 3) Every custom property `src/styles.css` uses is declared: the currently undeclared tokens (`--mm-danger` 14 uses, `--mm-hover` 5, `--mm-muted` 6, `--mm-find` 2, `--mm-find-active` 2, `--mm-find-fg` 4, `--mm-panel-shadow` 3, `--mm-card-shadow` 3, `--mm-split` 2, `--mm-folders` 2, `--mm-fence-ring` 9 — counts as of 2026-09-01) are each either defined in the chrome token block or replaced at every use site by a token that is. No `var(--mm-…)` in `src/styles.css` names a property with no definition anywhere in `src/styles.css` or `THEMES.md`.
- (Req 4) `var()` fallbacks are removed from chrome rules whose token is now defined (e.g. the three `--mm-card-shadow` fallbacks that disagree with each other are gone). Fallbacks remain only for contract variables a third-party theme might omit, and each such fallback is the value documented in `THEMES.md`.
- (Req 5) The typo `var(--mm-bg-elev, #ffffff)` in `.start-action` (`src/styles.css:1695` pre-change) reads `--mm-bg-elevated`, so the splash's neutral buttons follow the theme's elevated background on every bundled dark theme.
- (Req 6) `THEMES.md` has a section titled "Chrome tokens (optional)" listing every chrome token with its default and a one-line description, stating that a theme may override any of them and need not define any. The existing required contract of 34 variables is unchanged.
- The new/changed CSS carries citation comments per `.sandcastle/CODING_STANDARDS.md` citing `PRD 018 Req <n>` (PRD 018 Req 34), and no visual redesign occurred: this issue only adds token definitions, rewires undeclared tokens, and fixes the Req 5 typo — primitive classes, component wrappers, and migration are later sub-issues of #198.
- Iteration used `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code); the full gate `npm run validate:quick` was run ONCE, right before declaring the goal met (not after every small change, and not as a baseline), and printed `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- A summary comment from the implementer exists on issue #202.

## Context

PRD: `prd/018-consistent-ui-styling.md` (Reqs 1–6, section "A. Chrome tokens"; Non-goals matter — do not touch document-rendering rules, `themes/` files, export/print CSS, or the control panel). Parent: #198. This is the first sub-issue of the PRD: only the token layer and docs, no `.btn`/`.menu`/`.dialog` primitives yet. `src/styles.css` is 4,200 lines — do not read it whole; grep for the token names and `var(--mm-` to find use sites. The theme contract lives on `.theme-root` (documented in `THEMES.md`, 34 variables); the existing `:root` blocks near the top of `styles.css` (`--mm-slide-ease`, `--mm-splash-top`) are internal motion/layout tokens, not the contract, and stay as they are. Note some existing fallbacks for the same undeclared token disagree across sites (the PRD's Problem section documents `--mm-card-shadow`'s two values) — when defining the token, pick one value per the PRD's "picks one, does not invent" rule. `color-mix()` is fine in this codebase (modern WebView/browser targets). The later lint sub-issue (PRD Req 26) will mechanically check "every used token is declared" — leave the token block clearly delimited (e.g. begin/end comment markers) so that lint can find it.

# Spec: Hosted Platform implementation (kind: 'hosted'): REST-backed seam, shared comments/images, roaming settings (#73)

## Goal

All acceptance criteria in issue-specs/issue-73.md are satisfied for issue #73, with evidence visible in the session: a `kind: 'hosted'` Platform implementation exists in `src/platform/` satisfying the seam in `src/platform/types.ts` against the server's REST API, with no hosted-flavor branching outside `src/platform/` beyond existing capability checks; comment sidecars and pasted images persist as blobs inside the workspace and are visible to other signed-in members; the User settings layer is stored server-side as a per-user blob (roaming) and the Workspace layer resolves from the manifest; and `npm run validate:quick` has been run once at the end and passes.

## Acceptance criteria

- **(PRD 007 Req 2 — the seam)** A `Platform` implementation with `kind: 'hosted'` exists in `src/platform/` (e.g. `src/platform/hosted.ts`) and satisfies the seam in `src/platform/types.ts` by calling the existing REST API (`/api/workspaces/<id>/files/...`, `/api/me`, etc. in `server/app.ts` / `server/workspaces.ts`) with the signed-in session's bearer token. The `kind` union in `src/platform/types.ts` includes `'hosted'`, and `src/platform/index.ts` resolves the hosted platform when the served HTML carries the hosted marker (`src/lib/hostedGate.ts`) — Tauri, the dev shim, and static web resolution are unchanged.
- **(PRD 007 Req 2 — no leakage)** App code outside `src/platform/` does not branch on the hosted flavor except via the existing platform capability checks (optional-method presence / the checks already used to distinguish flavors). Evidence: a grep over `src/` excluding `src/platform/` shows no new `kind === 'hosted'`-style branching outside capability-check patterns already established.
- **(PRD 007 Req 8 — shared comments)** Comment sidecars are stored as blobs inside the workspace prefix: a comment written by one signed-in member is visible to a different member on next load of the same document. Covered by an E-numbered e2e test in `tests/e2e/hosted.spec.ts` (two sign-in sessions against the local dev mode server).
- **(PRD 007 Req 8 — shared images)** Pasted images are stored as blobs inside the workspace and render for every member with `doc.read`: the hosted platform implements `writeBinaryFile` (image paste path, SPEC20) against the API, and `resolveAssetSrc` maps doc-relative image refs to URLs the signed-in webview can load. The server accepts and serves binary workspace blobs (extend the files endpoints if they are currently text-only). Covered by an E-numbered e2e test where one member pastes an image and a second member sees it rendered.
- **(PRD 007 Req 9 — roaming settings)** The PRD 002 layered configuration resolves in the hosted flavor with the Workspace layer read from the manifest's `settings` slot (`src/lib/hostedWorkspace.ts`) and the User layer stored server-side as a per-user blob behind an authenticated endpoint (outside any workspace prefix, keyed by the signed-in user id). Changing a personal setting, then loading the app in a fresh browser session as the same user, shows the changed setting; a different user does not inherit it. Covered by an E-numbered e2e test.
- New pure logic (URL/path mapping, settings-blob plumbing, any manifest/settings resolution helpers) lives in `src/lib/` or as pure platform helpers with unit tests; behaviour sites carry citation comments per `docs/COMMENT-FORMAT.md` (cite `PRD 007 Req 2/8/9` as the existing hosted code does), and `docs/MAP.md` is regenerated via `npm run map` if the spec→code mapping changed.
- Out of scope (owned by sibling issues — do not build here): workspace create/open/delete flows (#75), folder management / upload / download / ETag conflict UX (#76), membership & custom-roles settings UI (#77), start pages (#78), the permission-enforcement sweep (#79). This issue may rely on workspaces created via the API directly in tests.
- Iteration used `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code), with single hosted e2e tests run via `npx playwright test -g '<title>'` while debugging — the full e2e suite was not used as an inner loop or as a starting baseline.
- `npm run validate:quick` has been run **once**, at the end, in the implementer's session, and prints `QUICK VALIDATION: ALL PASSED`.
- A summary comment from the implementer exists on issue #73.

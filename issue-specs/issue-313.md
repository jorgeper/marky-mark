# Spec: search doesn't select well (#313)

## Goal

All acceptance criteria in issue-specs/issue-313.md are satisfied for issue #313, with evidence visible in the session: clicking a Search-view result in edit mode selects exactly the matched text even when a gridded table sits above the match or the match is inside a table cell (today every match below a table selects the wrong characters because canonical-buffer offsets are dispatched into the expanded editor document); clicking a result in preview mode highlights the exact hit words with a `mark` in the find-active colours instead of only flashing the whole enclosing block in the pale comment tint; the landed hit in both modes and the `<mark>` in the result rows use the bright `--mm-find` / `--mm-find-active` / `--mm-find-fg` tokens rather than `--mm-comment-tint-active`; new E-numbered e2e tests pin the exact selected/marked text below a table and in preview; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #313.

## Acceptance criteria

- **Edit-mode landing selects exactly the hit.** With the folder root open, a query in the Search view, and the app in edit mode, clicking a content match (`data-testid="search-match"`) leaves the editor's main selection covering exactly the matched text (`window.getSelection().toString()` / `state.sliceDoc(from, to)` equals the matched substring) for every match, including: a match in a plain paragraph before any table, a match inside a gridded table cell, and a match on a line below a gridded table. Reproduced today with a doc containing `| col a | col b |` / `| --- | --- |` / `| cell | needleword four |` followed by `> quoted needleword five` and `Tail paragraph **bold needleword six** end.`: the clicks select `""`, `dleword fo` and `e\n\nTail pa`. Root cause: `landSearchMatch` (src/App.tsx, PRD 014 Req 8) feeds `matchDocOffsets(stateRef.current.buffer, match)` (canonical text) straight into `editorSelectRef` (raw CodeMirror document, where SPEC40 table mode expands every gridded table onto more characters and lines). The fix resolves the match against the text the editor actually holds — e.g. map the canonical line through `canonicalLineMapper` (editor/src/components/tableMode.ts) and re-find the hit on that raw line with the compiled matcher / occurrence index, or map the offsets through the table-mode spans — never by trusting canonical character offsets. Line endings are not the cause (verified: LF and CRLF files behave identically).
- **Edit-mode landing is loud.** In addition to the selection (whose `--mm-selection` tint is an 18%-alpha wash), the landed range carries a visible hit decoration in the find-active colours (background `--mm-find-active`, text `--mm-find-fg` — the same pair `.cm-searchMatch-selected` uses in editor/styles.css), either persisting until the selection changes / the document edits, or as a flash lasting at least ~900ms. The decoration must not disturb the FindBar's own `@codemirror/search` state (opening the bar afterwards still works exactly as E291/E345 assert), and must not carry the comment/highlight machinery's classes or data attributes.
- **Preview-mode landing marks the exact words.** Clicking a content match while in preview mode wraps the matched text in the rendered document with a `mark` element (via `highlightRange` from src/lib/domtext.ts over the doc-text space, the same mechanism the find bar's `applyFindMarks` uses — never `mark.hl`, never `data-cid`), scrolled into view, styled with `--mm-find-active` / `--mm-find-fg`. The mark's `textContent` equals the matched text. Locating the hit: resolve the match's source line to its anchored block (`[data-mm-line]`, the walk already in `landSearchMatch`), then find the compiled matcher's occurrences inside that block's rendered text and pick the one whose index equals the match's index among the panel's matches for that file inside the same block's source line range (the results in `searchResults` already carry every match with its line). When the hit cannot be found in the rendered text (the match sat in dropped markup, e.g. a link URL or fence info string), fall back to the existing block flash — but the flash must then use the find colours, not the comment tint. The mark is removed (unwrap + `normalize()`, document text unchanged) on the next landing, a query change, a document switch, a mode toggle, or the next preview re-injection; it never survives into the comment anchoring pass as text.
- **Brighter colours everywhere the hit shows.** `.search-match-text mark` (the excerpt in the result rows) and the landing flash `@keyframes mm-search-flash` / `.doc .search-flash` no longer reference `--mm-comment-tint-active`; they use the find token set (`--mm-find` for the row excerpt, `--mm-find-active` for the landed hit, `--mm-find-fg` for text), so the hit reads with its own foreground on light and dark themes exactly as E291 asserts for find marks. No new colour literals; tokens only, per `docs/STYLE-GUIDE.md` and the style lint in `scripts/validate.mjs`. If a new token is genuinely needed it is declared in the `--mm-find*` block of src/styles.css (~line 136) and documented in THEMES.md and docs/STYLE-GUIDE.md.
- **Same-file and cross-file paths both fixed.** The behaviour above holds whether the clicked match's file is already the active document (immediate `landSearchMatch`) or opens through `openDocGuarded` and the commit-driven landing effect; the result list, query and collapse state are untouched by the click (E342's guarantees stand).
- **Tests.** New e2e tests in tests/e2e/search.spec.ts, numbered from the next unused ID (E543 at spec time; check `grep -rhoE "test\('E[0-9]+" tests/e2e | sort` before numbering), assert: (a) in edit mode the selected text equals the matched text for a match below a gridded table and for a match in a table cell (the exact repro doc above is a good seed); (b) in preview mode a `mark` whose text equals the matched text exists after the click with computed background `rgb(240, 136, 62)` and colour `rgb(31, 35, 40)` (the token defaults, as E291 checks); (c) the result-row `mark` background is the `--mm-find` default `rgb(255, 223, 93)`. Any new pure helper under `src/lib/` (e.g. the block-relative occurrence resolver) has a unit test in its matching `tests/unit/<kebab>.test.ts` numbered from the next unused U ID (U1250 at spec time). E342 and every existing search/find test pass unmodified — no assertion weakened, nothing skipped.
- **Citations and standards.** Changed behaviour carries `PRD 014 Req 8 (issue #313): …` citation comments; `src/lib/` additions stay React-free and platform-free; no `console.*`; `npm run map` output (docs/MAP.md) is regenerated if the spec→code table changes.
- **Verification economy.** During the attempt the implementer iterates with `npm run typecheck` and `npm run test:unit` (or one targeted e2e via `npx playwright test -g '<title>'`), baselining with the quick tier only; the full gate `npm run validate:quick` has been run ONCE, right before declaring the goal met, and prints `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- A summary comment from the implementer exists on issue #313 describing the root cause (canonical-vs-expanded offsets), what the landing now does in each mode, the colour change, and how it was verified.

## Context

The issue names two things: the found hit should be "way more visible / brighter", and "it's not selecting the right words". Both are the Search view's landing (PRD 014 Req 8), not the find bar: the find bar's preview marks were probed and wrap the right words, and already use the bright `--mm-find*` tokens. The landing lives in src/App.tsx `landSearchMatch` / `openSearchResult` / the cross-file landing effect (~lines 7635–7720; grep `PRD 014 Req 8`). Edit mode calls `editorSyncRef.goToLine(match.line)` then `editorSelectRef(matchDocOffsets(buffer, match))` — `matchDocOffsets` (src/lib/searchScan.ts) is correct over the text it is given, but that text is the canonical buffer while the editor holds the SPEC40 expanded form; `canonicalLineAt` / `canonicalLineMapper` in editor/src/components/tableMode.ts are the existing two-way line maps (issue #260/#264 hit the same drift for heading copy-links and scroll sync). Preview mode today only flashes the nearest `[data-mm-line]` block at or above the match line (a whole `UL`, `TABLE`, `PRE` or multi-line `P`) with `.search-flash` in the comment tint — no word-level highlight exists. `highlightRange` / `getDocText` in src/lib/domtext.ts and the find engine's `applyFindMarks` / `clearFindMarks` (App.tsx ~1293–1340) show how to wrap and unwrap exact-text marks safely alongside comment marks. Colours: the `--mm-find*` tokens sit in src/styles.css ~136–142; the comment-tinted rules to change are `.search-match-text mark` and `.doc .search-flash` / `@keyframes mm-search-flash` (~2846–2865); the editor-side hit colours are `.cm-searchMatch(-selected)` in editor/styles.css (~865). E2E setup: tests/e2e/search.spec.ts (`seedSearchTree`, `searchFor`), helpers `seedFolders`, `openFolderRoot`, `fsWrite`; `Control+e` toggles edit mode. The desktop e2e suite is serialized and slow — run single tests with `npx playwright test -g '<title>'` while iterating.

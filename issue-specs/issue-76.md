# Spec: Hosted files and editing: folder management, single-file upload/download, ETag concurrency (#76)

## Goal

All acceptance criteria in issue-specs/issue-76.md are satisfied for issue #76, with evidence visible in the session: the hosted folder sidebar creates, renames, deletes and moves files and folders through both a right-click context menu and drag-and-drop, backed by server-side move/rename that checks exactly one catalog permission per endpoint; single-file upload (File menu, folder context menu, drop onto the sidebar) and single-file download (File menu, file context menu) work for holders of `file.upload`/`file.download`, with a 20 MB cap and a Markdown + rendered-asset allowlist enforced on the client (clear rejection message) and independently on the server; saves carry the ETag from load, so a save against a file another member has since written is refused and the user is prompted to reload the newer version or overwrite it rather than silently losing that write; the new behaviour is pinned by unit tests (U295+) and offline hosted e2e tests (E187+); and `npm run validate:quick` has been run once at the end in the implementer's session and prints `QUICK VALIDATION: ALL PASSED`.

## Acceptance criteria

- **(PRD 007 Req 18 — folder management)** In a hosted workspace the folder sidebar supports the full set: New File, New Folder, Rename, Delete, and moving a file or folder into another folder, reachable **both** from the right-click context menu (`folderContextMenu` in `src/lib/folderOps.ts`, `src/components/FolderPanel.tsx`) and by dragging a row onto a folder row (drag-and-drop is new — the panel has none today; it lands in the shared component, so any flavor whose platform exposes the move seam gets it, and the existing shim/desktop folder-tree tests must keep passing). A moved or renamed directory takes its contents with it, open tabs/state follow the rename (the existing `remapPath` path in `src/App.tsx` § SPEC35 §5.3), and a newly created **empty** folder is visible in the sidebar and still there after a reload — blob storage has no directories, so the implementation must make that explicit (e.g. a hidden placeholder blob under the folder's prefix that the tree does not list) rather than leaving the folder to vanish.
- **(PRD 007 Req 18 — the server side of it)** The hosted platform (`src/platform/hosted.ts`) implements the SPEC35 seams the sidebar drives — at minimum `renameEntry` (rename **and** move, recursive for a directory prefix) and `trashEntry` — against real endpoints. There is no rename/move route today: add one (or more), each declaring and checking **exactly one** permission from the catalog after the existing `requirePermission` guard, and add the row(s) to the endpoint→permission table in `server/README.md`. The mapping: moving/renaming a **file** requires `file.rename`; creating, renaming, moving or deleting a **folder** requires `folder.manage`; deleting a file stays `file.delete`. A move onto an existing path does not silently destroy the target (409/400 or a unique name, the implementer's call — but state it in the citation comment), an unknown source is 404, and a caller without the verb gets 403 regardless of what the UI showed. Per PRD 007 Req 17 the UI also hides or disables the menu items and drop targets the current user's permissions don't allow — a Viewer sees no New File / Rename / Delete / move affordance.
- **(PRD 007 Req 19 — single-file upload)** A member with `file.upload` can upload one file from three entry points: a File-menu item, the folder context menu (uploading into the clicked folder), and dropping a file from the OS onto the folder sidebar (`onFileDrop` in `src/platform/hosted.ts` currently comments the case away as this issue's scope). The uploaded file lands at the target path, appears in the sidebar, and reads back byte-identical — an uploaded Markdown file opens in the editor, an uploaded image renders in a document that references it (the `?raw=1` byte path already exists). An upload into a folder that already holds that name must not silently overwrite the existing blob.
- **(PRD 007 Req 19 — limits, enforced twice)** Uploads are capped at 20 MB and restricted to Markdown (`.md`, `.markdown` — `isMarkdownFile` in `src/lib/folderTree.ts`) plus the asset types the app renders (`png`, `jpg`, `jpeg`, `gif`, `webp`, `svg` — the set in `RAW_CONTENT_TYPES` in `server/workspaces.ts` and the image-dialog filter in `src/platform/tauri.ts`). The rule is a pure function in `src/lib/` (shared by client and server, unit-tested), the client rejects with a message that says *which* rule failed (too large vs unsupported type, naming the limit/extension) and uploads nothing, and the **server independently** rejects an oversize or disallowed upload (413 / 415, body naming the reason) so a hand-rolled request cannot bypass the UI (PRD 007 Req 17).
- **(PRD 007 Req 19 — single-file download)** A member with `file.download` can download the current document from the File menu and any file from the file context menu; the bytes that arrive are the workspace blob's (Markdown and images alike), saved under the file's own basename. Bulk/multi-file transfer is explicitly out (PRD 007 non-goals). A member without `file.download` sees neither entry, and any download-specific endpoint added checks that verb server-side.
- **(PRD 007 Req 20 — ETag optimistic concurrency)** A hosted read records the file's ETag and a save carries it (`If-Match`-shaped conditional write); when the blob changed on the server since that read the save is **rejected with the stored content untouched** (412 from the server) and the app prompts the user with two real choices: reload the newer server version into the editor (local edits discarded, buffer clean, subsequent saves use the new ETag) or overwrite it (an unconditional write that succeeds and re-arms the ETag). Cancelling/dismissing leaves the buffer dirty and unsaved — never a silent success. A first write of a path that does not exist yet is not rejected. `StorageProvider` in `server/providers/types.ts` grows the conditional-write capability and the Azure Blob implementation honours it (`server/providers/azure/blob.ts`) — no Azure SDK import appears outside `server/providers/azure/`.
- **(Flavor containment)** All hosted-specific behaviour stays inside `src/platform/`, `server/`, and hosted-specific components/libs. App code outside `src/platform/` must not branch on the hosted flavor except through the existing optional-capability checks (PRD 007 Req 2) — the conflict prompt, upload/download items and sidebar drag-and-drop are generic UI mounted on capability presence, not on `kind === 'hosted'`. The no-`console.*` rule applies to `src/`.
- **Pure logic is unit-tested (U295+; the current ceiling is U294).** The upload allowlist/size rule, the move/drop target validation (no folder into its own descendant, no no-op self-move, name collisions), the permission→menu-item gating, and the conflict-resolution state machine live as pure functions in `src/lib/` (extend `folderOps.ts`/`hostedWorkspace.ts` or add siblings) with vitest tests under `tests/unit/`, per `.sandcastle/CODING_STANDARDS.md`.
- **E2e coverage runs offline (E187+; the current ceiling is E186 — do not renumber, weaken or skip existing tests).** New Playwright tests in `tests/e2e/hosted.spec.ts` (plus `tests/e2e/folder-tree.spec.ts` if sidebar drag-and-drop is exercised on the shim) run against the local hosted server on 4924 with Azurite and seeded mock users only — no Azure, no external network — and observably verify at least: creating a file and a folder in the hosted sidebar, renaming and then moving an item into another folder via the context menu and via drag-and-drop, with the change visible after a reload; an upload appearing in the sidebar and reading back, and an oversize/disallowed upload rejected with its message and no blob written (the server refusing it directly too); a download producing the file's bytes; a member lacking `file.upload`/`file.download`/`file.rename` seeing neither the affordance nor a successful API call (403); and the conflict path — member A loads, member B saves, A's save is refused, Reload shows B's content, and the Overwrite branch leaves A's content on the server.
- **Standards, docs, map.** New behaviour carries citation comments (`// PRD 007 Req 18/19/20: …`) per `docs/COMMENT-FORMAT.md`; new or changed endpoints appear in `server/README.md`'s endpoint→permission table; `docs/MAP.md` is regenerated via `npm run map` if the citation set changed (the quick gate diffs it).
- **Scope guard.** No membership/custom-roles settings UI (#77), no start-page action list (#78), no permission-enforcement sweep beyond the endpoints this issue adds or extends (#79), no multi-file/bulk upload or download, no real-time co-editing, no trash or version history (PRD 007 non-goals — hosted deletes are permanent, so no UI here may promise recovery).
- Iteration used `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code), with single e2e tests run via `npx playwright test -g '<title>'` while debugging — the full e2e suite was not used as an inner loop, and any starting baseline used the quick tier only.
- `npm run validate:quick` has been run **once**, at the end, in the implementer's session, and prints `QUICK VALIDATION: ALL PASSED`.
- A summary comment from the implementer exists on issue #76.

# Spec: Server: record former unique names on the manifest and let them be reclaimed (#301)

## Goal

All acceptance criteria in issue-specs/issue-301.md are satisfied for issue #301, with evidence visible in the session: the workspace manifest carries a server-owned `formerNames: string[]` (optional on read, any client-supplied value ignored) that a rename appends the previous unique name to — a case-only change excepted — and that renaming back removes; creation and rename with another workspace's former name succeed and strip that name from the other workspace in the same request; `GET /api/workspaces` rows carry `formerNames` (empty array when none); new U-numbered tests in `tests/unit/server-workspaces.test.ts` cover each of those; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #301.

## Acceptance criteria

- **Req 1 — the field exists and is server-owned.** `WorkspaceManifest` in `src/lib/hostedWorkspace.ts` carries an optional `formerNames?: string[]`, and `validateWorkspaceManifest` accepts it: absent is valid (every pre-existing manifest still parses — this is load-bearing, since `parseWorkspaceManifest` failure is a 500 on every workspace route), a present value must be an array of well-formed unique names (the same `uniqueNameFormatProblem` the `uniqueName` field uses), and a malformed one is rejected by name like the other fields. `serializeWorkspaceManifest` round-trips it.
- **Req 1 (cont.) — a client can never set it.** On `PUT /api/workspaces/<id>/manifest` (`server/workspaces.ts` ~line 840, the rename write path) the stored `formerNames` is computed from the *existing* manifest plus the rename that just happened; whatever the request body carried in that field is discarded, exactly as `created` already is. Reads treat an absent field as `[]`.
- **Req 2 — a rename records the previous name.** When the PUT changes the unique name to a different name under `uniqueNameKey` (the PRD 020 Req 1 case-insensitive comparison), the previous name is appended to `formerNames`. A case-only change (`alpha` → `Alpha`) updates `uniqueName` as today and records nothing. A body that omits `uniqueName`, or a friendly-name-only save, records nothing.
- **Req 3 — renaming back reclaims your own name.** If the incoming name matches (case-insensitively) one of this workspace's own `formerNames`, that entry leaves the list as the name becomes current, and the name just given up is appended. After `A → B → A` the manifest reads `uniqueName: 'A'`, `formerNames: ['B']`; the list never holds the current name, and never holds the same name twice.
- **Req 4 — chains are flat.** After `A → B → C` the manifest reads `formerNames: ['A', 'B']` (append order preserved) — one flat list of names that each point at this workspace, no old→new mapping to follow, so no chain and no loop is representable.
- **Req 5 — listing rows carry former names.** `WorkspaceListing` (`src/lib/workspaceLifecycle.ts`) gains `formerNames: string[]` and the `GET /api/workspaces` loop in `server/workspaces.ts` (~line 725) fills it, `[]` when the manifest has none. The field rides the same row — and therefore the same PRD 017 listing policy and PRD 019 scratchpad filter — as `uniqueName`; nothing else about the row changes. Existing constructors of the type (e.g. the `listing()` helper in `tests/unit/workspace-lifecycle.test.ts`) are updated to keep typecheck green.
- **Req 6 — former names never count as taken.** `takenUniqueNames` keeps collecting *current* names only, so creation and rename with a name that is currently another workspace's former name succeed under exactly today's rules (format, reserved words, collision with a current name) with no warning and no confirmation. This must be asserted, not assumed.
- **Req 8 — reclaiming ends the redirect.** When a request makes a name current — the create route (`POST /api/workspaces`), the manifest PUT rename, and the scratchpad provisioning path that mints a name via `dedupeUniqueName` — any *other* workspace whose `formerNames` holds that name (compared with `uniqueNameKey`) has it removed as part of the same request, its manifest rewritten. The scan reuses the existing single manifest fan-out rather than adding a second full pass (`takenUniqueNames` already walks every manifest; extend or pair it with one helper — the PRD's non-goals rule out a per-name claim index). No new blob kind, no new prefix.
- **Req 9 — reserved words never enter the history.** The reserved-word refusal on rename is unchanged (400, `uniqueNameProblem`'s own message), and since only a name that was legitimately current can be appended, no reserved word can reach `formerNames`.
- **Req 10 — deletion takes the history with it.** History lives on the manifest and nowhere else, so `DELETE /api/workspaces/<id>` (which drops every blob under the prefix) already removes it; the implementer states this explicitly rather than adding a tombstone or an index.
- **Scope.** Server-side only; hosted (cloud) builds. No client-visible behaviour changes: no former-name resolution in `src/lib/hostedPaths.ts`, no address-bar rewrite after rename, no settings → Names display, no not-found copy change (PRD 024 Reqs 7, 11–16, 18, 19 belong to later siblings). Desktop/Tauri, dev-shim and single-file builds are untouched.
- **Req 17 — unit coverage** lands as new U-numbered tests in `tests/unit/server-workspaces.test.ts`, alongside U1054 and using that file's existing in-memory storage/`call` harness (U1234 is the current repo-wide maximum U number; test IDs must be unique repo-wide — the gate checks it). Covered: history append on rename; nothing recorded on a case-only rename; renaming back moves the name out of the history (`A → B → A`); a chain `A → B → C` yielding `['A','B']`; client-supplied `formerNames` on a PUT ignored; creation with another workspace's former name succeeding and stripping it from that workspace; rename doing the same; listing rows carrying the field (`[]` when none). Manifest-shape coverage (absent field parses, malformed rejected) sits with the other `validateWorkspaceManifest` tests.
- Changed and added code carries citation comments per `.sandcastle/CODING_STANDARDS.md`, in the `// PRD 024 Req <n>: <what and why>` style the surrounding `PRD 020 Req 1` comments already use; `docs/MAP.md` is regenerated with `npm run map` if citations changed (the gate diffs it).
- The implementer iterated with `npm run typecheck` and `npm run test:unit` (or a targeted run of the changed suite), and ran the full gate `npm run validate:quick` ONCE, right before declaring the goal met — not after every change and not as a start-of-attempt baseline — and it printed `QUICK VALIDATION: ALL PASSED`.
- A summary comment from the implementer exists on issue #301 recording what changed, the decisions taken (notably how the reclaim scan avoids a second manifest fan-out), and the gate evidence.

## Context

Everything server-side is in `server/workspaces.ts`: `takenUniqueNames` (~line 292, the one manifest fan-out that backs both collision checks), `uniqueNameTakenError` (~306), the create route (~660, mints a name for a name-only body), the listing loop (~713–770, where `uniqueName` is conditionally spread onto the row), the delete route (~781), the scratchpad provisioning path (~670 in `handleScratchpadResolve`), and the manifest PUT rename branch (~840–870, where `created` is already server-owned and the client's value ignored — the pattern `formerNames` should follow).

The manifest shape and its validator are `src/lib/hostedWorkspace.ts` (~148 `WorkspaceManifest`, ~200 `validateWorkspaceManifest`, ~294/304 parse/serialize); `uniqueNameKey`, `uniqueNameFormatProblem`, `uniqueNameProblem` and `dedupeUniqueName` are in `src/lib/workspaceNames.ts`; `WorkspaceListing` is in `src/lib/workspaceLifecycle.ts` (~27).

Read PRD `prd/024-rename-redirects.md` (Reqs 1–6, 8–10, 17 are this slice) and grep `PRD 020` before opening files — `docs/MAP.md` locates the rest. `src/App.tsx` is never read whole. Explicit non-goals from the PRD that bound the work: no per-name claim index, no name-keyed API routes or HTTP redirects, no cap on former names, no backfill for workspaces renamed before this ships, and no fix for the pre-existing unconditional-manifest-write race (a stale former name left by a race is inert by design).

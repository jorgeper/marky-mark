# Spec: Workspace storage model: blob layout, versioned manifest, permission catalog, and built-in roles (#72)

## Goal

All acceptance criteria in issue-specs/issue-72.md are satisfied for issue #72, with evidence visible in the session: each hosted workspace lives under its own per-workspace prefix in the blob container holding its files plus a versioned JSON workspace manifest (name, created/modified timestamps, members with roles, custom role definitions, everyone-access, workspace-scoped settings) with no database; a fixed permission catalog of exactly the fourteen verbs from PRD 007 Req 13 exists as pure, unit-tested logic together with the five built-in roles (Owner, Editor, Contributor, Commenter, Viewer) whose exact permission sets match Req 14 and which cannot be edited or deleted; every workspace-scoped REST operation the server exposes documents exactly one required permission from the catalog in `server/README.md`'s endpoint table and answers 403 when the caller's resolved permissions lack it, proven by offline unit and hosted e2e tests; and `npm run validate:quick` passes in the implementer's session.

## Acceptance criteria

- **Blob layout: per-workspace prefix, no database (PRD 007 Req 7).** Every workspace's data lives under a distinct per-workspace prefix inside the existing blob container (`MM_STORAGE_CONTAINER`, via the `StorageProvider` seam in `server/providers/types.ts` — no new Azure SDK imports outside `server/providers/azure/`): its Markdown/asset files plus one **workspace manifest** blob. Nothing about a workspace is stored anywhere except blobs — no database, no server-local state files. The chosen layout (prefix scheme, manifest blob name, how the manifest is kept invisible to normal file listings) is the implementer's, and is documented in `server/README.md`.
- **Versioned manifest (PRD 007 Req 7).** The manifest is a versioned JSON evolution of the local `.marky-workspace` format (see `src/lib/workspace.ts` for the ancestor): it carries an explicit schema-version field and records the workspace name, created and modified timestamps, members and their roles, custom role definitions (named subsets of the permission catalog — the *editor UI* is #77, but the manifest shape supports them now), the everyone-access setting (on/off plus its default role), and workspace-scoped settings (the PRD 002 Workspace layer slot). Parse/serialize/validate live as pure functions with no I/O (per `.sandcastle/CODING_STANDARDS.md` module rules); an unsupported schema version or malformed manifest is rejected with a clear error, never silently coerced. The schema is documented (in `server/README.md` or a doc it links).
- **Fixed permission catalog (PRD 007 Req 13).** A single pure module defines the catalog as exactly these fourteen verbs and no others: `doc.read`, `doc.edit`, `file.create`, `file.delete`, `file.rename`, `file.upload`, `file.download`, `folder.manage`, `comment.read`, `comment.write`, `workspace.settings`, `workspace.members`, `workspace.roles`, `workspace.delete`. All role definitions and endpoint requirements reference this catalog (typed — an unknown verb is a type/validation error, not a typo that passes).
- **Five built-in roles with exact sets (PRD 007 Req 14).** Built-in roles ship as named permission sets, pinned by unit tests to exactly: **Owner** = all fourteen; **Editor** = `doc.read`, `doc.edit`, `file.create`, `file.delete`, `file.rename`, `file.upload`, `file.download`, `folder.manage`, `comment.read`, `comment.write`; **Contributor** = Editor minus `file.delete`, `file.rename`, `folder.manage`; **Commenter** = `doc.read`, `file.download`, `comment.read`, `comment.write`; **Viewer** = `doc.read`, `file.download`, `comment.read`. Built-ins are not editable or deletable: any model operation or API path that mutates role definitions rejects attempts to change or remove a built-in, and a custom role cannot shadow a built-in name.
- **Permission resolution is pure and tested.** A pure function resolves (manifest, user id) → the user's permission set, honoring: explicit membership (built-in or custom role name), custom role definitions from the manifest, the everyone-access setting with its default role for non-members, explicit membership overriding the everyone-role, and empty permissions for a non-member of a workspace without everyone-access. Unit tests cover each branch, including a member whose role name resolves to nothing (fails closed — no permissions).
- **Every workspace-scoped REST operation documents and checks one permission (PRD 007 Req 13).** The server exposes workspace-scoped operations sufficient for #73/#75 to build on — at minimum: create a workspace (creator becomes Owner in the manifest), read and update a workspace's manifest, and list/read/write/delete files under a workspace's prefix. Each such endpoint declares exactly one required permission from the catalog, the mapping is visible in `server/README.md`'s endpoint table, and the server answers 403 (after the existing 401 auth guard) when the caller's resolved permissions lack the verb. Workspace creation and any deliberately pre-permission surface (e.g. listing workspace metadata, per PRD Req 11) are documented as such in the same table. The exhaustive end-to-end 403 sweep and UI affordance gating remain #79's job; this issue establishes the mechanism and applies it to every endpoint it ships.
- **Offline test coverage.** New vitest tests (U243+, under `tests/unit/`, collected by `npm run test:unit`) pin the manifest parse/serialize/version handling, the catalog, the exact built-in role sets, the built-in immutability rule, and permission resolution. New Playwright tests (E172+, in `tests/e2e/hosted.spec.ts` or a new auto-collected spec) run offline against the local mode (server + Azurite + seeded mock users, the arrangement `hosted.spec.ts` already boots) and observably verify at least: creating a workspace yields a manifest blob under its prefix with the creator as Owner; a second seeded user with a Viewer grant can read but gets 403 writing; a non-member without everyone-access gets 403 reading file content. Zero Azure resources or network beyond localhost. Existing tests are not weakened, renumbered, or skipped.
- **Standards, citations, map.** New behaviour carries citation comments (`// PRD 007 Req 7/13/14: …`); `docs/MAP.md` is regenerated via `npm run map` if the citation set changed (the quick gate diffs it); no `console.*` in `src/`.
- **Scope guard.** No hosted `Platform` implementation (#73), no New/Open/Delete workspace UI (#75), no membership or custom-roles settings UI (#77), no Graph membership picker (#74), and no UI affordance gating (#79). This issue is the data model, blob layout, and server-side permission machinery only; a minimal API surface for siblings to build on is in scope, screens are not.
- Iteration was done with `npm run typecheck` and `npm run test:unit` (plus targeted e2e runs like `npx playwright test -g 'E172'`), with the full gate run ONCE at the end — not after every small change, and not as a starting baseline (baseline with the quick pair only).
- `npm run validate:quick` passes in the implementer's session, printing `QUICK VALIDATION: ALL PASSED`.
- A summary comment from the implementer exists on issue #72.

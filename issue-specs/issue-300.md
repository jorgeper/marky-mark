# Spec: header links dont scroll well in edit mode (#300)

## Goal

All acceptance criteria in issue-specs/issue-300.md are satisfied for issue #300, with evidence visible in the session: a hosted `/<workspace>/<file>#<slug>` visit that comes up in edit mode (plain edit and split) scrolls the editor so the heading's source line is at the top of the editor viewport and the caret rests on the first character of the heading text, even when the editor was already showing another document, mounts lazily after the open, or has a remembered per-file scroll position; the same caret placement applies to `#fragment` links opened from the editor and to TOC jumps in edit mode, while read-mode landing, the miss notice and the split preview half's own click landing are unchanged; a new hosted e2e test drives the edit-mode landing; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #300.

## Acceptance criteria

- **Edit-mode deep-link landing (PRD 020 Req 19, issue #300).** In the hosted flavor, visiting `/<workspace>/<path…>/<file>#<slug>` (signed in, or through the sign-in gate) when the app comes up in edit mode lands the editor with the heading's source line as the first visible gutter line (the same few-lines tolerance the PRD 012 Req 6 tests in `tests/e2e/toc.spec.ts` use for `editorTopGutterLine`). This holds whether the editor was already mounted showing a session-restored document, mounts lazily after the linked file opens, or the file has a remembered SPEC16 §3 scroll position: the fragment wins over the remembered position. The edit branch of the landing verifies where the editor actually landed and retries per frame, bounded (the pattern and the reason documented on the mode-switch restore effect in `src/App.tsx`, near "Into edit (full or split)"), instead of one fire-and-forget `scrollToLine` dispatched before the editor holds the linked document or into a freshly created view whose initial layout swallows it.
- **Editor is the pane that lands in split view.** With edit mode and `splitEdit` on, the landing scrolls the editor (not the preview half); the preview half follows through the existing split scroll sync with the editor leading, so the heading's anchor is at or near the top of the preview half too (`previewTopAnchorLines` in `tests/e2e/helpers.ts`). No new preview scroll implementation is added.
- **Caret on the first word of the heading.** After an edit-mode heading navigation the caret is an empty selection on the heading line, placed at the first character of the heading text: after the ATX `#` run and the whitespace that follows it (for a setext heading, the start of the text line), never at column 0 in front of the markers. `.cm-activeLine` is the heading line and focus follows so typing continues there (as `goToLine` does today). This applies to three entry points: the boot fragment landing above, a `#fragment` opened from the editor (the SPEC43 §11 / SPEC11 §4 `openEditorLink` path: modifier-click, the openLink hotkey, Link ▸ Open Link), and the TOC jump in edit mode (PRD 012 Req 6 still holds: caret on the heading line, now at its text). They share one editor-handle entry point (extend `goToLine` with a column, or add a sibling such as `goToHeading`); scroll-only callers of `scrollToLine` (mode-switch restore, split sync, the split preview half's click landing) gain no caret and are not rerouted.
- **Nothing else moves.** Read-mode landing through `scrollPreviewToLine`, the PRD 020 Req 19 miss notice (an unmatched slug in edit mode still shows `heading-miss-notice`, leaves the file at the top and moves no caret), the split preview half's own `#fragment` click landing (E516), and the dev shim's `#open=` hash contract are unchanged. Desktop and single-file builds change only through the shared caret/landing code, and the existing desktop-shim TOC and fragment-link tests still pass.
- **Editor package boundary.** Any change under `editor/` follows `editor/AGENTS.md`: no imports from `src/`, new capability exposed through the `EditorSyncHandle` (or a prop seam), and the package's own suite passes (`npm test` run inside `editor/`; its `U<n>` IDs share the repo-wide register). The editor-package-boundary check in the quick gate stays green.
- **Citations.** Every new or changed behaviour carries a citation per `.sandcastle/CODING_STANDARDS.md`, e.g. `// PRD 020 Req 19 (issue #300): …` for the landing and `// PRD 012 Req 6 (issue #300): …` for the caret column. If `npm run map` output changes, the regenerated `docs/MAP.md` is committed alongside.
- **End-to-end coverage.** A new test in `tests/e2e/hosted.spec.ts` takes the next unused E-number (E573 at spec time; re-check with `grep -rhoE "test\('E[0-9]+" tests/e2e | sort` before committing) and, with the existing helpers (`signIn`, `pathWorkspace`, `signInTo`, `HEADED_DOC`, `editorTopGutterLine`, `previewTopAnchorLines`, the `mode-switch` test id and its `data-mode` attribute): puts the app in edit mode, visits the file URL with a `#<slug>` for a heading below the fold (for example `#deep-section` of `HEADED_DOC`), and asserts the editor's top gutter line is within a few lines of the heading's source line, `.cm-activeLine` has the heading's text, and the caret column is the first text character (for instance by typing one character and asserting the heading line now reads `## XDeep Section`, or by reading the selection); then repeats the visit with split on and asserts the editor lands and the preview half's top anchor is at or near the heading line. If a pure helper is added for the heading-text column, it gets a unit test in `tests/unit/<kebab-module>.test.ts` under the next unused `U<n>` (U1278 at spec time; re-check across `tests/unit` and `editor/tests`). Existing tests (E400, E514–E516, E569, E570, the `toc.spec.ts` Req 6 tests and the rest) are not weakened, renamed or renumbered; a collision after a parallel merge bumps the newer test's number.
- **Iteration economy.** The implementer iterates with `npm run typecheck` and `npm run test:unit` (plus the single targeted e2e test via `npx playwright test -g 'E573'` or whichever number it takes, and `npm test` inside `editor/` when `editor/` changed) after each change, and baselines an attempt with the quick tier only.
- **Full gate.** `npm run validate:quick` has been run ONCE in the implementer's session, right before declaring the goal met (not after every small change and not as a baseline at the start), and prints `QUICK VALIDATION: ALL PASSED`.
- **Summary comment.** A summary comment from the implementer exists on issue #300 describing the root cause found, what changed, the new test number(s), and the validate:quick result.

## Context

- Repro from the issue: a hosted URL like `/<workspace>/<file>.md#troubleshooting` opened in edit mode does not land the editor on that heading, while the preview lands fine. The reporter asks that the editor be the pane that scrolls when in editor mode, and that the cursor land on the first word of the heading.
- The landing lives in `landOnFragment` in `src/App.tsx` (grep `PRD 020 Req 19`); its edit branch does `pendingScrollLineRef.current = null; editorSyncRef.current.scrollToLine(line); return` once, with no verification. The neighbouring mode-switch restore effect (grep `Into edit (full or split)`) documents why a single dispatch into a fresh CodeMirror view is unreliable and shows the bounded verify-and-retry loop to mirror. A second likely cause: the editor's `[value]` effect in `editor/src/components/Editor.tsx` converges CodeMirror's document to the new buffer asynchronously, so the tick can run while the view still holds the previous document and `scrollToLine` clamps against the wrong line count. Reproduce with the failing e2e test first, then fix.
- Hosted landing tests (E400, E569, E570) only assert after `landInPreview`, which is why the edit-mode path has never been pinned. `E516` in `tests/e2e/fragment-links.spec.ts` pins the split preview half's click landing; leave it alone.
- `EditorSyncHandle` (`editor/src/components/Editor.tsx`, grep `goToLine`) already has `scrollToLine` and `goToLine` (scroll plus caret at line start, PRD 012 Req 6); `jumpToTocEntry` and `openEditorLinkRef` in `src/App.tsx` are the other two edit-mode heading navigations. Heading lines come from `headingAnchors` in `src/lib/shareLinks.ts` over `parseSections` (`src/lib/sectionModel.ts`), which also carries the heading title; the text column is derivable from the source line.
- `getByTestId` is the e2e selector convention; class locators stay for CodeMirror's own DOM (`.cm-line`, `.cm-activeLine`, `.cm-content`). The hosted suite's helpers and fixtures are at the top of `tests/e2e/hosted.spec.ts` and in `tests/e2e/helpers.ts`.

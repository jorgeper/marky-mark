# Spec: comments should work in editor (#341)

## Goal

All acceptance criteria in issue-specs/issue-341.md are satisfied for issue #341, with evidence visible in the session: a comment or highlight whose quoted text crosses inline markdown syntax (bold, emphasis, inline code, link text, escapes, soft line breaks) paints in the CodeMirror editor in plain edit and split edit over the matching source span, while absent or ambiguous quotes still never mispaint; a ⌘/Ctrl modifier-click on a painted comment range in the editor activates it (comments pane open, card active) the same way a modifier-click opens a link, and a plain click only places the caret; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #341.

## Acceptance criteria

### Rendering: the editor paints what the preview paints

- Editor-pane painting no longer requires the anchor's `exact` quote to occur byte-for-byte in the markdown source. A record (comment or highlight) whose rendered quote spans inline syntax paints in the editor, in plain edit and in split edit, with the same `.mm-hl` decoration, `data-cid`, `data-color`, `active`/`flash`/`ghost` treatment it gets today. Covered at minimum: `**strong**` / `*em*` / `_em_` markers inside or at the edges of the quote, inline `` `code` `` backticks, link text (`[text](url)`, with the rendered-links view on and off), backslash escapes, a soft line break inside one paragraph, and a quote beginning on a heading / list / blockquote line after its block prefix.
- The painted source span runs from the first through the last visible character of the match, so syntax that sits between them (a closing `**`, a link's `](url)`) is painted along, and syntax before the first or after the last visible character is not. The decoration is never placed on a visibly wrong range.
- The skip rule survives: a quote that has no visible-text occurrence in the source, or several occurrences with no strictly best prefix/suffix agreement, is not painted (never guessed). A unique occurrence, or one occurrence strictly best by stored context, paints. E426's `ambiguous` entry still does not paint; its `absent` entry (`bold prose` across a `**` marker) now does, and E426 plus the `mapHighlightsToSource` unit tests in `tests/unit/anchoring.test.ts` are updated to the new contract (this is the PRD 023 Req 21 "updated to the new UX, not deleted" precedent, not a weakening — the comments in the fixture say so).
- Because the smart-edit caret context (Delete Comment, recolor, Remove Highlight), the pane's activation flash and the two-way sync all read the painted ranges, they work over such records without further wiring; at least one e2e asserts pane-to-editor activation (card click → editor decoration `.active`/flash) on a formatted-text comment in plain edit.
- The visible text and its offset map are built once per mapping pass, not once per record (the pass runs on the existing 200 ms debounce for every comment in the document).

### Clicking: the link gesture activates a comment, a plain click only places the caret

- In the editor (plain edit and split edit), a modifier-click on a painted **comment** range — ⌘ on macOS / Ctrl elsewhere, the exact `metaKey || ctrlKey` predicate `linkViewMousedown` uses for SPEC43 §11 — activates the record: the comments pane opens if closed (persisted, as today), the card is active and scrolled into view, the editor decoration carries `.active`, and in split edit the preview marks go active. Overlapping records still resolve through `pickHitRecord` (comment over highlight, innermost comment wins).
- A modifier-click on a painted **highlight** range gives the `.active` cue only: no pane effect, no card (PRD 023 §18 unchanged).
- A plain click on a painted range places the caret and does nothing else: no activation, no `.active` change, no pane opening, no card change. E425, E427 and E444 are updated to the modifier gesture, and a new e2e proves the plain click is inert on a comment range in plain edit while the caret lands where clicked.
- A modifier-click on a painted range leaves the editor selection as it was: no caret move and no second cursor. (CodeMirror's default `clickAddsSelectionRange` is ⌘ on mac / Ctrl elsewhere, so the handler must claim the mousedown the way the link handler does.)
- When a modifier-click lands on text that is both a link and a painted range, exactly one thing happens: the link opens (the SPEC43 §11 handler keeps precedence) and no record activates.
- While the modifier is held, painted ranges show `cursor: pointer`, riding the existing `mm-link-modifier` root class from `linkModifierCue` (styles in `editor/styles.css`).
- The modifier-click handler is a pure factory in the editor package testable without a browser (the `linkViewMousedown` / U1159 shape): a unit test proves the modified click reports the covering ids and claims the event, and the plain click reports nothing and claims nothing.

### Contract, docs, hygiene

- The `onHighlightClick` seam doc in `editor/src/components/Editor.tsx` (and any package README text describing it) states the new gesture; the stale "the click itself is never claimed, so caret placement always stands" wording is gone.
- PRD 023 §18 carries an `**Amended (issue #341, 2026-09-07)**` blockquote (the §14–15 precedent from issue #331) recording both changes: editor activation by modifier-click with plain click as caret placement, and visible-text mapping superseding PRD 022 Req 12's "exact-quote match against the source" while keeping its skip-over-mispaint rule.
- Every new or changed behaviour site carries an `// Issue #341:` citation (the issue #308 precedent); `docs/MAP.md` is regenerated by `npm run map` and committed if it changed.
- New tests take the next unused IDs on the shared registers at implementation time (E589+, U1306+ as of this spec; verify with a grep first — parallel branches move them). No existing test is deleted, skipped or weakened; the three rewrites above change the gesture and the E426 expectation only.
- Iterate with `npm run typecheck` and `npm run test:unit` (or targeted tests: `npx playwright test -g 'E426'`, `npx playwright test -g 'E425'` …). Baseline an attempt with the quick tier only.
- `npm run validate:quick` has been run ONCE in the implementer's session, right before declaring the goal met (not after each change, not as a starting baseline), and printed `QUICK VALIDATION: ALL PASSED`.
- A summary comment from the implementer exists on issue #341 (what changed, decisions, tests added/updated, files, gate result).

## Context

Both halves already exist as seams; this issue changes their rules, not their shape.

- **Painting.** `src/App.tsx` (`// PRD 022 Req 12` block near `editorHighlights`) maps records to source on a 200 ms debounce through `mapHighlightsToSource` in `src/lib/anchoring.ts`, which requires `anchor.exact` (rendered plain text) to occur verbatim in the canonical source via `allIndexes`, then disambiguates with `contextScore`. That is why anything with inline syntax never paints. The editor package already exports the visible-text machinery the fix needs: `visibleTextForRange`, `findNormalized` / `countNormalized` / `findNormalizedNth`, and `sourceRangeForVisibleMatch(source, fromLine, toLine, needle, nth)` in `editor/src/lib/selectionMap.ts` (built on `stripInline`, fence-aware). `src/lib/annotationMenu.ts` is the precedent for a `src/lib` module importing them from `@marky-mark/editor` (source→rendered direction, PRD 023 §19). Rendered plain text is `getDocText` in `src/lib/domtext.ts`; the editor side receives CANONICAL offsets and maps them through the table grid itself (`docHighlightRanges` in `editor/src/components/Editor.tsx`).
- **Clicking.** `highlightsExt` in `editor/src/components/Editor.tsx` reports covering ids on a mousedown+mouseup pair without claiming the event; `App.tsx` `activateFromHit` → `pickHitRecord` (`src/lib/markHit.ts`) → `handleMarkClick` opens the pane and activates the card. The gesture to copy is `linkViewMousedown` and `linkModifierCue` in `editor/src/components/linkView.ts` (registered as `linkOpenExtension` in the Editor's extension list, before `history()`); its cursor cue is the `.mm-link-modifier` block in `editor/styles.css`. The package never sees the comment store (`editor/AGENTS.md`): keep the kind rule in the app.
- **Tests to know.** `tests/e2e/comments.spec.ts`: E424–E427 (editor paint + click), E442–E445 (`seedOverlapDoc`, overlap + plain-edit click + card→editor flash), E561–E563 (issue #308, comment tint + View ▸ Editor Highlights), E454/E456/E457 plain-click the decoration only to place the caret (they keep working). Helpers `addComment` / `addHighlight` in `tests/e2e/helpers.ts` author over a preview phrase. Unit: `tests/unit/anchoring.test.ts` (`PRD 022 Req 12 editor-pane highlight mapping`, U1107+), `editor/tests/link-spans.test.ts` U1159 for the handler-factory pattern.
- **Out of scope.** The preview's plain-click activation is unchanged; no new setting; no change to the comment format; PRD 022's Non-goal that cross-block quotes may still skip stands. Issue #298 (comment handling inside the reusable editor package) needs its own PRD and is not this issue.

# Spec: Releaser lane: classify sandcastle:release issues, issue-body format, preflight guards (#58)

## Goal

All acceptance criteria in issue-specs/issue-58.md are satisfied for issue #58, with evidence visible in the session: `npm run sandcastle` classifies open `sandcastle:release` issues into a releaser lane driven by `.sandcastle/release-prompt.md` and records releaser runs in `.sandcastle/logs/timings.jsonl`; the machine-parseable release-issue body format (version, platforms, changelog entry) is documented in `.sandcastle/release-prompt.md`; the preflight guards (malformed body → explanatory comment and no tree changes, version ≤ newest tag → refusal comment, abandoned drafts → report listing exact `gh release delete` commands) exist as pure logic covered by passing unit tests; and `npm run validate:quick` has passed in the implementer's session with a summary comment posted on issue #58.

## Acceptance criteria

- **Label and listing.** A `sandcastle:release` label is defined in `.sandcastle/github.mts` alongside the existing `TRIGGER_LABEL_DEFS` entries (so `ensureLabelsExist` creates it), and a listing helper for open issues carrying it exists, mirroring `listRequiresPrdIssues`.
- **(R4) Lane wiring.** `.sandcastle/main.ts` contains a release-lane runner modeled on `runPrdLane`: it lists open `sandcastle:release` issues, classifies each with pure logic (see below), and for a runnable issue dispatches an agent named `releaser` with `promptFile: "./.sandcastle/release-prompt.md"`, wrapped in `timed("releaser", { issue: <n> }, …)`. The phase string equals the agent name — that is what lets `control-panel/server.js` `parseRuns` (phase === role match, ~line 122) pair the `timings.jsonl` entry with `sandcastle-issue-<n>-releaser.log` and render the lane like implementer/reviewer lanes.
- **Pure classification module.** A `.sandcastle/release-lane.mts` (pure, no `gh`/fs calls — same convention as `prd-lane.mts`, with the impure runner staying in `main.ts`) exports the issue-body parser and a classify function returning discriminated actions (at minimum: malformed body, out-of-order version, drafts-to-report, proceed).
- **(R5) Body format + parse guard.** `.sandcastle/release-prompt.md` exists and documents the structured, machine-parseable issue-body format — version (strict semver, prerelease id kept), platforms (`mac` | `windows` | `both`), and the changelog entry — as the contract that the future `/new-release` skill (PRD R3) and publish close-out (PRD R16) consume. The parser accepts exactly that format; a malformed body (missing/invalid version, unknown platform, missing changelog entry) classifies to an action whose runner posts one explanatory comment on the issue and ends the lane with no changes to the working tree.
- **(R6) Ordering guard.** A version older than or equal to the newest existing `v*` tag classifies to a refusal action: the runner comments why and stops. The comparison is prerelease-aware (reuse or mirror `parseVersion`/`compareVersions` in `scripts/updater-manifest.mjs`); a unit test reproduces the #19 incident shape (cutting 0.4.0-alpha.4 when v0.4.0-alpha.5 exists → refused).
- **(R7) Draft report.** Preflight builds a report of abandoned draft releases (the repo has two real ones today: v0.3.0-alpha.1, v0.2.0-alpha.3) listing the exact `gh release delete <tag>` command per draft, and the runner posts it as an issue comment. No code path in the lane deletes a release.
- **No duplicate guard comments.** Guard/report comments carry a recognizable marker line (mirror the `PARENT_CLOSE_MARKER` pattern in `prd-lane.mts`) and the runner checks existing comments before posting, so re-classifying the same unchanged issue on a later loop pass does not spam the thread.
- **Unit tests that actually run.** The parser, classifier, ordering guard, and draft-report builder are covered by tests discovered by `npm run test:unit`. Note: colocated `.sandcastle/*.test.mts` files are NOT picked up (vitest `include` is `tests/unit/**/*.test.ts`), so either place the tests in `tests/unit/` importing from `.sandcastle/release-lane.mts` (precedent: `tests/unit/control-panel-runs.test.ts` imports `control-panel/server.js`) or extend the vitest include — tests must demonstrably run in the suite. New tests follow CODING_STANDARDS: `U<n>:` titles continuing the existing sequence, never renumbering existing tests. A colocated `.sandcastle/release-lane.test.mts` may exist additionally for template symmetry, but does not substitute.
- **Scope held.** The cut itself (PRD R8–R13: release branch, version bump, tag, CI watch, draft verify) is NOT implemented — the prompt/lane stops after preflight, and the prompt says the cut lands in a follow-up. No `sandcastle:release` issues exist yet, so no live release-issue run is expected as evidence; the evidence is the wiring plus passing tests.
- **Verification.** Iterate with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code) after each change; run `npm run validate:quick` ONCE, right before declaring the goal met — not after every small change and not as a starting baseline — and it prints `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- **Reporting.** A summary comment from the implementer exists on issue #58.

## Context

Parent #25 and `prd/008-releaser-agent.md` define the full flow; this issue is R4–R7 only. The PRD lane is the pattern to copy end to end: pure classification in `.sandcastle/prd-lane.mts` (unit-testable, GitHub-derived state), impure runner `runPrdLane` in `.sandcastle/main.ts` (~line 573), `gh` wrappers in `.sandcastle/github.mts` (labels at ~line 252). Timing plumbing is `.sandcastle/timing.mts` (`timed()` appends to `.sandcastle/logs/timings.jsonl`); the control panel's lane matching is `control-panel/server.js` `parseLogName`/`parseRuns`. Prerelease-aware semver lives in `scripts/updater-manifest.mjs` (`parseVersion`, `compareVersions`) — note `.sandcastle/` is outside `tsconfig.json`'s include, so importing an untyped `.mjs` there is unremarkable, but a test in `tests/unit/` importing `.sandcastle/*.mts` will pull that file into `npm run typecheck`. Release issues carry only `sandcastle:release` (the `/new-release` skill, a later issue, is the only filer) — keep the lane's listing label-scoped like the PRD lane so plain-`sandcastle` implement classification never sees them. Comment style in `.sandcastle` code cites the PRD (`prd/008` R-numbers), not `SPEC<n>`.

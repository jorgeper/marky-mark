# Spec: Rescind invitations: remove a pending guest from Management → People (#193)

## Goal

All acceptance criteria in issue-specs/issue-193.md are satisfied for issue #193, with evidence visible in the session: `DELETE /api/admin/invitations/<userId>` exists behind `deployment.admin` and only deletes guests whose `externalUserState` is `PendingAcceptance` (409 otherwise), Management → People shows a confirm-guarded destructive **Rescind** action on Pending rows that removes the row and scrubs the rescinded id from every workspace manifest, the flow (success, membership cleanup, non-admin 403, accepted-guest refusal) is e2e-tested against the mock directory, both hosting guides and the route docs cover the new `User.ReadWrite.All` permission and route, and `npm run validate:quick` passes in the implementer's session.

## Acceptance criteria

- `DELETE /api/admin/invitations/<userId>` exists in `server/admin.ts` behind the same `deployment.admin` guard as `POST /api/admin/invitations`. Before deleting, the server asks the directory for the target: unless it is a guest with `externalUserState = PendingAcceptance` (the `pending` flag Req 33 already surfaces), it refuses with **409** and a clear message. Members, accepted guests, and admins are never deletable from the app.
- On success the server deletes the user via Graph `DELETE /v1.0/users/{id}` **as the signed-in admin** over the existing OBO exchange (`server/providers/azure/obo.ts` scope set grows to include `User.ReadWrite.All`). A Graph refusal surfaces through the existing 502-with-`error.code` pathway (see the invite flow in `server/providers/azure/graph.ts`). No token ever appears in a log line or response.
- In the same operation, any workspace membership recorded for the rescinded id (e.g. the role-at-invite grant from PRD 017 Req 30) is removed from every workspace manifest — the admin routes already read all manifests (`server/admin.ts` workspace listing) — so no manifest is left with a dangling unresolvable member. A row for the rescinded id no longer appears in any workspace's members after the operation.
- Management → People (`src/components/ManagementPanel.tsx`): rows carrying the Pending badge offer a destructive-styled **Rescind** action with a confirm step that names the guest's email; on confirm + success the row disappears from the list. Non-pending rows never offer it. The client call lives beside the invite call in `src/platform/hostedAdmin.ts`.
- The mock directory (`server/providers/mock/directory.ts`) supports deleting a pending guest, and desktop-shim e2e tests (numbered `E<n>`, in the relevant `tests/e2e/` suite) cover offline: rescind from Management → People removes the row; the workspace-membership cleanup; a non-admin gets 403; rescinding an accepted guest is refused (409).
- The unit-testable pieces (e.g. eligibility/refusal decision, manifest scrub) have `vitest` coverage in the existing unit lanes, and new behaviour carries `// SPEC<n> §x.y:`-style citations consistent with `.sandcastle/CODING_STANDARDS.md`.
- Docs: `docs/HOSTING-AZURE.md` § 1.5 and the matching permission steps in `docs/HOSTING-AZURE-PORTAL.md` add **`User.ReadWrite.All`** (delegated, admin consent) in the existing § 1.5 style, explaining what it powers; `docs/AUTHENTICATION.md` § "Adding people" mentions rescinding; the route table in `server/README.md` documents `DELETE /api/admin/invitations/<userId>`.
- If the collected desktop-shim e2e count grew, `E2E_TEST_FLOOR` in `scripts/validate.mjs` is re-pinned to the new count.
- Iteration used `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code, e.g. `npx playwright test -g '<title>'`) after each change; the full gate `npm run validate:quick` was run **once**, right before declaring the goal met — not after every small change and not as a starting baseline — and passed, printing `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- A summary comment from the implementer exists on issue #193.

## Context

PRD 017 (`prd/017-deployment-admins.md`) explicitly non-goaled revoking invitations; this issue adds it. The invite flow this mirrors is issue #190's `POST /api/admin/invitations` in `server/admin.ts` (guard, Graph-as-caller via OBO, 502 mapping) — grep `Req 29`/`Req 33` citations. The Pending badge and `pending` flag come from Req 33 (`server/providers/azure/graph.ts` `USER_SELECT`, `src/components/ManagementPanel.tsx`). The mock directory already has invitation levers (`server/providers/mock/directory.ts`) plus local-only test hooks under `/api/directory/invitations/` in `server/app.ts` — the new admin route is a real route, not a test hook, and must also work on Azure. Manifest reads/writes go through `providers.storage` as in `server/admin.ts`'s workspace listing. Destructive-action styling and confirm patterns already exist in the management surfaces — match them.

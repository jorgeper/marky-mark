# Spec: comments dont render the highlight in edit mode (#308)

## Goal

All acceptance criteria in issue-specs/issue-308.md are satisfied for issue #308, with evidence visible in the session: a comment record (no marker color) paints its anchored range in the CodeMirror editor in plain edit and split edit with the fixed comment tint, and a new e2e test proves it; View carries a hotkey-less "Editor Highlights" checkbox row backed by a new persisted setting that defaults on, and turning it off removes every editor-pane highlight decoration live while leaving the preview's marks and the comments pane untouched; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #308.

## Acceptance criteria

- **Comments paint in the editor.** With comments enabled, a comment record (kind `comment`, no color) whose anchor quote occurs exactly once in the source paints as an `.mm-hl` background decoration covering exactly the quote, in both plain edit (split off) and split edit, using the fixed comment tint (computed background is not transparent). Highlight records keep their per-color paint (E424–E427 unchanged). If the implementer finds a concrete defect in the current path (`src/App.tsx` editor-highlight effect, `mapHighlightsToSource` in `src/lib/anchoring.ts`, `highlightsExt` in `editor/src/components/Editor.tsx`, or the `.mm-hl` rules in `editor/styles.css`) that keeps a comment record from painting, it is fixed with a cited comment; if none is found, the criterion is met by the new test below proving the behaviour.
- **A new persisted setting exists.** `Settings` gains a boolean key (suggested name `editorHighlights`) with default `true`, a `bool` parser entry, and a scope tag in `SETTINGS_SCOPES` (suggested `'U'`, the `lineNumbers` precedent — a reader's preference), each carrying an `// Issue #308:` citation. Unit tests in `tests/unit/settings.test.ts` cover the default and that a stored `false` round-trips.
- **A new command and View row exist.** `CommandId` in `src/lib/commands.ts` gains `toggleEditorHighlights`; `buildViewItems` in `src/lib/menuSpec.ts` emits a checkbox row labelled `Editor Highlights`, checked when the setting is on, with no accelerator, placed inside the `commentsEnabled` block directly after the Next/Previous Comment rows (so the master switch removes it along with the rest of the comments UI). `ViewMenuState` gains an OPTIONAL field for it whose absence reads as on, so every existing frozen menu fixture stays valid (the `openOnly` / `showNonMd` precedent). The desktop native menu and the hosted in-app menu (`src/lib/appMenu.ts`, which already iterates `buildViewItems`) both show the row. A unit test in `tests/unit/menu-spec.test.ts` (next unused `U` number; the highest today is U1268) asserts label, checkbox state tracking, no accelerator, placement after `prevComment`, and absence when `commentsEnabled` is false.
- **The command flips the setting live.** The App command handler for `toggleEditorHighlights` toggles the persisted key through `updateSettings` (the `toggleLineNumbers` shape at `src/App.tsx` ~5043). The PRD 022 Req 12 editor-highlight effect in `src/App.tsx` (~6199) treats the setting as an additional gate: off ⇒ `setEditorHighlights(null)` so no `.mm-hl` decoration remains in the editor; on again ⇒ the ranges repaint without a remount or mode switch. The preview's `mark.hl` painting, the comments pane, comment navigation, and the comments master switch are not affected by this setting.
- **E2E coverage.** New desktop e2e tests in `tests/e2e/comments.spec.ts` (next unused `E` numbers; the highest today is E554) using existing helpers (`addComment`, `openSettings`/`saveSettings` for split off, `Control+e`, `getByTestId('editor')`): (a) a comment record paints in plain edit and in split edit with a non-transparent background and the joined `.mm-hl` text equals the quote; (b) dispatching `toggleEditorHighlights` via `window.__mmDispatch` removes all `.mm-hl` decorations from the editor while the preview (split edit) still shows `mark.hl`, and dispatching again restores them; (c) the off state survives a reload (persisted setting). Test IDs follow `.sandcastle/CODING_STANDARDS.md`; no existing test is weakened or renumbered.
- **Citations and map.** Every new or changed behaviour site carries an `// Issue #308:` citation (this issue has no SPEC/PRD section of its own). If `npm run map` changes `docs/MAP.md`, the regenerated file is committed; the quick gate diffs it.
- **Iteration and gate.** The implementer iterates with `npm run typecheck` and `npm run test:unit` (plus targeted e2e via `npx playwright test -g '<title>'`), baselining an attempt with the quick tier only, and runs `npm run validate:quick` ONCE right before declaring the goal met; it prints `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- **A summary comment from the implementer exists on issue #308** describing what changed, the new test IDs, and the gate result.

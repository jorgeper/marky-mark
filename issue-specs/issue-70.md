# Spec: Hosted backend scaffold: server/, provider seams, and Azurite/mock local dev mode (#70)

## Goal

All acceptance criteria in issue-specs/issue-70.md are satisfied for issue #70, with evidence visible in the session: a Node backend in `server/` serves the built SPA and a REST API from one origin and starts locally in dev mode with a single npm script; the backend reaches auth, storage, and user directory only through three provider interfaces with Azure implementations (Entra ID, Blob Storage, Microsoft Graph) and no Azure SDK import outside the Azure provider modules; a local dev mode backs storage with Azurite and auth + directory with seeded mocks, covered by hosted-flavor tests that run inside `npm run test:e2e` with no Azure resources or network access; and `npm run validate:quick` passes in the implementer's session.

## Acceptance criteria

- **Server scaffold exists (PRD 007 Req 1).** A TypeScript Node backend lives in `server/`, serving both the built SPA (from the existing `npm run build` output) and a REST API (e.g. under `/api/`) from one origin — same host and port. A single npm script in the root `package.json` (name the implementer's choice, e.g. `server:local`) starts it locally in local dev mode, including whatever it depends on (Azurite, a built SPA) — no manual prerequisite steps. In production mode the server starts under plain `node` on current Node LTS with all configuration supplied via environment variables, so the same code deploys unchanged to Azure App Service (Linux); this is demonstrated by documentation plus typecheck, not by a live Azure deployment (the full hosting guide is PRD Req 23, a later issue).
- **Provider seams are real (PRD 007 Req 3).** The server defines three provider interfaces — auth (token validation/sign-in), storage (files + metadata), and user directory (search, display names, avatars) — and all request handling reaches vendor services only through them. Azure implementations exist for each (Entra ID, Blob Storage, Microsoft Graph) and are selectable via configuration. Verifiable seam check: a grep for Azure SDK imports (`@azure/`, MSAL, Microsoft Graph client packages) over `server/` and `src/` hits only inside the dedicated Azure provider modules. The Entra ID and Graph implementations are verified by `npm run typecheck` and unit tests only — no cloud calls in the session.
- **Local dev mode works offline (PRD 007 Req 4).** A local development mode wires the storage provider to Azurite (added as a devDependency and launched locally, with the Blob Storage provider pointed at the emulator's well-known dev endpoint) and wires the auth + directory providers to mocks with seeded test users. The mode selection (env var or similar) is documented in a `server/README.md` or equivalent doc, alongside the env vars each mode needs.
- **Hosted-flavor e2e coverage runs inside `npm run test:e2e`.** New Playwright tests in a new `tests/e2e/*.spec.ts` file (auto-collected by the config glob), numbered from the next unused ID (E159+), boot the hosted server in local dev mode — server, Azurite, and any SPA build arranged by the suite itself (Playwright `webServer` entries or global setup), on a port that doesn't clash with the existing shim server's 4923 — and observably verify at least: an unauthenticated API request is rejected (401); sign-in as a seeded mock user succeeds; a file written through the API reads back with the same content (a real round-trip through Azurite); user-directory search returns seeded mock users; and the server serves the SPA's HTML at `/`. All of this with zero Azure resources and no network beyond localhost. Existing tests are not weakened, renumbered, or skipped.
- **Unit tests cover the seam-level logic.** New vitest tests (U216+, under `tests/unit/`, collected by `npm run test:unit`) cover provider-agnostic server logic worth pinning — e.g. provider selection/config parsing and the mock directory/auth behavior — per the conventions in `.sandcastle/CODING_STANDARDS.md`.
- **Typecheck covers the server.** `npm run typecheck` passes and includes the new `server/` TypeScript (root tsconfig include, project reference, or an equivalent wired into the same script — not a separate command the gate never runs).
- **Standards and map.** New behaviour carries citation comments per `.sandcastle/CODING_STANDARDS.md` (`// PRD 007 Req <n>: …` for this work), and `docs/MAP.md` is regenerated via `npm run map` if the citation set changed (the quick gate diffs it).
- **Scope guard.** `src/platform/` gains no hosted `Platform` implementation and app code outside `server/` and `tests/` is not restructured — PRD Req 2 (the hosted front end) is a sibling issue; the SPA the server serves is the existing app as built today.
- Iteration was done with `npm run typecheck` and `npm run test:unit` (plus targeted e2e runs like `npx playwright test -g 'E159'`), with the full gate run ONCE at the end — not after every small change, and not as a starting baseline (baseline with the quick pair only).
- `npm run validate:quick` passes in the implementer's session, printing `QUICK VALIDATION: ALL PASSED`.
- A summary comment from the implementer exists on issue #70.

# Spec: loading indicator after login is tiny (#316)

## Goal

All acceptance criteria in issue-specs/issue-316.md are satisfied for issue #316, with evidence visible in the session: the hosted boot frame (`hosted-booting`) shows a visibly larger, more modern loading indicator styled by its own dedicated CSS rule rather than the 9px `.search-scanning-spinner` sizing; the indicator stays minimal (app background, one element, no text, no theme colour literals, tokens only), keeps its late fade-in, remains `role="status"` with the existing `aria-label` and `data-testid="hosted-booting"`, and honours `prefers-reduced-motion`; the search-panel and workspace-switcher spinners are unchanged in size; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #316.

## Acceptance criteria

- The loading indicator on the hosted boot holding frame (`.hosted-booting`, rendered in `src/components/HostedSignIn.tsx` around line 627) is visibly larger than today: its rendered box is at least 28px square (the current spinner is 9px with a 2px border). A dedicated class (e.g. `.hosted-booting-spinner` owning its own size, stroke and shape) styles it; it no longer inherits its 9px size from `.search-scanning-spinner`.
- The indicator looks more modern and slick while staying minimalistic: one element, no label text, no logo, no card or panel behind it, on the plain app background. A thin-stroke ring with an accent-coloured arc (`--mm-accent`) over a faint track (e.g. `color-mix` of `--mm-fg` or `--mm-border`) with a smooth ease-in-out or linear spin is the intended direction; the implementer may choose a comparably minimal design, but it must remain a single element with no text.
- The late fade-in is preserved: the indicator is invisible for the first ~400ms of the hold and fades in only if the wait outlasts that beat (the existing `mm-boot-hold-in` behaviour), so a quick boot still shows one still frame and then the workspace.
- Under `@media (prefers-reduced-motion: reduce)` the indicator does not spin continuously (it may pulse gently in opacity or sit static), extending the app's single existing reduced-motion carve-out in `src/styles.css` (around line 1145) rather than adding a second unrelated one, unless the existing block's scope comment says otherwise, in which case a scoped second block with a citation comment is acceptable.
- The frame's contract is unchanged: `data-testid="hosted-booting"`, `role="status"`, `aria-label="Opening Marky Mark"`, `aria-hidden="true"` on the spinner element, still mounted outside `.theme-root`, still `position: fixed; inset: 0; z-index: 130` covering every App surface. The existing e2e tests in `tests/e2e/hosted.spec.ts` that assert on `hosted-booting` continue to pass unmodified (their assertions must not be weakened).
- The search panel spinner (`.search-scanning-spinner` in `src/components/SearchPanel.tsx`) and the workspace switcher loading spinner (`src/components/WorkspaceSwitcher.tsx`) keep their current 9px size and appearance; only the boot frame's indicator changes.
- All new CSS follows `docs/STYLE-GUIDE.md` and passes the style lint: no raw colour literals in chrome rules (tokens only, contract-variable fallbacks allowed as already used in `.hosted-booting`), every `var(--mm-…)` defined, `border-radius` via a scale token (`--mm-radius-pill`), no literal `font-size`/`box-shadow`. Both light and dark surfaces read correctly because colours derive from tokens.
- Changed behaviour carries a citation comment per `.sandcastle/CODING_STANDARDS.md` (e.g. `PRD 020 Req 5+6 (issue #316): …` on the new CSS rule and, if touched, the TSX element).
- One e2e assertion covers the size: an existing or new test in `tests/e2e/hosted.spec.ts` (E-numbered per the suite's convention) asserts that while `hosted-booting` is visible its spinner element's bounding box is at least 28px wide and tall. If the spec's e2e count floor or numbering conventions require a new number, follow them.
- During the attempt the implementer iterates with `npm run typecheck` and `npm run test:unit` (or the single targeted e2e test via `npx playwright test -g '<title>'`), baselining with the quick tier only; the full gate `npm run validate:quick` has been run ONCE, right before declaring the goal met, and prints `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- A summary comment from the implementer exists on issue #316 describing what changed (before/after size and design), and how it was verified.

## Context

The "spinny thing after login" is the hosted boot holding frame from PRD 020 Req 5+6 (issue #253): `src/components/HostedSignIn.tsx` ~line 624–630 renders `<div className="hosted-booting">` with `<span className="search-scanning-spinner hosted-booting-spinner">`. The size comes entirely from `.search-scanning-spinner` in `src/styles.css` (~line 2767: 9px, 2px muted border, `mm-search-spin` 0.8s), which was designed for the search panel's caption-sized status line and merely borrowed here. `.hosted-booting-spinner` (~line 2936) currently adds only the delayed fade-in (`mm-boot-hold-in` 120ms after 400ms). The cleanest change is to stop reusing the search class on the boot frame (or override every sizing property) and give `.hosted-booting-spinner` its own full rule, keeping the keyframes and the fade-in. The frame mounts outside `.theme-root`, so only the contract variables with fallbacks (`--mm-bg`, `--mm-fg`, `--mm-fg-muted`, `--mm-border`, `--mm-accent`, see ~line 2905) are reliably defined there; use those with fallbacks as `.hosted-booting` already does. E2E coverage of the frame lives in `tests/e2e/hosted.spec.ts` (~lines 395, 479–485, 6527–6679); the `/api/me` route-hold pattern at ~line 470 is the way to keep the frame on screen long enough to measure it. Style rules: `docs/STYLE-GUIDE.md` Do/Don't list; citation format: `.sandcastle/CODING_STANDARDS.md`.

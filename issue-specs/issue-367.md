# Spec: Live control channel: WebSocket bridge, agent-control toggle, and MCP session tools (#367)

## Goal

All acceptance criteria in issue-specs/issue-367.md are satisfied for issue #367, with evidence visible in the session: under `MM_AGENT_BRIDGE=1` the server accepts an authenticated, workspace-bound WebSocket upgrade that registers the tab with the existing `createSessionBroker` (session torn down on close, takeover on a second tab via `session_replaced`); with the `agentBridge` setting on, a hosted tab renders an agent-control toggle (`agent-control-toggle`) whose opt-in opens that channel and drives the issue #366 executor, shows a persistent `agent-control-indicator` while opted in, and turns off when another tab takes over or the channel closes; `POST /api/mcp` registers the nine session tools of PRD 027 Req 7 dispatching through the broker, answering `no_controlled_session` when the token's workspace has no controlled tab while file tools stay unaffected; with the setting off no toggle, indicator or WebSocket exists; new unit tests and hosted-lane e2e tests (toggle/indicator, takeover, session tools failing then succeeding, loose sub-second round trip) prove it; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #367.

## Acceptance criteria

### Server: the WebSocket control channel (PRD 027 Req 9, Req 10)

- A new server module (e.g. `server/agentBridgeSocket.ts`) owns the upgrade route for the control channel, on a workspace-scoped path such as `GET /api/workspaces/<id>/agent-session` (HTTP `Upgrade: websocket`). It exists only when the agent-bridge flag is on: with `MM_AGENT_BRIDGE` off no upgrade handler is attached for the path, the upgrade attempt is refused (the socket is closed without a `101`) and no bridge module code runs on that request.
- The channel authenticates with the user's **existing session**: the token arrives as the same `Authorization: Bearer` header or, since a browser `WebSocket` cannot set headers and an upgrade is a same-origin GET, the existing `?access_token=` query form already accepted by `sessionToken` in `server/app.ts`. The token is validated through `providers.auth.validateToken`; a missing, invalid or expired token is refused (no `101`, a `401`-style refusal on the raw socket). Membership is checked through the existing `requirePermission` path for the workspace in the URL (a member who may open the workspace, i.e. `doc.read`); a non-member is refused. The route is added to `WORKSPACE_ROUTE_PERMISSIONS` in `server/workspaces.ts` so the drift test covers it.
- On a successful upgrade the connection is registered with the ONE app-wide broker (`createSessionBroker` from `server/agentBridge.ts`, created once per `createApp` and shared with the MCP endpoint) as the workspace's controlled session, via a `SessionTransport` whose `send` writes an encoded `ServerToTabMessage` text frame and whose `close` closes the socket. Inbound text frames are decoded with `decodeBridgeMessage`; a valid `TabToServerMessage` is handed to the session handle's `deliver`, a malformed frame is ignored (never a crash, never a log line carrying the payload). Socket close or error calls the handle's `close`, so the workspace has no controlled session afterwards.
- Takeover is the broker's: a second successful upgrade for the same workspace makes the broker send `session_replaced` to the first socket and close it; the second socket is the live session.
- The WebSocket server side is either the `ws` package added to `dependencies` (not `devDependencies`, since `node server/index.ts` needs it at run time; `package-lock.json` updated, and the payload table in `docs/HOSTING-AZURE.md` that says the server imports "exactly two" packages is corrected) or a small in-repo RFC 6455 implementation (handshake, masked text frames, ping/pong, close). Either way the server module adds no coupling to Azure specifics and stays behind the existing provider seams (PRD 027 Req 14). Node 22's built-in `WebSocket` client is enough for tests; no client-side dependency is added.
- `createApp` keeps its current signature and byte-identical behaviour for every existing caller (`createServer(createApp(...))` in the unit tests still works). The upgrade handler is exposed alongside it (e.g. a new export that returns `{ request, upgrade }` or an `attach(server)` helper) and `server/index.ts` wires the `'upgrade'` event of its `http.Server` to it when the flag is on.

### Server: MCP session tools (PRD 027 Req 7, Req 4, Req 10)

- `MCP_TOOLS` in `server/mcp.ts` lists exactly fourteen tools: the five existing file tools unchanged, plus `get_editor_state`, `open_file`, `scroll`, `set_selection`, `replace_selection`, `insert_text`, `replace_range`, `apply_format`, `save`, each with a closed JSON-Schema `inputSchema` matching the corresponding `BridgeToolRequest` member (minus `id`) in `src/lib/agentBridgeProtocol.ts`: `scroll` takes a `target` object (`{by: 'lines'|'pages', amount}` or `{to: 'line', line}` or `{to: 'heading', heading}`), `set_selection`/`replace_range` take numeric `from`/`to`, the four mutating tools require `revision`, `apply_format` takes `op` from `SMART_FORMAT_OPS`. The string-only `ToolSchema` type is widened as needed; no tool takes a workspace parameter (the token names it).
- `handleMcp` receives the broker and dispatches every session tool through `broker.dispatch(resolved.workspaceId, call)`, so control tools can only ever reach the tab registered for the token's workspace. Malformed arguments (validated through `decodeToolRequest` with a server-minted id, or an equivalent closed check) answer the existing `invalid_params` tool error.
- Result mapping is data, never a 500: a `{ ok: true }` bridge result becomes a `tools/call` result whose `structuredContent` is `{ state: <EditorStateSnapshot> }` (text mirrors it); a `{ ok: false }` result becomes an `isError: true` result whose payload is `{ error: { code, message, ... } }` with the bridge error's own code (`no_controlled_session` with message `no controlled session`, `stale_revision` carrying the fresh `state`, `timeout`, `tool_failed`). With no controlled tab for the workspace, every session tool answers `no_controlled_session`; file tools answer exactly as before regardless of tab state.
- `ToolErrorCode` (or the type that carries it) admits the bridge error codes; `server/README.md`'s MCP row and "Agent bridge" section describe the fourteen tools and the upgrade route, and the sentence saying the session tools and WebSocket "are not mounted yet" is gone.

### Client: toggle, channel, indicator (PRD 027 Req 1, Req 9, Req 10, Req 13)

- `src/platform/hosted.ts` implements `attachAgentBridge(executor)` (keeping the executor for the channel; no channel is opened by attaching) and exposes ONE new optional `Platform` seam for control state (e.g. `agentControl?: { enable(): void; disable(): void; subscribe(cb: (state: 'off' | 'connecting' | 'on') => void): () => void }`), typed in `src/platform/types.ts` and implemented only by the hosted flavour when the page is bound to a workspace. `tauri.ts`, `web.ts` and the dev shim do not implement it, so those builds render no toggle and open no channel.
- `enable()` opens exactly one same-origin `WebSocket` to the upgrade route with the stored session token (the `?access_token=` form), reaches `'on'` once open, runs `executor.execute` for every decoded `tool_request` and sends back the encoded `tool_result`; `session_replaced`, socket close or socket error moves the state to `'off'`; `disable()` closes the socket and moves to `'off'`. Closing the tab lets the browser close the socket, so the server tears the session down. The hosted platform holds the only `new WebSocket` call site in `src/`; no new `window.*` global, no `__mm*` seam, no CodeMirror access from bridge code.
- With the applied `agentBridge` setting on and the platform offering the seam, the app renders an agent-control toggle (test id `agent-control-toggle`, a labelled switch/checkbox, checked exactly while the state is `'on'`) in hosted chrome outside the Settings panel. While the state is `'on'` a persistent indicator (test id `agent-control-indicator`, text making clear an agent can read and edit this session) is visible in both preview and edit modes without any hover or reveal gesture; it disappears the moment the state leaves `'on'`. When another tab takes over, the first tab's toggle becomes unchecked and its indicator disappears with no user action.
- With the setting off (the default), no toggle and no indicator are rendered and no WebSocket is opened, so the client behaves as today; turning the setting off while opted in disables the channel. The gate reads the applied setting, so turning it on takes effect through the existing settings save with no reload.
- New chrome follows `docs/STYLE-GUIDE.md` (tokens, existing primitives); the style lint in the quick gate passes. New behaviour carries `// PRD 027 Req 7|9|10|11 (issue #367): …` citations.

### The bundle scan (SPEC11 §6.6, `scripts/validate.mjs`)

- Because the hosted platform ships inside both bundles, the full gate's static bundle scan is updated deliberately rather than dodged: `new WebSocket` moves out of `FORBIDDEN` into a counted allowlist mirroring `FETCH_ALLOWLIST` (the count re-pinned from fresh `npm run build` and `npm run build:web` outputs, which need no Rust), with a comment explaining that the one site is reachable only under the hosted marker, only with the experimental setting on, and only after the user opts in. The `FETCH_ALLOWLIST` count is unchanged (the channel reuses the existing wrapper for nothing and adds no `fetch(`). Evidence in the session: the two builds run and a grep of `dist/assets/*.js` and `dist-web/index.html` for `new WebSocket` matches the pinned count.

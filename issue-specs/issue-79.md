# Spec: End-to-end permission enforcement: server 403s and UI affordance gating (#79)

## Goal

All acceptance criteria in issue-specs/issue-79.md are satisfied for issue #79, with evidence visible in the session: every workspace-scoped REST route enforces exactly one documented catalog verb — including the three verbs nothing enforces today (`file.create` for creating a blob that does not exist yet, `comment.read`/`comment.write` for comment sidecars) — so a hand-rolled API call without the verb earns a 403 naming it no matter what the UI showed; the hosted UI hides or disables what the signed-in member's permissions don't allow (no Edit Mode / Save / editable editor without `doc.edit`, no comment composer without `comment.write`, no comments loaded without `comment.read`, on top of the file and workspace-settings gating that already ships), driven by one pure permission→affordance mapping in `src/lib/` with no `kind === 'hosted'` branching in app code; a Commenter can actually comment and a Viewer can write nothing; local-file mode and per-user settings stay unaffected by workspace role; the matrix is pinned by unit tests (U320+) and offline hosted e2e tests (E205+); and `npm run validate:quick` has been run once at the end and prints `QUICK VALIDATION: ALL PASSED`.

## Acceptance criteria

- **(PRD 007 Req 13+17 — every route checks exactly one verb, and the whole catalog is enforced)** Each workspace-scoped route in `server/workspaces.ts` requires exactly one `Permission` and answers `403 {"error":"forbidden","required":"<verb>"}` when it is missing — the shape `requirePermission` already sends. Today 11 of the 14 catalog verbs are reachable; after this issue **all 14 are enforced by some operation**, with the three currently-dead verbs wired as:
  - `file.create` — a `PUT /api/workspaces/<id>/files/<path>` (JSON or `?raw=1`) whose blob **does not exist yet** is a create and requires `file.create`; a PUT over an existing blob is a save and requires `doc.edit`. The existing in-code comment at the PUT branch ("no built-in role grants file.create without doc.edit") explains why it was deferred — it stops being true the moment a custom role (PRD 007 Req 15) grants one without the other, which is exactly what the new tests do.
  - `comment.read` / `comment.write` — requests whose target path is a **comment sidecar** (`<doc>.comments.json`, per `src/lib/sidecar.ts` `sidecarPathFor`) require `comment.read` on GET and `comment.write` on PUT/DELETE instead of `doc.read`/`doc.edit`/`file.delete`. Add the path predicate as a pure exported helper (e.g. `isSidecarPath` in `src/lib/sidecar.ts`) so server and client share one definition rather than each re-deriving the suffix. Pasted images and every other blob stay on the doc/file verbs.
  The mapping must be readable in one place — a declarative route→verb table, or per-route comments that a test can enumerate — not spread across prose. Directory (`/api/directory/*`), sign-in, `/api/me`, and the per-user layer (`/api/me/files`) are not workspace-scoped and keep their current auth-only (401) behaviour.
- **(PRD 007 Req 17 — enforcement is independent of the UI)** For a member holding a restricted custom role, direct `fetch`/`request` calls against every mutating workspace route return 403 with the right `required` verb and **leave stored state untouched** (re-list/re-read as an authorized user to prove nothing landed), with no reliance on any client-side check. A non-member of a workspace without everyone-access still gets 403 (not 404) on content reads while list metadata stays open (Req 11) — do not regress that.
- **(PRD 007 Req 17 — the whole role matrix behaves)** Concretely observable for the five built-in roles (Req 14): a **Commenter** can open a doc, read comments, and **successfully write a comment** (the sidecar write must no longer demand `doc.edit` — it is currently impossible for a Commenter, which is the headline bug this issue fixes) but cannot save the document itself; a **Viewer** can read the doc and its comments and write neither; a **Contributor** can create and edit files but not delete, rename, or manage folders; an **Editor** can do all doc/file/folder/comment work but not `workspace.*`; an **Owner** everything. Verify against the real endpoints, not against a table of expectations.
- **(PRD 007 Req 17 — document-level UI gating)** In a hosted workspace, a member without `doc.edit` sees no way to modify the open document: the editor is read-only (the `readOnly` prop the CodeMirror panes already accept — grep `authoringFrozen` in `src/App.tsx`; permission-gating is a *separate* reason from PRD 004's frozen-store case, so keep the two distinguishable and give the permission case its own explanation to the user), and **Edit Mode**, **Save**, **Save As…** and the equivalent hotkeys are absent or disabled in `src/lib/menuSpec.ts` (the `canUpload`/`canDownload` optional-field pattern is the model to follow so pre-existing `MenuState` call sites and frozen menu fixtures stay valid). No save request is issued that could only earn a 403.
- **(PRD 007 Req 17 — comment UI gating)** Without `comment.write`, the comment composer/reply/resolve/delete affordances are hidden or disabled and no sidecar write is attempted (no error-toast loop from autosave). Without `comment.read`, comments are not loaded or shown for the doc. With both, today's comment behaviour is unchanged. Reuse the existing comment-affordance seam (`src/lib/commentAffordance.ts`) rather than adding a parallel gate if it fits.
- **(One pure mapping, one seam, no flavor branching)** The permission→affordance decision stays a **pure** function in `src/lib/` — extend `fileGrantsFromPermissions` / `FileGrants` in `src/lib/fileGrants.ts` to the full affordance set (docs, comments, and the file rows it already covers) or add a sibling module it composes; app code reads it through one optional platform seam (`fileGrants?()` in `src/platform/types.ts` today) whose absence still means "everything this flavor's other seams offer" for desktop, the shim and the web build. App code outside `src/platform/` must not branch on `kind === 'hosted'` (PRD 007 Req 2). Keep the single-resolution-per-page-load caching in `src/platform/hosted.ts` (`grants`).
- **(Local docs and personal settings are not workspace-gated)** A local file opened client-side in the hosted flavor (PRD 007 Req 21, #78 — `local.owns(path)` in `src/platform/hosted.ts`) stays fully editable and savable even when the bound workspace grants nothing, and with no workspace bound at all. The per-user settings layer (`/api/me/files`, PRD 007 Req 9) keeps roaming for any signed-in user regardless of their role in any workspace — a Viewer can still change their own theme.
- **(Failures the user can act on)** A 403 that does slip through (a role changed in another tab mid-session; a stale cached grant set) surfaces the server's named refusal to the user rather than failing silently or corrupting state — the pattern `src/platform/hostedWorkspaces.ts` already uses for the members/roles endpoints. The doc is not left looking saved when the save was refused.
- **Pure logic is unit-tested (U320+; the current ceiling is U319).** New vitest tests under `tests/unit/` cover: the permission→affordance mapping for all five built-in roles and for restricted custom roles; the sidecar-path predicate (positive, negative, and lookalike names); the menu gating in `menuSpec.ts`; and the server route enforcement via the in-process harness `tests/unit/server-workspaces.test.ts` already uses (`call(user, method, path)`) — including a test that asserts **every** catalog verb in `PERMISSIONS` is required by at least one route, so a future verb cannot be added and left dead.
- **E2e coverage runs offline (E205+; the current ceiling is E204 — do not renumber, weaken or skip existing tests).** New Playwright tests in `tests/e2e/hosted.spec.ts` run against the local server on 4924 (Azurite + seeded mock users, no Azure, no external network) and observably verify at least: a Commenter writing a comment that a second member then reads; a member without `doc.edit` seeing a read-only editor with no Edit Mode/Save while their direct `PUT` earns 403 `doc.edit` and the stored bytes are unchanged; a custom role with `doc.edit` but not `file.create` being refused a new path with `required: 'file.create'` while an overwrite of an existing path succeeds; and comments hidden for a role without `comment.read`. Use the existing `signIn` / `signInTo` / `workspaceWithRole` helpers at the top of that file.
- **Standards, docs, map.** New and changed behaviour carries citation comments (`// PRD 007 Req 13/17: …`) per `docs/COMMENT-FORMAT.md` and `.sandcastle/CODING_STANDARDS.md`; `server/README.md`'s endpoint documentation reflects the final route→verb table; `docs/MAP.md` is regenerated via `npm run map` if the citation set changed (the quick gate diffs it); no `console.*` in `src/`.
- **Scope guard.** No new roles or catalog verbs (the 14 are fixed by Req 13), no membership/roles UI redesign (#77), no upload/download or ETag behaviour changes (#76, Req 19/20), no start-page or File-menu restructuring beyond the gating above (#78), no auth/sign-in changes, and no new endpoints unless a verb genuinely has no operation to attach to (say so in the summary comment if that happens).
- Iteration used `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code), with single e2e tests run via `npx playwright test -g '<title>'` while debugging — the full e2e suite was not used as an inner loop, and any starting baseline used the quick tier only.
- `npm run validate:quick` has been run **once**, at the end, in the implementer's session, and prints `QUICK VALIDATION: ALL PASSED`.
- A summary comment from the implementer exists on issue #79.

## Context

Parent #13; PRD `prd/007-azure-hosted-workspaces.md` Req 17, with Req 13 (one documented verb per operation), Req 14 (the five built-in roles), Req 15 (custom roles — the reason verbs can be granted independently) and Req 2 (no flavor branching outside `src/platform/`) as the constraints. Blockers #76/#77/#78 have landed on this branch, so most of the machinery already exists — this issue is the **sweep that closes the gaps**, not a build from scratch.

Affordance mapping: `src/lib/fileGrants.ts` (`FileGrants`, `ALL_FILE_GRANTS`, `fileGrantsFromPermissions`), consumed via the optional `fileGrants?()` seam in `src/platform/types.ts`, implemented in `src/platform/hosted.ts` (cached `grants`), read in `src/App.tsx` (grep `PRD 007 Req 17`, `folderGrants`) and applied in `src/components/FolderPanel.tsx` / `src/lib/folderOps.ts`. Sidecars: `src/lib/sidecar.ts` (`sidecarPathFor` → `<doc>.comments.json`), written from `src/App.tsx` via `writeTextFile` (grep `sidecarPathFor`). Menus: `src/lib/menuSpec.ts` (`MenuState`, the `canUpload`/`canDownload` optional pattern).

Tests: `tests/unit/server-workspaces.test.ts` drives the server in-process (fast — prefer it for route matrices); `tests/e2e/hosted.spec.ts` has `signIn`, `signInTo`, `workspaceWithRole`, `listFiles` helpers and E191 as the model for a "UI hides it, API refuses it" test.

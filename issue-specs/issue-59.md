# Spec: Releaser lane: the cut — release branch, changelog, gate, tag, draft verification, merge-back (#59)

## Goal

All acceptance criteria in issue-specs/issue-59.md are satisfied for issue #59, with evidence visible in the session: `.sandcastle/release-prompt.md` is a full cut runbook (prd/008 R8–R13, R15, R17) that performs all release mechanics on `release/vX.Y.Z`, runs the full `npm run validate` gate before any push or tag exists, has the agent itself push the branch and annotated tag, verify the draft, merge back into the default branch, and stop before publishing (`--draft=false` remains exclusively human, R12); `classifyReleaseIssue` in `.sandcastle/release-lane.mts` gains the windows-append and awaiting-publish states with the runner in `.sandcastle/main.ts` handling them, all new pure logic is covered by unit tests passing in `npm run test:unit`; and `npm run validate:quick` has passed in the implementer's session with a summary comment posted on issue #59.

## Acceptance criteria

- **(R8) The cut sequence.** `.sandcastle/release-prompt.md` replaces its "not implemented yet" milestone with a runbook that cuts branch `release/vX.Y.Z` from the up-to-date default branch (`git fetch origin main` → branch from `origin/main`) and performs, in order, each gated on the previous, all on that branch: `npm run release:prepare -- X.Y.Z` (four version files + lockfiles, commits itself), the changelog commit (next criterion), `npm run licenses` (commit `THIRD-PARTY-NOTICES.md` only if changed), a Windows-reserved-filename scan given as an explicit command in the prompt (e.g. `git ls-files` filtered for reserved stems `con prn aux nul com1–9 lpt1–9` judged case-insensitively on the basename before its first `.` — must produce no matches; cf. `src/lib/folderOps.ts` RESERVED and docs/DEVELOPING.md), and the full `npm run validate` gate, which must print `VALIDATION: ALL PASSED`.
- **(R9) Changelog.** The runbook commits the issue's approved entry (the `{{CHANGELOG}}`/issue-body `## Changelog` section, verbatim) at the top of `CHANGELOG.md` on the release branch, creating the file on the first cut, under a heading naming the version. After the draft exists (R11), the same text verbatim becomes the GitHub Release notes via `gh release edit vX.Y.Z --notes-file ...` (editing a draft is not publishing; keep or drop the workflow's asset-table header — implementer's call, but the approved entry must appear verbatim). Preflight already blocks a missing entry (a body without `## Changelog` classifies malformed), so the runbook can rely on the entry existing.
- **(R10) Failed gate aborts.** The runbook's ordering makes it structurally true that a failed gate aborts before any push or tag exists: nothing is pushed and no tag is created until `VALIDATION: ALL PASSED` has printed. On a gate failure the agent posts one comment with the failure evidence (failing step + tail of output) and stops; it never tags or pushes an unvalidated tree.
- **(R11) Push, watch, verify.** After the gate: the agent itself pushes the release branch, then the annotated tag `vX.Y.Z` created on the release branch tip (`git tag -a vX.Y.Z -m "Marky Mark X.Y.Z"`), so the tag points into the release branch. It then watches the triggered `release.yml` run to completion (poll `gh run list`/`gh run view` about once a minute), and when the draft exists verifies it: asset list is exactly the dmg, the `marky-mark-web-*.html`, `SHA256SUMS.txt`, the `*.app.tar.gz`, and `latest.json`; downloads the assets and checks `sha256sum -c SHA256SUMS.txt`. It comments the draft URL plus the verification evidence on the issue. The sandbox normally has no push credentials (agents don't push — `main.ts` ~307); the releaser is the sanctioned exception (R11), so the runbook establishes them itself (e.g. `gh auth setup-git` before pushing) — and the `main.ts` comment is updated so it doesn't read as contradicting the releaser.
- **(R12) Publish stays human.** After draft verification the runbook stops and hands over with a final "awaiting publish" comment. The existing hard rules stay: the agent never runs `gh release edit --draft=false` (under any configuration) and never deletes a release.
- **(R13) Platform sequencing.** For `platforms: both`, the runbook dispatches `gh workflow run release-windows.yml -f tag=vX.Y.Z` only after the mac/web draft exists and is verified, watches it, then verifies the appended `*-setup.exe` and the refreshed `SHA256SUMS.txt`, commenting the evidence ("windows appended"). For `platforms: windows` where tag `vX.Y.Z` already exists, the mac cut is skipped entirely and only the windows dispatch+verify runs — which requires a classifier change: `classifyReleaseIssue` returns a new discriminated action (e.g. `windows-append`) when platforms is `windows` and `tagNames` contains `vX.Y.Z`, bypassing the ordering guard for exactly that case (unit test: a `windows` request for a version equal to an existing tag is not refused; a `mac`/`both` request for the same version still classifies `out-of-order`, preserving the #19 guard). A `windows` request whose tag does not exist takes the normal full-cut path (ordering guard applies, windows follows the verified draft).
- **(R15) Merge-back.** After the tag push (not gated on CI), the runbook merges the release branch into the default branch and pushes it, so main carries the shipped version files and changelog entry. The `release/vX.Y.Z` branch itself is never deleted (permanence guard from #57 stays untouched; no new deletion sites appear).
- **(R17) The issue is the running log.** Every phase transition — preflight acknowledged, gate passed, tag pushed, CI green, draft verified and awaiting publish, windows appended, plus the failure comment of R10 — lands as exactly one comment on the release issue, each beginning with a fixed recognizable marker line (extend the `*_MARKER` constants pattern in `release-lane.mts`; do not build phase markers from `{{AGENT_MARKER}}`, which varies with the model string).
- **Idempotent resume.** The release issue stays open until publish (#60's close-out), so the loop re-dispatches the releaser on every pass; re-runs must never redo completed phases or duplicate comments. The runbook derives its position from actual state (existing phase-marker comments cross-checked against reality: does `release/vX.Y.Z` exist on the remote, does the tag exist, does the run/draft exist) and resumes from the first phase not done — in particular, a fully-verified cut awaiting publish results in no action and no new comment. Additionally, host-side: `classifyReleaseIssue` returns an `awaiting-publish` (or equivalent) action when the draft-verified/awaiting-publish marker is present in the issue's comments, and `runReleaseLane` then skips creating a sandbox at all (unit-tested).
- **Runner and stale text.** `runReleaseLane` in `.sandcastle/main.ts` handles the new action kinds (dispatching the runbook with whatever extra promptArgs it needs, e.g. the changelog entry and/or a mode flag), keeps the `timed("releaser", …)` phase name so the control panel pairing is unchanged, and every comment that currently says the cut "is a follow-up" (main.ts lane header ~741–747, release-prompt.md) is updated — no stale statements remain (the repo lints these in review; cf. commit df399c3).
- **Sandbox can run the gate.** `npm run validate` step 8 is `cargo check`, and `.sandcastle/Dockerfile` currently installs no Rust toolchain — the image gains one (rustup stable is enough; the gate never runs `tauri build`) so the releaser sandbox can complete the full gate. A full image rebuild is not required session evidence; the Dockerfile change plus a note suffices.
- **Unit tests.** All new pure logic (windows-append and awaiting-publish classification, any new comment/marker builders or state helpers) is covered by tests in `tests/unit/release-lane.test.ts`, discovered by `npm run test:unit`, with `U<n>:` titles continuing the existing sequence (never renumbering existing tests). Impure runbook behaviour (git/gh/CI) is prompt-driven and not unit-testable — the evidence for it is the prompt text plus the classifier tests.
- **Scope held.** No live cut is expected as evidence (no `sandcastle:release` issue exists; cutting a real release is not part of this issue). Publish close-out (R16) is #60, the `/new-release` skill is #61, and retiring `/release-mac`//`/release-windows` + rewriting docs/RELEASING.md (R18) is #62 — none of that lands here; `.claude/commands/release-mac.md` and `release-windows.md` stay.
- **Verification.** Iterate with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code) after each change; run `npm run validate:quick` ONCE, right before declaring the goal met — not after every small change and not as a starting baseline — and it prints `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- **Reporting.** A summary comment from the implementer exists on issue #59.

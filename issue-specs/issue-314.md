# Spec: settings fixes (#314)

## Goal

All acceptance criteria in issue-specs/issue-314.md are satisfied for issue #314, with evidence visible in the session: in the hosted Settings dialog the workspace tab is labelled "Manage", sits immediately after Editor, is present only while the Workspace scope is selected (absent in User scope, with a bounce to General when the scope switches away while it is open) and keeps its `settings-tab-workspace` test id and internal `workspace` tab id; each role row's name in the Roles section renders at the small chrome text size (`--mm-text-small`, the same size as the member names in People) with the "built-in" / "N permissions" hints unchanged; the Names, People, Roles and Delete workspace sections draw no top border and add no spacing of their own beyond the shared section-header margins; E364 and E529 (and the shared `openSettings`/`openWorkspaceSettings` helpers) are amended to the new label and scope rule; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #314.

## Acceptance criteria

- **Roles rows font.** In `src/styles.css`, `.workspace-role-name` (rendered by `src/components/WorkspaceRoles.tsx` for the five built-in rows and every custom role row) resolves to `font-size: var(--mm-text-small)` — the same computed size the member-name `<label>` in the People section gets from `.dialog label`. The adjacent `.hotkey-hint` spans ("built-in", "N permissions") and the Edit/Delete buttons keep their current styling. No raw pixel literal; use the token so the style lint in the quick gate stays green.
- **No separators.** The `.workspace-names, .workspace-members, .workspace-roles, .workspace-danger { margin-top; border-top; padding-top }` rule in `src/styles.css` (near line 3379) is gone or reduced so that none of the four sections (`workspace-names-section`, `workspace-members-section`, `workspace-roles-section`, `workspace-delete-section`) has a top border, and their vertical rhythm comes only from `.section-header`'s own margins (`14px 0 8px`, `:first-child` collapsed to 0) — exactly like the sections on General, Appearance, Editor and Hotkeys. Computed `border-top-width` on each section is `0px`.
- **Manage label.** In `TABS` (`src/components/SettingsPanel.tsx`) the entry with `id: 'workspace'` carries `label: 'Manage'`. The `SettingsTab` union, the `data-testid="settings-tab-workspace"` button id, `settings-scope-content-*` ids and every `workspace-*-section` id are unchanged. Breadcrumbs derive from `TABS`, so any breadcrumb naming the tab now reads "Manage" without a second string.
- **Workspace scope only.** The rail filter in `tabsBody` renders the `workspace` tab only when `scope === 'workspace'` (in addition to the existing `wsAccess.workspaceTab` condition). Under User scope the button is absent from `settings-tabs` — no placeholder, no disabled button. Its position is unchanged: immediately after Editor, before Hotkeys. Because the static web build passes `scopeSelector={false}` and the scope is then pinned to `'user'`, the tab can never appear there; nothing else about the web build changes.
- **Bounce to General.** A `useEffect` beside the existing `USER_ONLY_TABS` bounce: when `scope` becomes `'user'` (including the automatic reset when the workspace closes or `scopeSelector` is false) while `tab === 'workspace'`, the tab becomes `'general'` and any nested page is cleared (`setPage(null)`), mirroring the Hotkeys/Experimental bounce in the other direction. The existing bounce for a lost permission (`!wsAccess.workspaceTab`) stays.
- **Everything else unchanged.** The tab still requires an open hosted workspace and at least one permitted section (`useWorkspaceAccess`); the four sections and their components are untouched apart from the CSS above; no change to the desktop User | Workspace scope semantics; no new delete/close-workspace action on desktop.
- **Citations.** Every changed behaviour carries an `// Issue #314: …` citation comment per `.sandcastle/CODING_STANDARDS.md`; the stale "shows in both scopes" comment above the `TABS` entry is rewritten to describe the new rule rather than left contradicting the code.
- **E364 amended** (`tests/e2e/hosted.spec.ts` ~line 2213): in User scope the tab list is asserted to be exactly `General, Appearance, Editor, Hotkeys, Experimental` and `settings-tab-workspace` has count 0; after clicking `settings-scope-workspace` the list is `General, Appearance, Editor, Manage, Hotkeys` (Hotkeys/Experimental are User-only — assert whatever the rail actually shows in Workspace scope, verified by running the test) and clicking the tab shows the members, roles and delete sections; switching back to `settings-scope-user` while on Manage lands on General with the tab gone. The "no workspace bound → no tab" tail of the test stays. The test title is updated to say Manage.
- **E529 amended** (`tests/e2e/styling.spec.ts` ~line 282): it clicks `settings-scope-workspace` before `settings-tab-workspace`, and its comment/title say Manage. Optionally it (or a new test taking the next unused E-number — E573 at spec time; re-check with `grep -rhoE "test\('E[0-9]+" tests/e2e | sort` before committing) also asserts each `workspace-*-section` has computed `border-top-width` of `0px` and that `.workspace-role-name` and a `.workspace-member-field label` share the same computed `font-size`.
- **Shared helpers amended.** `openSettings(page, 'workspace')` in `tests/e2e/helpers.ts` (and therefore `openWorkspaceSettings` in `hosted.spec.ts`, used by ~19 tests) clicks `settings-scope-workspace` before clicking `settings-tab-workspace`, so every existing hosted membership/roles/names/danger-zone test still reaches the tab. Tests that already assert the tab's absence after switching to Workspace scope (~lines 1509 and 2192) keep passing. No existing test is weakened, renamed or renumbered.
- **Iteration economy.** The implementer iterates with `npm run typecheck` and `npm run test:unit`, plus targeted e2e runs (`npx playwright test -g 'E364'`, `-g 'E529'`, and a couple of `openWorkspaceSettings` users such as `-g 'E365'`), after each change, and baselines an attempt with the quick tier only.
- **Full gate.** `npm run validate:quick` has been run ONCE in the implementer's session, right before declaring the goal met (not after every small change and not as a baseline at the start), and prints `QUICK VALIDATION: ALL PASSED`. If `npm run map` output changes, the regenerated `docs/MAP.md` is committed alongside.
- **Summary comment.** A summary comment from the implementer exists on issue #314 describing what changed, which tests were amended, and the validate:quick result.

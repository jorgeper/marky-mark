# Spec: Release close-out: on publish, comment final links and close the release issue (#60)

## Goal

All acceptance criteria in issue-specs/issue-60.md are satisfied for issue #60, with evidence visible in the session: a GitHub Actions workflow triggered by release publish (new workflow, or a job alongside `updater-manifest.yml`) finds the open `sandcastle:release` issue whose `**Version:**` matches the published tag, posts one marked comment with the final release links, and closes the issue; the workflow is a safe no-op for the `updater` rolling release, for duplicate publish events, and when no matching open issue exists, and it never publishes or deletes anything; a `workflow_dispatch` recovery path with a `tag` input exists; `npm run validate:quick` has passed in the implementer's session and a summary comment from the implementer exists on issue #60.

## Acceptance criteria

- **(R16) Close-out workflow exists.** A workflow fires when a real release is published — either a new `.github/workflows/release-closeout.yml` or a separate job in `updater-manifest.yml`. If it lands in `updater-manifest.yml`, the existing `advance` job, its fixed-string `concurrency` group, and its event-type comments must be left semantically untouched (they encode the issue #19 fix). A new workflow is the lower-risk choice.
- **Matching by the #58 body contract.** The workflow derives the version from the tag (strip the leading `v`), lists open issues labeled `sandcastle:release` (label constant `RELEASE_LABEL` in `.sandcastle/github.mts`), and matches the one whose body's `**Version:**` line equals that version — the machine-parseable format documented in `.sandcastle/release-prompt.md` ("THE RELEASE-ISSUE BODY FORMAT") and parsed by `parseReleaseIssueBody` in `.sandcastle/release-lane.mts`. The workflow's match pattern must accept exactly what that contract emits (`**Version:** X.Y.Z[-pre.N]`, no leading `v`). If matching is implemented as JS/TS beyond a trivial `--jq`/regex over that line, the logic is pure and covered by unit tests in `tests/unit/` (colocated `.sandcastle/*.test.mts` files are not discovered by `npm run test:unit`; test titles use the `U<n>:` convention without renumbering existing tests).
- **The close-out actions.** On a match, the workflow posts exactly one comment on the release issue containing the final release links (at minimum the release page URL for the tag) and then closes the issue as completed. Release issues are closed by publish, not by merge keywords — no code path adds `Closes #<n>` style keywords for release issues.
- **Idempotent and safe under duplicate events.** One publish can fire more than one `release` event type (see the comment block in `updater-manifest.yml`). Re-delivery must not double-comment or re-close: the closed-issue → no-open-match path exits cleanly as a no-op, the comment carries a recognizable marker line (mirror the `🏰 Sandcastle releaser:` markers in `.sandcastle/release-lane.mts`), and concurrent duplicate runs are serialized (a `concurrency` group) or guarded by a marker check before posting.
- **Non-release tags skipped.** The rolling `updater` tag, and any published release with no matching open `sandcastle:release` issue (e.g. today's manually cut releases), end as clean no-op runs — no comment, no close, no failure.
- **Manual recovery path.** The workflow also accepts `workflow_dispatch` with a required `tag` input (mirroring `updater-manifest.yml`), so a failed publish-time run can be re-run by hand against the same tag.
- **Hard limits held.** The workflow never publishes a release, never flips `--draft=false`, never deletes a release or tag, and requests only the permissions it needs (`issues: write`; `contents: read` if it checks out the repo). The cut itself (PRD R8–R13) and command retirement/docs (R18) stay out of scope.
- **No live-publish evidence expected.** No release will be published during the attempt, so evidence is the workflow file (valid YAML — `npm run typecheck`/`test:unit` do not lint workflows, so eyeball or `actionlint` if available), plus any unit tests for extracted matching logic.
- **Verification.** Iterate with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code) after each change; run `npm run validate:quick` ONCE, right before declaring the goal met — not after every small change and not as a starting baseline — and it prints `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- **Reporting.** A summary comment from the implementer exists on issue #60.

## Context

This is R16 of `prd/008-releaser-agent.md` (parent #25); #58 (merged) built the lane and defined the issue-body contract this workflow consumes. The contract text lives in `.sandcastle/release-prompt.md` and its reference parser plus the `🏰` marker precedent in `.sandcastle/release-lane.mts`; `RELEASE_LABEL` is in `.sandcastle/github.mts` (~line 325). `updater-manifest.yml` is the sibling publish-triggered workflow and documents the duplicate-event and concurrency traps from issue #19 — read its header comments before choosing trigger types. Running `tsx`/`.mts` code inside Actions requires `npm ci`, which is heavy; a `gh issue list --json number,body` pipe with a small `node -e` or `--jq` match against the `**Version:**` line is the lightweight route, as long as the pattern stays consistent with `parseReleaseIssueBody`. Comments in workflow/`.sandcastle` code cite `prd/008 R16`, not `SPEC<n>`.

# Spec: Entra ID sign-in and API authentication guard (#71)

## Goal

All acceptance criteria in issue-specs/issue-71.md are satisfied for issue #71, with evidence visible in the session: an unauthenticated visitor to the hosted server sees only a sign-in page (no editor, sidebar, or document content) and signing in as a seeded mock user in local dev mode renders the app shell, proven by hosted-flavor e2e tests running offline inside `npm run test:e2e`; the SPA carries a complete Entra ID auth-code + PKCE flow (S256 challenge, state-checked callback, code-for-token exchange against the tenant's token endpoint) whose logic is covered by unit tests with no cloud calls; every `/api/` endpoint except the deliberately unauthenticated sign-in surface answers 401 without a valid bearer token for the configured tenant; and `npm run validate:quick` passes in the implementer's session.

## Acceptance criteria

- **SPA-side Entra PKCE flow exists (PRD 007 Req 5).** The SPA implements the full single-tenant auth-code + PKCE sign-in flow: generate a code verifier and S256 challenge, redirect to the tenant's authorize URL (the server's `POST /api/auth/sign-in` already answers `{kind:'redirect', authorizeUrl}` in azure mode — the SPA appends its `redirect_uri`, `state`, and `code_challenge`), handle the redirect back (rejecting a mismatched `state`), and exchange the code for a token at `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token` as a public client. The flow's logic (verifier/challenge generation, URL construction, callback parsing, exchange request/response shape) lives as pure, unit-testable functions (e.g. in `src/lib/` or `src/platform/`); it is verified by `npm run typecheck` and unit tests with mocked fetch only — no Entra tenant, no network calls in tests.
- **Unauthenticated visitors see only a sign-in page.** When the SPA is served by the hosted server (`server/`) and there is no valid session, the page shows only a sign-in surface — no editor, no folder sidebar, no menus, no document content. The web and desktop flavors (static web build, Tauri, dev shim) are completely unaffected: they never show a sign-in page. The detection mechanism (server-injected marker, probe endpoint, or similar) is the implementer's choice, but it must work with the unmodified `dist/` build the server already serves and must not misfire when that same build is hosted statically elsewhere.
- **Local dev mode signs in end to end.** In `MM_MODE=local`, the sign-in page lets a seeded mock user (see `server/providers/mock/users.ts`) sign in; afterwards the normal app start page renders, subsequent `/api/` calls carry the bearer token, and the session survives a page reload. In azure mode the page offers a sign-in-with-Microsoft action that starts the redirect flow (this branch is covered by unit tests/typecheck only).
- **The API guard holds (PRD 007 Req 5).** Every `/api/` endpoint except the deliberately unauthenticated sign-in surface (currently `POST /api/auth/sign-in`, plus any endpoint the flow legitimately needs pre-auth, e.g. a mode/config probe) answers 401 without a valid bearer token. In azure mode, token validation stays pinned to the configured tenant's issuer and the client-id audience via JWKS (already implemented in `server/providers/azure/entra.ts` — kept and still unit-tested). Any endpoint added by this issue is inside the guard unless it must be pre-auth by design.
- **E2e coverage runs offline inside `npm run test:e2e`.** New Playwright tests numbered E165+ (in `tests/e2e/hosted.spec.ts` or a new auto-collected spec file) observably verify at least: an unauthenticated visit to the hosted server shows only the sign-in page (editor/sidebar absent); signing in as a seeded mock user renders the app shell; the session survives a reload; and an unauthenticated API request still gets 401. Zero Azure resources, no network beyond localhost. Existing tests are not weakened, renumbered, or skipped.
- **Unit tests pin the flow logic.** New vitest tests (U229+, under `tests/unit/`, collected by `npm run test:unit`) cover the PKCE/callback/exchange logic and any new server-side guard or endpoint behavior, per `.sandcastle/CODING_STANDARDS.md`.
- **Standards and map.** New behaviour carries citation comments (`// PRD 007 Req 5: …`), and `docs/MAP.md` is regenerated via `npm run map` if the citation set changed (the quick gate diffs it).
- **Scope guard.** No hosted `Platform` implementation (`kind: 'hosted'`) is added (that is issue #73), no workspace manifest or permission semantics (issues #72/#79), and no start-page redesign (#78). After sign-in the existing app behaving as it does today is sufficient — hosted file access is out of scope.
- Iteration was done with `npm run typecheck` and `npm run test:unit` (plus targeted e2e runs like `npx playwright test -g 'E165'`), with the full gate run ONCE at the end — not after every small change, and not as a starting baseline (baseline with the quick pair only).
- `npm run validate:quick` passes in the implementer's session, printing `QUICK VALIDATION: ALL PASSED`.
- A summary comment from the implementer exists on issue #71.

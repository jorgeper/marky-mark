# Spec: Editor: render the heading copy-link button to the right of the heading text, not in a gutter; narrow the line-number column (#261)

## Goal

All acceptance criteria in issue-specs/issue-261.md are satisfied for issue #261, with evidence visible in the session: in the hosted editor the PRD 020 Req 18 heading copy-link button renders inline at the right of the heading text on the cursor's heading line (not in a left gutter) without shifting the heading text or entering the document text; the `headingLinkGutter` / `.cm-heading-link-gutter` column is removed so the left gutter is only the line numbers plus their normal padding; the button keeps the same glyph, `createHeadingLinkButton` factory, ~2s "Link copied" confirmation, live-region announcement and focus-preserving click; the e2e/unit coverage keyed on `heading-copy-link-gutter` and the PRD 020 Req 18 "in the gutter" wording are updated to the new placement; `npm run validate:quick` passes; and a summary comment from the implementer exists on issue #261.

## Acceptance criteria

### The button moves to the right of the heading text

- With the cursor resting on a heading line in the hosted editor, the copy-link control renders **at the right of that heading's text**, on the same line — not in a column left of the text. Its left edge is at or to the right of the heading text's right edge; it never overlaps the glyphs.
- The **trigger is unchanged**: the control appears only when the cursor's line is a heading by `isHeadingLine` (`editor/src/lib/headingLine.ts` — the issue #260 pre-filter, which must keep working past the background parse cut-off) **and** the seam's `getUrl(canonicalLine)` resolves non-null, addressing the **canonical** line via `canonicalLineAt` (issue #260: a gridded table above the cursor puts the raw editor line and the canonical line apart). On a body line, a fenced `# not-a-heading` line, or an untitled buffer, no control exists.
- The control is **not part of the document text**: `EditorState.doc` / the buffer written back through `onChange` is byte-identical with the control present, and the heading's text does not shift horizontally when the control appears or disappears. The implementation is a CodeMirror widget decoration at the heading line's end (or an absolutely positioned marker aligned to the line's right edge) — the `SmartEditWidget` / `.smart-edit-anchor` zero-size-anchor pattern in `editor/src/components/Editor.tsx` is the in-repo precedent for chrome that hangs off a line without moving it.
- **Wrapped headings**: for a heading long enough to wrap, the control's resting place is deliberate and stable — end of the last visual line **or** right edge of the first visual line, one of the two, stated in a citation comment — and it does not overlap the heading text in either case.
- Same control, same behaviour otherwise: same link glyph, same rest tooltip/`aria-label` ("Copy link to heading"), the same `createCopyLinkController` confirmation contract (copy at click time, `is-copied` + "Link copied" only on a landed clipboard write, ~2s, then rest), the same polite `aria-live` announcement, and `mousedown` `preventDefault` so focus and the resting cursor stay in the editor on click.
- It is still built from the shared `createHeadingLinkButton` factory (`editor/src/lib/headingLinks.ts`) so the editor and preview placements stay one control; that module's doc comment describing the "editor gutter placement" is rewritten to describe what now exists.
- The announcement text stays **out of the comment-anchor text space**: the live region is not left sitting inside the preview root, and inside the editor it neither enters `state.doc` nor is picked up by a copy of the heading line. Reusing `ensureCopyLinkLiveRegion` or parking the span outside `.cm-content` are both acceptable; state which was chosen and why.
- The placement holds wherever the gutter placement worked today — plain edit and the split view's edit half, live preview on or off — and stays **hosted-only** (PRD 020 Req 15): the Editor gets the seam nowhere else, so the desktop (Tauri), dev-shim and single-file builds still show no editor heading control.
- The preview's `mm-heading-link` graft (`decorateHeadingLinks`) is **unchanged** — it is already to the right of the heading.

### The gutter is gone and the number column narrows

- `headingLinkGutter` and `HeadingLinkMarker` are **removed**, not left dead: `rg 'heading-link-gutter|headingLinkGutter|HeadingLinkMarker|heading-copy-link-gutter' src editor tests docs` returns nothing outside an amendment/history note. The `.cm-heading-link-gutter` rule leaves `editor/styles.css` with it.
- No gutter column other than the line numbers reserves horizontal space per line for this control. With line numbers on, the total `.editor-wrap .cm-gutters` width is **narrower than before by the removed column** (~22px) and fits only the digits plus their normal padding; with line numbers off, no gutter is present at all.
- Everything issue #272 established about the gutter survives: `.cm-gutters` stays **flush** at the editor pane's left edge (inset ≤ 2px), keeps its themed right rule off `--mm-border` (issue #63) and its themed surface/digit colours (issue #52), and grows **no** left rule. The SPEC43 §3 smart-edit button, which hangs left into `.cm-content`'s padding, still lands correctly and is not clipped.
- The heading control's CSS is rewritten for the new placement rather than left describing a gutter: the `.heading-link-btn` block and its `is-copied::after` caption (currently floated toward the content because "the narrow gutter never has to fit the words") must read correctly where the button now sits, and the caption must not run off the pane's right edge or cover the heading text. All colours resolve through `--mm-*` tokens and pass the style lint (`docs/STYLE-GUIDE.md`, `scripts/validate.mjs`).
- The compartment plumbing keeps its property: the extension still lives in its own `Compartment` reconfigured off `hasHeadingLink`, reading the seam through `headingLinkRef`, so App re-render identity churn never rebuilds the control mid-confirmation.

## Context

Everything editor-side lives in `editor/src/components/Editor.tsx`: `HeadingLinkMarker` (~1022–1072) and `headingLinkGutter` (~1078–1110), mounted through `headingComp` at ~1765 and reconfigured at ~2296–2305; the `HeadingLinkSeam` type and its comments are at ~441 and ~486. For the "chrome on a line that does not move the text" pattern, read `SmartEditWidget` (~963–998) and `.smart-edit-anchor` / `.smart-edit-btn` (`editor/styles.css:790–815`): a zero-size inline anchor plus an absolutely positioned button, with the issue #263 fence-card offset showing how per-line geometry gets corrected in CSS rather than in the widget. Note the smart-edit button hangs *left*; this one goes right, so the anchor belongs at the line's end.

Issue #260 is upstream and its two guards must survive verbatim in the new code path: `isHeadingLine` instead of a raw `syntaxTree` read, and `canonicalLineAt` to convert the raw editor line to the canonical line the seam addresses. Issue #272 is the other upstream — read the gutter comments it left in `editor/styles.css` before touching them, and keep E136's flush/right-rule-only contract passing.

# Spec: /new-release skill: interview, changelog approval, file the sandcastle:release issue (#61)

## Goal

All acceptance criteria in issue-specs/issue-61.md are satisfied for issue #61, with evidence visible in the session: a `/new-release` skill exists at `.claude/skills/new-release/SKILL.md` that interviews the owner for version, platform set, and optional highlights; validates strict semver and tag ordering with the same prerelease-aware rules as `.sandcastle/release-lane.mts` (windows-append against an existing tag allowed, mirroring `classifyReleaseIssue`); requires explicit owner approval of the drafted changelog entry before proceeding; and files a `sandcastle:release` issue whose body parses `ok` under `parseReleaseIssueBody` without ever starting the cut; a unit test guards the skill's body template against parser drift; and `npm run validate:quick` has passed in the implementer's session with a summary comment posted on issue #61.

## Acceptance criteria

- **(R1) The skill exists and interviews.** `.claude/skills/new-release/SKILL.md` exists with `name: new-release` / `description:` frontmatter (following the `.claude/skills/new-prd/SKILL.md` precedent, which makes it invocable as `/new-release`). It instructs an interview collecting: the version, the platform set (exactly one of `mac`, `windows`, `both`), and optional highlights the owner wants emphasized in the changelog. The owner drives; the skill never invents a version.
- **(R1) Validation before proceeding.** The skill validates, before drafting anything: the version is strict semver `MAJOR.MINOR.PATCH` with an optional pre-release id that is never stripped — bare (no leading `v`, the tag adds it), no build metadata — and is **newer than the newest existing `v*` tag** under prerelease-aware precedence (a full release outranks its own pre-releases; numeric identifiers compare numerically). These are exactly the rules of `parseVersion` / `compareVersions` / `newestReleaseTag` in `.sandcastle/release-lane.mts`; the skill either invokes them (e.g. an `npx tsx -e` one-liner importing from that module) or replicates them precisely — either way a version the skill accepts must never later classify `malformed` or `out-of-order` in preflight. One deliberate exception, mirroring `classifyReleaseIssue`: a `windows` request whose tag `vX.Y.Z` already exists is valid (the R13 windows-append path — e.g. adding the Windows installer to an already-cut mac release); `mac`/`both` requests get no such exception. On validation failure the skill explains and re-asks; it never files.
- **(R2) Changelog drafted and owner-approved.** The skill drafts the changelog entry for the version from the commits and the closed issues since the last release tag (e.g. `git log <newest-tag>..origin/main --oneline` plus `gh issue list --state closed` filtered since that tag's date — most work lands as direct `RALPH:` commits, so commits are a first-class source, not just PRs), folding in the owner's highlights. It presents the draft to the owner for edit/approval and loops on their edits; it does not continue to filing until the owner explicitly approves the text. The approved text is carried forward verbatim.
- **(R3) The issue is filed, in the contract format.** The skill ends by creating a GitHub issue labeled `sandcastle:release` (and NOT the plain `sandcastle` label — the labels are disjoint so the implement lane never sees release issues) whose body is exactly the machine-parseable contract documented in `.sandcastle/release-prompt.md` and parsed by `parseReleaseIssueBody`: a `**Version:** X.Y.Z` line, a `**Platforms:** mac|windows|both` line, and a non-empty `## Changelog` section holding the approved entry verbatim. Because the `sandcastle:release` label does not currently exist on the GitHub repo, the skill ensures it exists before filing (e.g. `gh label create` if missing, matching the color/description conventions of the other `sandcastle:*` labels / `.sandcastle/setup.mts` `LABEL_ROWS`).
- **(R3) The skill never starts the cut.** After filing, the skill reports the issue URL and stops — it never runs `npm run sandcastle` or any release mechanics; the next orchestrator pass picks the issue up. The skill's text states it is the only supported way to file a release issue (hand-authored bodies are unsupported, though preflight will still refuse malformed ones).
- **Drift guard.** The skill embeds the exact body template it files, and a unit test (in `tests/unit/`, `U<n>:` title continuing the existing sequence, discovered by `npm run test:unit`) asserts that a body built from that template parses `ok` via `parseReleaseIssueBody` — so the skill and the parser cannot drift apart silently. Reading the template out of `SKILL.md` in the test or duplicating it as a tested constant are both acceptable; the tie to the real parser is what matters.
- **Scope held.** Retiring `.claude/commands/release-mac.md` / `release-windows.md` and rewriting `docs/RELEASING.md` is PRD R18 (issue #62) — none of that lands here; both command files stay. No changes to the releaser lane, runbook, or close-out workflow are expected (they shipped in #58–#60); if any stale repo text claims the `/new-release` skill is future work, update it, but do not touch the lane's behaviour.
- **Verification.** Iterate with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code) after each change; run `npm run validate:quick` ONCE, right before declaring the goal met — not after every small change and not as a starting baseline — and it prints `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- **Reporting.** A summary comment from the implementer exists on issue #61.

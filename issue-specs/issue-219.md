# Spec: Workspace unique names: creation flow, migration, rename (PRD 020 Reqs 1–4) (#219)

## Goal

All acceptance criteria in issue-specs/issue-219.md are satisfied for issue #219, with evidence visible in the session: hosted workspaces carry a validated, deployment-unique (case-insensitive) unique name that the server enforces on creation and rename — rejecting collisions and reserved names with errors the UI surfaces inline; the New Workspace flow asks for the unique name up front, pre-validated as you type, plus an optional friendly display name; existing workspaces migrate idempotently (display name slugified and deduped into the unique name, the original preserved as the friendly name, migration logged); an Owner can change both names in workspace settings; and `npm run validate:quick` passes in the implementer's session.

## Acceptance criteria

- **Manifest carries the unique name (Req 1).** `WorkspaceManifest` (`src/lib/hostedWorkspace.ts`) has a unique-name field alongside the existing display `name`. `validateWorkspaceManifest` accepts it when present and well-formed (1–100 characters, only `[A-Za-z0-9._-]`) and rejects a malformed value with an error naming the problem. Manifests written before the field existed still parse (the `scratchpad?` optional-field precedent), so pre-migration reads never break.
- **Server enforces uniqueness and reserved names (Req 1).** A shared, unit-tested module owns the name rules: charset/length validation, case-insensitive comparison, and the reserved list — at minimum `scratch`, `scratchpad`, and the route words the server already serves (`api`; include any other top-level path segments in use). `POST /api/workspaces` and the rename write path (`server/workspaces.ts`) reject a unique name that is invalid, reserved, or collides case-insensitively with any existing workspace's unique name, with a 4xx JSON error whose message the client can show verbatim. Unit tests cover accept/reject cases including case-insensitive collision and reserved names.
- **Creation flow asks for the name up front (Req 2).** The New Workspace dialog (`src/components/WorkspaceSwitcher.tsx`, form logic in `src/lib/workspaceLifecycle.ts`) has a unique-name field validated as you type (format/length errors appear inline before submit) and an optional friendly display name field (free text). A server-side rejection (collision or reserved) is surfaced inline in the dialog, not swallowed. The created workspace's manifest holds both names.
- **Display semantics (Req 2).** Where workspace names appear in chrome (workspace switcher/Open dialog, settings), the friendly name is shown when set, the unique name otherwise; unset friendly name means the unique name is the display. The unique name is visible to the user at least in the creation dialog and workspace settings (full URL surfaces are later PRD 020 issues).
- **Migration (Req 3).** On upgrade, every existing manifest without a unique name gets one: the display name slugified (lowercased; runs of characters outside `[a-z0-9._-]` collapsed to `-`), deduped deployment-wide with `-2`, `-3`… suffixes, with the original display name preserved as the friendly name. Reserved words count as taken during dedupe so migration never mints a reserved unique name. Migration is idempotent — a second run changes nothing — and logs each workspace it migrates. Unit tests cover slugify, dedupe, reserved-word avoidance, and idempotency.
- **Rename (Req 4).** Workspace settings (alongside `WorkspaceMembers`/`WorkspaceRoles`/`WorkspaceDangerZone`) let a holder of the `workspace.settings` verb change the unique name and the friendly name. The server applies the same validation/uniqueness rules to a unique-name change as to creation and the change takes effect immediately (subsequent listings and manifest reads show it). Friendly-name changes never touch the unique name. A caller without `workspace.settings` cannot rename (existing 403 semantics).
- **Citations.** New behaviour carries `// PRD 020 Req <n>:` citation comments per `.sandcastle/CODING_STANDARDS.md`, and `docs/MAP.md` is regenerated (`npm run map`) if citations moved.
- **Test economy.** The implementer iterated with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code), and ran `npm run validate:quick` ONCE right before declaring the goal met — not after every small change and not as a full-suite baseline. `npm run validate:quick` passes in the implementer's session (`QUICK VALIDATION: ALL PASSED`).
- A summary comment from the implementer exists on issue #219.

## Context

Scope is PRD 020 Reqs 1–4 only (`prd/020-shareable-links.md`): names, not URLs — path routing, redirects, 404 pages, usernames, and share affordances are later issues. Rename's "old links 404" consequence (Req 8) is out of scope here.

Server: `server/workspaces.ts` — creation at the `POST` branch (~line 492, `buildNewWorkspaceManifest`), whole-manifest write via `PUT .../manifest` gated on `workspace.settings` (~line 634), listing loop (loads every manifest — the natural place to check collisions; there is no database, one manifest blob per workspace). `server/app.ts` routes show the in-use top-level API words. There is no existing migration precedent — a startup or first-touch pass is the implementer's design choice, but it must be idempotent and logged. Note the existing scratchpad workspace (PRD 019, friendly name "Scratchpad") will slugify into the reserved word — the dedupe-past-reserved rule above handles it.

Client: `src/lib/hostedWorkspace.ts` (manifest types + validation, unit-tested in `tests/unit/hosted-workspace.test.ts`), `src/lib/workspaceLifecycle.ts` (New Workspace form validation), `src/components/WorkspaceSwitcher.tsx` (dialog). Hosted-only surfaces; desktop/web builds are untouched. Style per `docs/STYLE-GUIDE.md` for any new form fields.

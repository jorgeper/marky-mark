# Spec: Settings dialog: one section-header style across every tab (People diverges) (#249)

## Goal

All acceptance criteria in issue-specs/issue-249.md are satisfied for issue #249, with evidence visible in the session: every second-level section header in the Settings dialog — the Workspace tab's sections included — renders through one codified section-header primitive with identical computed type and colour instead of the `.dialog h2` title-plus-rule look, `docs/STYLE-GUIDE.md` names that primitive in its vocabulary and Do / Don't list, `npm run validate:quick` passes in the implementer's session, and a summary comment from the implementer exists on issue #249.

## Acceptance criteria

- Every second-level section header rendered inside the Settings dialog (`.dialog.settings-modal`, `src/components/SettingsPanel.tsx:1441`) resolves to the same section-header class and markup shape, so their computed `font-size`, `text-transform`, `letter-spacing` and `color` are identical. The tabs to sweep: General, Appearance, Editor, Workspace, Hotkeys, Experimental, plus the nested LLM providers page reached from the Semantic zoom row (issue #247).
- The Workspace tab's four sections — `WorkspaceNames` ("Names"), `WorkspaceMembers` ("People"), `WorkspaceRoles` ("Roles"), `WorkspaceDangerZone` ("Delete workspace") — no longer render a bare `<h2>` inside the Settings dialog and no longer pick up `.dialog h2` / `.dialog h2:not(:first-child)` (`src/styles.css:1156`, `src/styles.css:1362`), whose 14px heading plus `border-top` hairline is the divergence the issue reports. Their section structure, order, copy, and every existing `data-testid` are unchanged.
- Dialogs where `<h2>` legitimately *is* the dialog title are visually unchanged: `ExportDialog`, `SavePicker`, `AboutDialog`, `UpdateDialog`, `WorkspaceSwitcher`, the confirm dialogs in `src/App.tsx`, and `ManagementPanel` (`.dialog.management-modal`, which today also relies on the multi-`h2` rule). If the multi-`h2` border-top rule is retired rather than left in place, `ManagementPanel` is migrated in the same change so it does not lose its section separation.
- The Hotkeys tab's Smart Edit group header (`.hotkey-group`, `src/styles.css:2892`) no longer restates the section-header's type properties: it renders through the same primitive, with any remaining difference limited to layout (spacing/rule), not font size, case, letter-spacing or colour.
- The Appearance tab is explicitly resolved rather than skipped: it either gains section headers built from the same primitive (headers added only — no row is reordered, removed, or otherwise restructured) or the summary comment records that it has no second-level sections and therefore no header to unify. Either way no hand-rolled header style remains on it.
- `docs/STYLE-GUIDE.md` names the settings-page section header as a primitive in "The primitive vocabulary" (with the class name, what it looks like, and the settings-section chrome around it — spacing and any rule), and its Do / Don't list gains an entry telling call sites not to hand-roll a section heading inside a settings tab.
- The style lint (`scripts/style-lint.mjs`) gains a rule catching a hand-rolled settings section header where one is mechanically detectable (for example a bare heading element inside the settings modal's tab content, or a CSS rule restating the section-header type properties); the corresponding Do / Don't entry is marked **[lint]** and the UI-styling bullet list in `.sandcastle/CODING_STANDARDS.md` lists it. If the implementer concludes no rule can be written without false positives, the summary comment on #249 says so and why.
- A new Playwright test in `tests/e2e/styling.spec.ts` carries the next unused `E<n>` id (528 is the highest in the suite today; numbers are never reused) and asserts by computed style that the settings section headers agree across at least two tabs, one of them the Workspace tab (which needs the hosted-workspace setup used by `tests/e2e/hosted.spec.ts`; reuse `fixtures.ts`/`helpers.ts` rather than re-implementing it). Any existing test that selects the workspace sections by `h2` is updated to the new markup and passes; no existing test is weakened, skipped or deleted.
- Every changed behaviour site carries a citation comment per `.sandcastle/CODING_STANDARDS.md` (`// PRD 018 §…` / `// Issue #249: …`), and `docs/MAP.md` is regenerated with `npm run map` if citations changed, so the validation gate's diff of it stays clean.
- The change holds in both builds — desktop (Tauri) and hosted (cloud) — since the Workspace tab only exists in the hosted build while the other tabs render in both.
- The implementer iterated with `npm run typecheck` and `npm run test:unit` (plus targeted `npx playwright test -g '<title>'` runs for the new/changed e2e test), and ran the full quick gate `npm run validate:quick` ONCE at the end — not as a start-of-attempt baseline and not after every change — with `QUICK VALIDATION: ALL PASSED` printed in the session.
- A summary comment from the implementer exists on issue #249 describing what changed, the Appearance finding, and whether a lint rule was wired in.

## Context

The Settings dialog's established section header is `.settings-modal .tab-section` (`src/styles.css:1316`): small all-caps, `--mm-text-caption`, `0.06em` letter-spacing, muted colour, rendered as `<h3 className="tab-section">`. It is used by the General and Editor tabs (`src/components/SettingsPanel.tsx:888` onward) and by the LLM providers page (`src/components/LlmSettings.tsx`). The Workspace tab's sections instead live in their own components (`src/components/Workspace{Names,Members,Roles,DangerZone}.tsx`, composed by `WorkspaceSettingsTab` in `src/components/WorkspaceAccessSettings.tsx`) and render plain `<h2>`, which `.dialog h2` styles as a *dialog title* and `.dialog h2:not(:first-child)` decorates with a top rule — that is the reported drift.

Two traps. First, `.dialog h2` is shared chrome: most dialogs use `<h2>` as their one title, and `ManagementPanel` uses several inside `.management-modal`; scope any CSS change to `.settings-modal` (or migrate ManagementPanel deliberately) rather than editing `.dialog h2` and hoping. Second, `tab-section` is also used in `ManagementPanel.tsx` as a plain `<div>` layout wrapper (lines 357/450/651) where the `.settings-modal`-scoped rule does not reach — a rename or a class-keyed lint rule must not trip over it.

Grep entry points: `rg 'tab-section' src`, `rg 'hotkey-group' src`, `rg 'PRD 018' src docs`. `prd/018-consistent-ui-styling.md` is the styling PRD; `docs/STYLE-GUIDE.md` holds the token layer, the primitive vocabulary, the `src/components/ui/` wrappers, and the Do / Don't list whose **[lint]** entries `scripts/style-lint.mjs` enforces (the lint scans `src/styles.css` outside its delimited blocks and every `src/**/*.tsx` except `src/components/ui/`). The tab set is final: #246 (Save/Cancel footer), #248 (People → Workspace rename) and #247 (LLM providers nested under Semantic zoom) are all closed and present on this branch.

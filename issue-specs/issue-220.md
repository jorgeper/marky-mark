# Spec: Path-based URLs: canonical paths, legacy redirect, not-found, sign-in deep links (PRD 020 Reqs 5–9) (#220)

## Goal

All acceptance criteria in issue-specs/issue-220.md are satisfied for issue #220, with evidence visible in the session: the hosted client resolves canonical path URLs — `/<workspace-name>` opens the workspace, `/<workspace-name>/<path…>/<file>` opens that file, percent-encoded per segment, with any `#<heading-slug>` fragment preserved; the address bar always shows the canonical path form (rewritten via `history.replaceState` on every open) and the legacy `/?workspace=<uuid>` form redirects to it and is emitted nowhere; a path matching no workspace or file renders an in-app not-found page naming what was looked for with a link to the workspace list; an unauthenticated visit to any such URL continues to the requested workspace/file/fragment after hosted sign-in; and `npm run validate:quick` passes in the implementer's session.

## Acceptance criteria

- **Path router (Req 5).** A pure, unit-tested module (extending `src/lib/hostedPaths.ts` or a sibling in `src/lib/`) maps a `location.pathname` to a target: `/<workspace-name>` is the workspace whose unique name matches (case-insensitively, the same `uniqueNameKey` rule that makes names unique — `src/lib/workspaceNames.ts`); `/<workspace-name>/<segments…>` is that file inside the workspace, each segment percent-decoded individually; the inverse builds the URL with each segment percent-encoded. Existing routes are not shadowed: `/` and `/scratchpad` (PRD 019 Req 1, `isScratchpadPath`) keep their current behavior. The hosted shell (`src/components/HostedSignIn.tsx`) resolves path visits before `<App/>` mounts, workspace open first and then the file, so a shared link lands with the workspace bound and the file open. A `#<heading-slug>` fragment survives resolution, rewrites, and redirects intact — actual scroll-to-heading is Req 19, a later issue, and is out of scope here.
- **Name resolution is possible and leak-free.** The client can resolve a unique name to a workspace id (e.g. `uniqueName` added to the `GET /api/workspaces` rows — `WorkspaceListing` in `src/lib/workspaceLifecycle.ts`, listing branch in `server/workspaces.ts` — or an equivalent server-side resolve). Whatever the mechanism, it reveals nothing about workspaces the listing policy (PRD 017 Req 11) hides from the caller: an unlisted workspace's path behaves as not-found for that caller.
- **Canonical address bar (Req 6).** After opening a workspace by any means — Open dialog/switcher, creation, the scratchpad resolve, a legacy redirect — the address bar shows `/<workspace-name>` (the `history.replaceState` pattern, PRD 009 Req 6); with a file open, it shows that file's Req 5 URL, tracking the active file; with the workspace closed it returns to `/`. The known emit/rewrite sites all conform: `src/platform/hostedWorkspaces.ts` (~line 239, workspace open via `location.assign`), `src/components/HostedSignIn.tsx` (scratchpad resolve, ~line 72), `src/App.tsx` (~line 3276, workspace close). A reload of any rewritten URL boots back into the same workspace/file.
- **Legacy redirect (Req 7).** Visiting `/?workspace=<uuid>` resolves the UUID and lands on the canonical path form (fragment preserved); an unknown UUID renders the Req 8 not-found page. A repo-wide grep shows no remaining code path that emits a `?workspace=` URL (parsing/redirecting it is fine); e2e helpers that build such URLs are migrated.
- **Not-found (Req 8).** A path matching no workspace, a file path not present in an otherwise-valid workspace, and an unknown legacy UUID all render an in-app not-found page that names what was looked for (the workspace name and/or file path) and links to the user's workspace list — never a blank screen, a raw 404, or a silent fall-through to the splash. Styled with the chrome tokens per `docs/STYLE-GUIDE.md`.
- **Sign-in preserves the deep link (Req 9).** An unauthenticated visit to any Req 5 URL (or legacy query URL) shows the hosted sign-in and, once it completes, continues to the originally requested workspace/file/fragment — in azure mode via a record that survives the Entra redirect round trip (the `SCRATCHPAD_INTENT_KEY` read-and-clear pattern in `src/lib/hostedGate.ts`, generalized or paralleled), in local mode directly. A leftover intent never routes a later, unrelated sign-in (read-and-clear semantics hold).
- **Tests.** The path-mapping module and any new pure logic have unit tests (round-trip incl. percent-encoded segments, case-insensitive matching, non-shadowing of `/` and `/scratchpad`). New `E<n>`-numbered e2e coverage in `tests/e2e/hosted.spec.ts` exercises at least: opening a workspace and a nested file by path URL, the address bar showing the canonical form after an Open-dialog open, the legacy-query redirect, and the not-found page — as far as the local-mode harness drives them.
- **Citations.** New behaviour carries `// PRD 020 Req <n>:` citation comments per `.sandcastle/CODING_STANDARDS.md`, and `docs/MAP.md` is regenerated (`npm run map`) if citations moved.
- **Test economy.** The implementer iterated with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code), and ran `npm run validate:quick` ONCE right before declaring the goal met — not after every small change and not as a full-suite baseline. `npm run validate:quick` passes in the implementer's session (`QUICK VALIDATION: ALL PASSED`).
- A summary comment from the implementer exists on issue #220.

## Context

Scope is PRD 020 Reqs 5–9 only (`prd/020-shareable-links.md`). Later issues own: scratch renaming and the `/<username>/scratch` reserved word (Reqs 10–12 — here the scratchpad simply rewrites to its own unique-name path like any workspace), share affordances (Reqs 14–18), and heading landing (Req 19 — this issue only keeps the fragment alive). Hosted-only: Tauri, dev-shim, and single-file builds are untouched; the hosted marker gate (`detectHostedMode`) already scopes the shell.

Issue #219 (merged on this branch) delivered unique names: validation/reserved rules in `src/lib/workspaceNames.ts`, manifest field + migration + rename in `server/workspaces.ts`. The server's SPA fallback already serves any path (`server/app.ts`), so routing is purely client-side. One architectural wrinkle: `createHostedPlatform` (`src/platform/hostedWorkspaces.ts` ~line 144) reads the `?workspace=` binding from `location.search` once at creation — the shell today normalizes exotic entries to that form before `<App/>` mounts (see `resolveScratchpadVisit` in `HostedSignIn.tsx` and the `SCRATCH_BOOT_KEY` hand-off). The implementer chooses whether the platform learns to read the path or the shell keeps translating, but the bar must end up showing the canonical path (Req 6), so the old "rewrite to `/?workspace=`" endpoint of that dance must go. For opening a specific file after boot, the scratch-boot hand-off is the precedent. Legacy-URL e2e assertions exist in `tests/e2e/hosted.spec.ts` (~10 uses of `?workspace=`) and one in `styling.spec.ts` — expect to update them.

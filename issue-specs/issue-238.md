# Spec: Move editor/preview/split styles into the package and document the --mm-* theming contract (#238)

## Goal

All acceptance criteria in issue-specs/issue-238.md are satisfied for issue #238, with evidence visible in the session: the editor/preview/split CSS is extracted from `src/styles.css` into package-owned stylesheets that `@marky-mark/editor` exports and the app imports from the package with no visual change, the package documents the `--mm-*` CSS-variable theming contract and ships a minimal default theme stylesheet so a bare embed looks presentable, `npm run validate:quick` passes in the implementer's session, and a summary comment from the implementer exists on issue #238.

## Acceptance criteria

- (PRD 021 Req 7 — extraction) The editor/preview/split CSS currently in `src/styles.css` lives in stylesheet file(s) owned by the `editor/` package: approximately the `.cm-*` editor blocks, `.editor-wrap`, the `.mm-md-*` markdown token classes, the `.doc*` document-rendering blocks, the split divider, the smart-edit menu, the table-grid, the code-card (per-block copy button), and the image-chip/object-selection blocks. Those rules no longer appear in `src/styles.css` (moved, not duplicated).
- (PRD 021 Req 7 — export/import) The package exports the stylesheet(s) via its `package.json` `exports` map (CSS subpath export(s) alongside the existing entry), and the app imports them from `@marky-mark/editor` (e.g. next to the `./styles.css` import in `src/main.tsx`) — no deep-path imports into `editor/src`, and no app file reaches back into package CSS by relative path.
- (Scope guard) App-owned styling stays in `src/styles.css`: chrome tokens and primitives (PRD 018), toolbar, menus, tabs, comments panel, and the comment-highlight `<mark class="hl">` styling (comments are app-side per PRD 021 non-goals; they enter the preview through the decoration hook, so their look remains the app's business).
- (PRD 021 Req 9 — contract doc) An in-package document (e.g. `editor/THEMING.md`, or an equivalent clearly discoverable in-package location) enumerates the `--mm-*` variables the moved CSS actually consumes — fonts (`--mm-font-body`, `--mm-font-mono`), syntax (`--mm-syn-*`: attr/comment/keyword/literal/meta/number/string/title), code (`--mm-code-bg`, `--mm-code-fg`), selection (`--mm-selection`), content width (`--mm-content-width`), and the rest derived by grepping the extracted stylesheets — each with a one-line meaning. The list matches the extracted CSS (no documented-but-unused or used-but-undocumented variables).
- (PRD 021 Req 9 — default theme) The package ships a minimal default theme stylesheet as a separately importable CSS export that assigns presentable defaults for every contract variable, so a bare embed with no host theming looks reasonable. Marky Mark does not depend on it: the app keeps injecting its own themes exactly as today via `src/themeRuntime.ts` (`applyThemeCss`/`loadAllThemes` untouched), and its 27 themes render as before.
- (PRD 021 Req 17 — no visual change) The extraction is behavior- and appearance-preserving: existing e2e suites pass without behavioral edits, and the moved CSS is present in both app builds (`npm run build` and `npm run build:web` resolve the package CSS imports — verified transitively by the gate).
- (PRD 021 Req 12) Citation comments (`SPEC<n>`/PRD) survive the move into the package stylesheets; if any `src/` files move or MAP-relevant paths change, `docs/MAP.md` is regenerated with `npm run map` so the gate's MAP diff is clean.
- The implementer iterated with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code) after each change, and ran the full gate `npm run validate:quick` ONCE, right before declaring the goal met — not after every small change and not as a baseline at the start — and it printed `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- A summary comment from the implementer exists on issue #238.

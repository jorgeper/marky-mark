# Spec: scratch file should always be there (#320)

## Goal

All acceptance criteria in issue-specs/issue-320.md are satisfied for issue #320, with evidence visible in the session: in the hosted app, while the signed-in owner's own scratchpad workspace is open, a "Scratchpad file" buffer is always alive (active or parked) — its tab and folder-panel row carry no ✕, and middle-click, File → Close / ⌘W and the folder row can neither close nor discard it; saving the scratch buffer turns it into an ordinary file (as today) AND leaves a fresh, empty, clean scratch buffer parked beside it, so the "Scratchpad file" row and tab never disappear after a save; opening a file inside the owner's scratchpad (sidebar, tab, or `/<username>/scratchpad/<file>` URL) keeps or creates the parked scratch buffer instead of removing it; ordinary untitled buffers, other users' scratchpads, desktop/shim/single-file builds and the fresh-on-entry / silent-discard-on-leave rules (PRD 023 Reqs 1, 3–5; PRD 019 Req 11) are unchanged; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #320.

## Acceptance criteria

- **The invariant.** Hosted build only. Whenever the signed-in user's own scratchpad workspace is the open workspace (the hosted binding's `scratchOwner` is the caller — `isOwnScratch` in `src/lib/hostedPaths.ts`), exactly one scratch buffer is alive: either **active** (the document on screen, `scratch` mark set, "Scratchpad file" in toolbar name, tab and browser title, PRD 023 Reqs 6–7) or **parked** (the issue #311 park slot filled, its inactive tab and `folder-item-scratch` row shown). There is never a moment inside the owner's scratchpad with neither. Someone else's scratchpad (PRD 023 Req 5), every other workspace, and single-file mode still have no scratch buffer at all.
- **It cannot be closed.** The scratch buffer's tab in `src/components/FileTabStrip.tsx` (active and parked) and its row in `src/components/FolderPanel.tsx` render **no ✕** (no `file-tab-close` / `folder-tab-close` element for it; the dirty ● still shows in the trailing slot when dirty, and the slot keeps its width so the label does not reflow). Middle-click on the scratch tab does nothing. The `closeFile` command (File → Close, the ⌘W hotkey) while the scratch buffer is the active document does nothing — no splash, no prompt, the buffer and its text stay; it may additionally be shown disabled in the menu if `src/lib/menuSpec.ts` can express that, but a no-op is sufficient. `onCloseScratch` / `onCloseScratchParked` / the scratch branch of `onCloseUntitled` in `src/App.tsx` go away (or become unreachable) rather than remaining as dead wiring. Close Others / Close All / the SPEC36 §7 quit walk are open-set walks the scratch buffer already sits outside of and stay untouched.
- **Saving spawns a fresh one.** When the scratch buffer is saved by any route — ⌘S, the Save command, Save As…, through the in-workspace picker (PRD 023 Req 9, E399) — the written file opens as an ordinary active document with its real name, normal styling, its own selected `folder-item` row and the standard unsaved-changes prompts (PRD 023 Req 12 unchanged), **and** a new scratch buffer is created **parked**: empty text, clean (no dirty dot), fresh editor history, labelled "Scratchpad file" with the `.scratch-name` treatment, its inactive tab and `open` row present. Clicking that row or tab restores an empty scratch buffer in edit mode with the canonical `/<username>/scratchpad` URL (the issue #311 restore path). Cancelling the picker changes nothing (PRD 023 Req 10). Saving an ordinary file while the scratch buffer is parked leaves the parked buffer exactly as it was.
- **Opening a file keeps it.** Opening another file inside the owner's scratchpad over the active scratch buffer parks it with its text and dirty state (issue #311, unchanged). Entering the owner's scratchpad directly on a file URL (`/<username>/scratchpad/<path>`, PRD 023 Req 2 / PRD 020 Req 13) opens that file as the active document — no fresh buffer is focused, the file wins — but an empty, clean scratch buffer is parked beside it so the row and tab are present. This amends the "never boots a scratch buffer" wording of PRD 023 Req 2 to "never boots an *active* scratch buffer"; a missing file still lands on the not-found page. The hosted platform exposes whatever extra boot signal this needs (e.g. an own-scratch flag next to `scratchStart` in `src/platform/types.ts` / `src/platform/hosted.ts`, derived from the sign-in gate's binding); desktop, the dev shim and the single-file build never set it.
- **Everything else stands.** Bare `/scratchpad`, `/<username>/scratchpad`, the Open Workspace "My scratchpad" row and the hamburger/home Open Scratchpad entries still boot a fresh *active* empty buffer, replacing any existing scratch buffer silently (PRD 023 Reqs 1, 3, 4; E397, E433, E434, E509, E510). Leaving the workspace (Close Workspace, navigating to another workspace, browser close or reload) still discards the scratch buffer silently with no prompt and no `beforeunload` (PRD 019 Req 11); the SPEC30 §3 crash-draft shadow of the active scratch buffer is unchanged; the parked buffer is still not persisted to `session` / `foldertree`. A ⌘N / New File buffer is still ordinary "Untitled" with normal prompts and no row (PRD 023 Req 8), and restoring a parked scratch over a dirty ordinary untitled still raises the `open-scratch` prompt.
- **One source of truth.** The tab, the row and the toolbar name keep reading the shared `docName.ts` resolution (`scratchPresence`) and the `scratchRef` / `scratchParkRef` synchronous guards (the issue #291/#311 pattern); no second scratch-state flag is introduced. `src/lib/` stays React-free; no colour/font literals are added to `src/styles.css` (the style lint in `tests/unit/style-lint.test.ts` enforces this — reuse the existing `--mm-scratch-name` tokens).
- **Tests.** In `tests/e2e/hosted.spec.ts`: E552 and E554 (which today click the scratch row's ✕) and E553 (which asserts the row disappears after save) are amended in place to the new contract, keeping their numbers — E552 pins that neither the tab nor the row has a close control, that middle-click and ⌘W leave the dirty scratch buffer on screen with its text; E553 pins the saved file as active/ordinary AND a clean parked "Scratchpad file" row and tab that restore an empty buffer; E554 pins that after a failed open the scratch buffer is still the only scratch on screen (one row, one tab) with its text. E433 is amended so a scratch file URL asserts the file is active with a parked (not active) empty scratch row. New tests numbered from the next unused E ID (E573 at spec time; confirm with `grep -rhoE "test\('E[0-9]+" tests/e2e | sort -t E -k2 -n | tail -1`) cover anything the amendments do not. Any new pure helper in `src/lib/` gets `it('U<n>: …')` cases from the next unused U ID (U1281 at spec time; confirm similarly under `tests/unit`). The `test-ID uniqueness` step and the e2e count floor in `scripts/validate.mjs` still pass; no existing test outside those named is weakened, skipped or renumbered.
- **Citations and map.** Every changed behaviour site carries its citation comment in the repo's format (`// Issue #320: …` beside the existing PRD 019 / PRD 023 / issue #311 citations), per `.sandcastle/CODING_STANDARDS.md`; `docs/MAP.md` is regenerated with `npm run map` if the gate's freshness check complains.
- **Test economy.** Iterate with `npm run typecheck` and `npm run test:unit` (or one targeted test via `npx vitest run <file>` / `npx playwright test -g '<title>'`), baselining with the quick tier only. The full gate runs **once**, right before declaring the goal met — not after every change and not as a start-of-attempt baseline.
- **`npm run validate:quick` passes**, run in the implementer's session, printing `QUICK VALIDATION: ALL PASSED`.
- **A summary comment from the implementer exists on issue #320**, describing what changed (no-close, spawn-on-save, parked-on-file-entry), which PRD wording it amends, and carrying the validate:quick evidence.

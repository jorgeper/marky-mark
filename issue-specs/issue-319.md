# Spec: odd question in main page (#319)

## Goal

All acceptance criteria in issue-specs/issue-319.md are satisfied for issue #319, with evidence visible in the session: a document the user saved never re-offers a crash-safe draft on a later launch (the boot staleness check compares the draft against the on-disk body with any embedded-comment trailer stripped, and a save that lands while the debounced shadow write is still in flight leaves no `draft.json` behind); the "Restore unsaved changes?" dialog explains where the copy came from and, when the drafted file no longer exists at its path, says so instead of naming it as if it were still there; unit and e2e tests cover both; `npm run validate:quick` has been run once in the implementer's session and passed; and a summary comment from the implementer exists on issue #319.

## Acceptance criteria

- **The dialog in the screenshot is understood and its causes are named.** The owner opened the hosted app (the splash shows a "Management…" button, so this is the hosted build) and was met by SPEC30 §3's crash-safe draft offer for "this is a test.md" with no document open. The implementer's issue comment names, from the code, the sequences that leave a `draft.json` behind for a document the user considers saved or gone, and states which of them the change closes. The offer itself (a genuine unsaved draft after a crash or a closed tab is offered once, on the splash, per issue #81) stays — this issue is about drafts that are offered when they should not be, and a question that does not explain itself.
- **A draft that matches the saved document is stale even when the file carries an embedded-comment trailer.** Today `savedText`/the draft hold the body after `splitEmbedded` (`src/App.tsx` `loadDocParts`), but the boot check (`src/App.tsx`, the `SPEC30 §3` block that calls `parseDraft` / `isStaleDraft`) compares the draft against the raw on-disk text, trailer included — so a leftover draft for any commented document is never stale and is re-offered on every launch until the user clicks Discard. After the change, staleness is judged against the trailer-stripped body (line endings still ignored per issue #42). A unit test in `tests/unit/drafts.test.ts` (or wherever the comparison ends up living) proves a draft equal to the body of a file with a `<!-- marky-mark-comments … -->` trailer is stale, and a real content difference is still offered.
- **A save that lands while the shadow write is in flight leaves no orphan draft.** The shadow-write effect only deletes the draft on a clean transition when `draftWrittenRef` is already true, and that flag flips only after the async `writeTextFile` resolves (on hosted, a network PUT). A save that completes in that window leaves `draft.json` on disk with pre-save content while the buffer is clean, and the next launch offers it. After the change, a draft write that resolves after the buffer has turned clean (or after the document changed) does not survive — however the implementer sequences it (delete after the in-flight write settles, re-check dirtiness once the write lands, a write generation counter, …). Covered by a unit test if the sequencing is extracted into `src/lib/`, or by a targeted e2e test otherwise.
- **Opening a document without editing it never produces a draft.** Targeted tests (unit where the predicate is pure, e2e otherwise) show that opening a document and closing it or the app with no keystrokes leaves no `draft.json` for: a CRLF file, a file with an embedded-comment trailer, and a file containing a table opened in table mode (SPEC38 §3.5 canonicalization). If any of these turns out to open dirty, fixing that is in scope.
- **The restore dialog explains itself.** The `restore-prompt` dialog keeps its test ids and its two buttons (`restore-yes` Restore, `restore-no` Discard) but (a) says in one plain sentence where the copy came from — edits that were never saved when the previous session ended — and (b) when the draft's `docPath` is set and the file no longer exists at that path, says the file is gone and that Restore opens the edits as a new Untitled document (which is what `restoreDraft` already does). The existing wording stays for the ordinary case where the file still exists. An e2e test (next free number after E537 in `tests/e2e/documents.spec.ts`) covers the missing-file wording and the Untitled landing; E92 and hosted E325 keep passing unchanged in intent (they may be strengthened, never weakened).
- **The contract is cited and mapped.** Changed behaviour carries `SPEC30 §3` citations (and `issue #319` where the reason is this issue) per `.sandcastle/CODING_STANDARDS.md`; `docs/specs/SPEC30.md` §3.3 is amended to state the missing-file wording and the trailer-aware staleness rule; `docs/MAP.md` is regenerated with `npm run map` if the spec→test table changes (the validate gate diffs it).
- **Iteration was done with the quick tier.** `npm run typecheck` and `npm run test:unit` (or `npx playwright test -g '<title>'` for one e2e test) after each change; no full-suite baseline at the start of an attempt.
- **`npm run validate:quick` has been run ONCE**, in the implementer's session right before declaring the goal met, and printed `QUICK VALIDATION: ALL PASSED`.
- **A summary comment from the implementer exists on issue #319**, naming the causes found, what changed, the tests added, and the gate result.

# Spec: Preview selection button: annotation-only Marky Mark menu on preview selections (#287)

## Goal

All acceptance criteria in issue-specs/issue-287.md are satisfied for issue #287, with evidence visible in the session: a text selection in either preview surface — the full preview pane and the split-mode preview pane — shows the blue Marky Mark hash button to the left of the selection whenever the annotation gate is open; clicking it opens a menu carrying **only** the Comment ▸ and Highlight ▸ entries of PRD 023 Reqs 8–9 (never Table/Image/Code Block/Diagram or any other text-editing row) and dismissing on Esc, outside pointerdown, scroll and selection collapse; its rows insert a comment (pane auto-opens, composer focused, mode unchanged), delete the comment under the selection, insert or recolor a highlight and remove it, all resolved through one shared row builder and one pure context model rather than a second copy of the editor's; unit coverage pins the preview context model and the annotation-only row set, e2e covers the preview insert/delete/recolor/remove flows and each dismissal path; and `npm run validate:quick` passes.

## Acceptance criteria

### The selection button (PRD 023 Req 13)

- Selecting text in the **full preview** pane (`mode === 'preview'`, the `[data-testid="doc"]` surface) shows a blue Marky Mark hash button positioned to the **left** of the selection and vertically aligned with it. It appears on the same selection state the annotation hotkeys already use (`selInfo`), and disappears the moment that selection collapses, is replaced by an empty/whitespace-only one, or leaves the preview surface.
- The **split-mode preview pane** is a preview surface too: a selection in the split preview (`splitDocRef`) shows the same button, anchored to that pane's selection. A selection or caret in the split **editor** half never grows one — that half already has the SPEC43 §3 gutter button.
- The button carries a stable `data-testid` (`smart-edit-selection` unless a better name is justified in a citation) so e2e can select it, and it reuses the editor's Marky Mark hash glyph and `.smart-edit-btn` accent styling through a **shared** export from the editor package rather than a second copy of `HASH_SVG` / a second CSS block (`editor/src/components/Editor.tsx:815–855`, `editor/styles.css:767–791`).
- The button is `position: fixed`, clamped into the viewport and clear of the `.toolbar-shell` band (`src/styles.css` `z-index: 80`, the issue #18 toolbar floor the retired popup applied inline) so it is never intercepted by the toolbar; it is chrome — it never shifts the rendered text, it is not part of the comment-anchor text space (never inside `.doc`'s text nodes), and it is hidden in print alongside the other floating chrome (`@media print`, `src/styles.css:1734`).
- Pressing the button does **not** collapse the selection the rows are about to act on (the widget's `mousedown` + `preventDefault()` idiom), and the resolved context is stashed at open time so the invoked row acts on exactly what the menu showed.
- The button is gated by the same all-or-nothing authoring gate as the editor's annotation entries — `settings.commentsEnabled`, `!authoringFrozen` (PRD 004 Req 15) and `docGrants.commentWrite` (PRD 007 Req 17), i.e. today's `mayComment`. With any of them closed the button is **absent**, not disabled.
- It is build-agnostic: present in the desktop shim and the hosted build alike, never gated on `platform.kind` (PRD 023's "both builds" line).

### The annotation-only menu (PRD 023 Req 13, non-goal "no preview text-editing entries")

- Clicking the button opens the Smart Edit menu component (`SmartEditMenu`, already exported from `@marky-mark/editor`) anchored at the button, containing **exactly two** top-level rows: **Comment ▸** and **Highlight ▸**. No Table, Image, Code Block, Diagram, Bold/Italic/Strikethrough/Inline Code/Link, Heading, Lists, Callout, Blockquote, Code Block, Horizontal Rule, Cut, Copy or Paste row is present, and no separator introducing them.
- The rows come from **one definition shared with the editor menu** — a new exported builder in `editor/src/lib/smartEdit.ts` (e.g. `buildAnnotationMenu(annotations, hotkeys, isMac)`) that `buildSmartMenu` also calls for its own Comment/Highlight block, so the two surfaces' labels, ids, order and enabled rules can never drift. Row ids stay the existing `comment` / `highlight` / `insert-comment` / `delete-comment` / `hl-<color>` / `remove-highlight`, so the `smart-edit-<id>` and `smart-edit-flyout-<id>` testids are the same in both surfaces.
- The Highlight flyout lists the four `MARKER_COLORS` in fixed vocabulary order (yellow, green, orange, pink) — never reordered by last-used — plus **Remove Highlight**; **Insert Comment** renders its hotkey and the armed color's row its `Mod+Alt+H` cue through `displayCombo`, exactly as the editor rows do.
- The menu keeps the SPEC43 §4 behaviour it inherits: viewport clamping, flyouts that flip at the viewport edge, ↑/↓/→/←/Enter/Esc keyboard navigation, and the `smart-edit-menu` testid.
- **Dismissal** covers all four paths named in Req 13: **Esc**, an **outside pointerdown**, a **scroll** (including a scroll of the preview scroller the selection lives in — verify the component's anchor-scroll rule actually fires for the container the app mounts the menu into, and close it app-side if it does not), and **selection collapse** (the selection going away closes the menu). Each closes the menu without authoring anything and without leaving the button stuck on screen.
- The menu never appears when the gate is closed (there is no button to open it), and closing it never switches modes, scrolls the preview, or moves the caret.

### The preview context model (PRD 023 Reqs 8–9 in a caret-free surface)

- Preview authoring resolves through **pure logic in `src/lib/`** — an addition to `src/lib/annotationMenu.ts` (a `previewAnnotationModel`, or a shared shape with `annotationMenuModel`), not a second ad-hoc rule inside `App.tsx`, and not a copy of the editor model. It takes the selection's rendered-text range, the resolved record ranges (`positions`, produced by `reanchor` in the paint effect) and the records, and returns which rows exist, which are enabled and what each resolves to.
- Because the preview has **no caret**, the selection is the only pointing context, and the model reads:
  - **Insert Comment** — always enabled while the button is up; anchors on the selection's rendered range (the offsets come straight from the rendered DOM via `rangeToOffsets`, so there is no source→rendered mapping to fail).
  - **Delete Comment** — enabled when an existing `kind: "comment"` record's painted range overlaps the selection; the record is picked by the existing kind-aware rule (`pickHitRecord`, `src/lib/markHit.ts`), never a second divergent rule.
  - **The four color rows** — when an existing `kind: "highlight"` record overlaps the selection they **recolor that record in place** (same id, same anchor, new `color`, never a second record); otherwise they **insert** a new highlight over the selection.
  - **Remove Highlight** — enabled on the same overlapping-highlight context, deleting that record.
  This is a deliberate reading of Reqs 8–9 for a surface with no caret: "a selection always wins over caret context" is the editor's rule for disambiguating two competing contexts, and applying it literally in preview would make the recolor and remove flows the issue asks for unreachable there. Pin the rule in a citation comment and in unit tests; note in the citation that a second highlight overlapping an existing one is therefore not authorable from the preview button (PRD 023 Req 5's overlap case is a comment over a highlight, which stays authorable).
- The model is fed the same gate as the button and returns "closed" for it, so gate and rows can never disagree.

### The flows (PRD 023 Reqs 8–11)

- **Insert Comment** creates an empty-bodied `kind: "comment"` 2.0.0 record over the selection, **auto-opens the comments pane**, focuses the empty composer ready to type, and **never switches modes** — invoking it in full preview leaves the user in preview, in split mode leaves them in split. It routes through the existing `insertCommentAt`, so cancel removes the freshly created record and submit lands the body and activates the card (no second creation path).
- **Delete Comment** removes that record, its card and its marks in both surfaces.
- **A color row** with no overlapping highlight inserts a `kind: "highlight"` record in that color over the selection via the existing `insertHighlightAt`, and updates the user-scoped last-used marker color (`lastMarkerColor`, PRD 022 Req 4); with an overlapping highlight it recolors that record via the existing `recolorHighlight` and updates the last-used color too.
- **Remove Highlight** deletes the overlapping highlight record and its marks.
- After any row lands, the selection is cleared and the button and menu go away — the surface is left in the same settled state the preview hotkeys leave it in (`previewAnnotation`'s `removeAllRanges()` / `setSelInfo(null)`), with no double-authoring on a second invocation.
- Records authored here carry no color on comments and no body on highlights, round-trip through the existing 2.0.0 writer unchanged, and paint in **both** surfaces (PRD 023 §18) exactly like hotkey- or editor-menu-authored ones.
- The two annotation hotkeys keep working in the preview unchanged (`Mod+Alt+M` / `Mod+Alt+H` over a selection); the button is an additional entry point, not a replacement, and both must resolve through the same model — a hotkey and the matching row over the same selection produce the same record.
- Nothing in the editor surface changes: the gutter button, its full Smart Edit menu, the editor context model (`annotationMenuModel`) and the split editor half behave exactly as #286 left them, and the split preview's scroll-neutrality (issue #278) is preserved.

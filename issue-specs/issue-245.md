# Spec: New Workspace dialog: duplicate-name error is too small and too easy to miss (#245)

## Goal

All acceptance criteria in issue-specs/issue-245.md are satisfied for issue #245, with evidence visible in the session: the New Workspace dialog's duplicate-name error renders at the dialog's body text size in the theme's error colour (never the 11px muted `.hotkey-hint` treatment), the unique-name input and the text typed in it carry the same error colour while the name is rejected and clear as soon as it is edited, a unit test proves the error colour stays legible on all 27 bundled themes, `npm run validate:quick` passes in the implementer's session, and a summary comment from the implementer exists on issue #245.

## Acceptance criteria

- In `src/components/WorkspaceSwitcher.tsx`, the New Workspace dialog's error lines — both the submit-time error (`data-testid="new-workspace-error"`, which carries the server's `The unique name "x" is already taken.`) and the type-time problem (`data-testid="new-workspace-unique-name-error"`) — no longer use the `hotkey-hint` class. They render through a dedicated error class whose `font-size` is `var(--mm-text-body)` (the same step as the rest of the dialog's text, and no smaller) and whose `color` is `var(--mm-danger)`.
- `.dialog .hotkey-hint` itself is unchanged: the hotkeys settings rows that legitimately use the small muted hint keep their current look. (Grep `hotkey-hint` before editing.)
- While the unique name is rejected — a duplicate reported by `lifecycle.create`, or a format/length/reserved problem from `uniqueNameProblem` — the unique-name input carries the error treatment: an error-coloured border (the existing `.dialog input.invalid` rule already sets `border-color: var(--mm-danger)`) and the typed value itself rendered in `var(--mm-danger)`.
- Whether a submit-time `create` failure is attributable to the unique name is decided by a pure, exported helper in `src/lib/workspaceLifecycle.ts` (named for what it answers, e.g. `isUniqueNameError`), so a permission/network failure still shows the message but does not falsely paint the name field red. That helper has unit tests in `tests/unit/workspace-lifecycle.test.ts` covering the duplicate-name message and at least one unrelated failure message.
- Editing the unique-name field clears the stale submit-time error and its styling immediately; once the field holds a valid name, no error message is shown and the input and its text are back to normal colours. (Today `error` state survives edits — fix that.)
- Every colour and font size introduced resolves through a token per `docs/STYLE-GUIDE.md` — no colour literals, no literal `font-size` values, no `color`/`fontSize` literals in inline `style={{}}` objects. `scripts/style-lint.mjs` (run inside `validate:quick`) must stay green.
- A unit test — modelled on `tests/unit/marker-tokens.test.ts`, which already reads the shipped CSS and computes WCAG ratios — asserts the error colour is legible on **every** bundled theme: it resolves `--mm-danger` (the `color-mix(in srgb, #cf222e 90%, var(--mm-fg) 10%)` default, or a theme's own override) against each `themes/*.css` dialog background and asserts a documented contrast floor. Any theme where the derived red falls under the floor gets an explicit per-theme `--mm-danger` override in its `themes/<name>.css`, with a comment saying why. The test enumerates the theme directory rather than hard-coding a list, so a new theme is covered automatically.
- An E-numbered Playwright test in `tests/e2e/hosted.spec.ts` (next free `E<n>`, following the file's existing hosted fixtures) drives the real duplicate path: create a workspace, open New Workspace again, submit the same unique name, and assert (a) the error message is visible and its computed `font-size` equals the dialog body text size — assert against the computed value of a sibling dialog text node or the resolved token, not a hard-coded px string — (b) its computed colour equals the resolved `--mm-danger`, (c) the input's computed border colour and text colour are that same error colour, and (d) typing a fresh name clears message and styling.
- Changes stay inside the hosted surface. `NewWorkspaceDialog` is hosted-only, so the desktop (Tauri) and single-file web builds need no behaviour change and none is introduced.
- Touched code carries a citation comment in the repo's format naming issue #245 and what it implements, matching the neighbouring `Issue #183 §2` / `PRD 020 Req 2` comments in the same file.
- Iteration used `npm run typecheck` and `npm run test:unit` (or a targeted `npx playwright test -g '<title>'` for the new e2e test); the full gate was **not** run as a per-change loop or as a start-of-attempt baseline.
- `npm run validate:quick` has been run **once**, at the end, and printed `QUICK VALIDATION: ALL PASSED` in the implementer's session.
- A summary comment from the implementer exists on issue #245, describing what changed and quoting the gate result.

## Context

The dialog is `NewWorkspaceDialog` in `src/components/WorkspaceSwitcher.tsx` (~lines 36–200). Two error sites exist today, both rendered with `className="hotkey-hint"`: the inline `typedProblem` from `uniqueNameProblem` (`src/lib/workspaceNames.ts`) under the unique-name input, and the `error` state at the bottom of the dialog, which is where the server's duplicate message lands via `lifecycle.create` returning `{ error }`. `.dialog .hotkey-hint` (`src/styles.css` ~line 1365) is `--mm-text-caption` (11px) and `--mm-fg-muted` — that is the "too small, not red" the issue reports.

Tokens are already in place: `--mm-danger` is defined once in the `CHROME TOKENS` block (`src/styles.css` ~line 114) as `#cf222e` tempered toward the theme's `--mm-fg`, so all 27 bundled themes restyle it without defining a chrome token; `.dialog input.invalid` and `.picker-error` (~lines 1177–1184) are the existing precedents for an error border and an error-coloured body-size message — prefer reusing or generalising them over inventing a parallel class. All 27 `themes/*.css` declare hex `--mm-bg`/`--mm-fg`, which is what makes the contrast test tractable; dialogs paint on `--mm-bg-elevated`.

Read `.sandcastle/CODING_STANDARDS.md` and `docs/STYLE-GUIDE.md` before writing CSS. The server-side duplicate message text is asserted in `tests/unit/server-workspaces.test.ts:977`; existing New Workspace e2e flows are around `tests/e2e/hosted.spec.ts:931` and `:2075`. Test ids must not be renamed. If any `SPEC<n>` citation is added or moved, regenerate `docs/MAP.md` with `npm run map` — the gate diffs it.

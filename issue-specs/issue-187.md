# Spec: PRD 017 (1/5): deployment-admin foundation — MM_ADMINS, deployment-level permissions, implicit admin grants, seeded users (#187)

## Goal

All acceptance criteria in issue-specs/issue-187.md are satisfied for issue #187, with evidence visible in the session: `server/config.ts` parses an optional `MM_ADMINS` (whitespace-in-entry refusal, count-only startup line, local-mode default `mock-katherine`); `deployment.admin` and `deployment.create` exist as deployment-level permission names outside `PERMISSIONS` that no role can grant; the shared `resolvePermissions` path unions the seven read/administer verbs for admins in every workspace so every route and the client's refusal prediction inherit it with no per-route change; `SEEDED_USERS` gains `mock-mary` (guest) with the four existing users unchanged; and `npm run validate:quick` passes.

## Acceptance criteria

- **Req 1 — `MM_ADMINS` parsing.** `loadConfig` in `server/config.ts` reads an optional `MM_ADMINS`: a comma-separated list of user ids (Entra oids in azure mode, mock ids in local mode). Entries are trimmed and empty entries dropped; an entry containing interior whitespace makes `loadConfig` throw in the existing actionable style, naming `MM_ADMINS` in the message. Unset or empty yields no admins (in azure mode), and the parsed admin ids are carried on the returned `ServerConfig` so the server can use them.
- **Req 1 — startup line.** The server's startup output reports the admin *count* (e.g. "2 deployment admins"); no admin id ever appears in a log line.
- **Req 25 — local default.** In local mode, `MM_ADMINS` unset defaults to exactly one admin, `mock-katherine`; setting `MM_ADMINS` in local mode overrides the default; azure mode has no default (unset means no admins).
- **Req 2 — deployment-level permission names.** `deployment.admin` and `deployment.create` exist as named deployment-level permissions beside the workspace verb catalog in `src/lib/hostedWorkspace.ts`. They are NOT members of `PERMISSIONS` (the fourteen-verb catalog is unchanged), `isPermission` rejects them, no built-in or custom role can grant them (manifest validation still refuses unknown verbs), and the role editor UI never offers them. Any refusal that names them uses the existing 403 shape `{ error: 'forbidden', required: '<name>' }` — this issue introduces the names and the shape contract; no new route consumes them yet.
- **Req 4 — implicit admin union.** In every workspace, a deployment admin implicitly holds exactly `doc.read`, `file.download`, `comment.read`, `workspace.settings`, `workspace.members`, `workspace.roles` and `workspace.delete`, as a union with whatever their explicit membership or the everyone-role grants — never an override (an admin who is also an Owner keeps full Owner permissions). No other verb is ever implicit: admins without membership do NOT get `doc.edit`, `file.create/delete/rename/upload`, `folder.manage` or `comment.write`.
- **Req 4 — single resolution path.** The union is implemented in the shared pure resolution function in `src/lib/hostedWorkspace.ts` (the `resolvePermissions` path that `requirePermission` in `server/workspaces.ts` calls), parameterized by whether the caller is an admin, so every existing server route inherits it with no per-route change and the client's refusal prediction can use the same pure function (client call sites pass non-admin until PRD 017's later issues expose admin status via `/api/me`). `GET /api/workspaces`' per-row `access` and every `requirePermission` gate reflect the union for admin callers.
- **Req 25 — seeded users.** `SEEDED_USERS` in `server/providers/mock/users.ts` gains a fifth user `{ id: 'mock-mary', username: 'mary', displayName: 'Mary Jackson', isGuest: true }`; the four existing users are byte-for-byte unchanged and remain non-admins, so no existing test changes meaning.
- **No behaviour change by default.** With `MM_ADMINS` unset in azure mode, permission resolution, listings, and refusals are byte-identical to today; no UI is added or changed in this issue.
- **Tests.** Unit tests (next unused `U` numbers, `describe('PRD 017 §…')`) cover: `MM_ADMINS` parsing (trim, empty-entry drop, whitespace refusal naming the variable, local default, azure no-default); the implicit-permission union of Req 4 across admin-non-member, admin-member, admin-with-everyone-role and non-admin callers, including that no write verb is implicit; and that the deployment-level names are outside `PERMISSIONS`/`isPermission` and role validation. New/changed code carries `// SPEC<n> §x.y` citation comments per `.sandcastle/CODING_STANDARDS.md`.
- **Docs touched only where this issue's code demands.** `server/README.md` documents `MM_ADMINS`, the two deployment-level permission names and the implicit admin set (the admin routes and settings record belong to later PRD 017 issues). `docs/MAP.md` is regenerated with `npm run map` and committed if it changed.
- **Verification.** Iterated with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code) during development; `npm run validate:quick` has been run ONCE, right before declaring the goal met — not after every small change and not as a full-suite baseline — and printed `QUICK VALIDATION: ALL PASSED` in the implementer's session.

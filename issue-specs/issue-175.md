# Spec: Merge-on-save on blob: client-supplied base on conditional saves (PRD 016 Reqs 7–10) (#175)

## Goal

All acceptance criteria in issue-specs/issue-175.md are satisfied for issue #175, with evidence visible in the session: a conditional document save can carry the client's base text and a stale save with base lands as a three-way merge on the blob path answering `200 { path, etag, merged: true, content }` (412 with stored content untouched on conflict, guard failure, or exhausted retries — never an unconditional write); the hosted platform sends base on every conditional save of a document it loaded and keeps today's `merged: true` and 412 handling; the existing GitHub lane still passes; and `npm run validate:quick` prints `QUICK VALIDATION: ALL PASSED` in the implementer's session.

## Acceptance criteria

- **(Req 7 — wire shape)** `PUT /api/workspaces/<id>/files/<path>` (the non-raw text branch in `server/workspaces.ts`, currently `const content = await readBody(req)` near line 1131) accepts an optional **base text** alongside the content on a conditional save (`If-Match` present). The suggested shape is a JSON body `{ content, base }` distinguished from the bare-text body by `Content-Type`; the exact wire shape is the implementer's, but it must be unambiguous against a bare-text body. A save without base behaves exactly as today (PRD 007 Req 20): match → write, stale → 412, no `If-Match` → deliberate overwrite. The existing request-size limit (`MAX_BODY_BYTES` in `server/http.ts`) applies to the whole body — no separate limit for base.
- **(Req 8 — server merge)** When `If-Match` is stale and base is present, the server runs the existing three-way line merge (`mergeThreeWay` in `server/merge.ts`) with base = the request's base, ours = the request's content, theirs = the current blob. A clean merge that passes `mergeKeepsFileWellFormed` is written with `writeIfMatch` on the head's ETag, retrying a bounded number of times if the head moves again (the existing `mergeStaleSave` loop / `MERGE_ATTEMPTS` pattern), and answers `200 { path, etag, merged: true, content }` with the merged text. A conflicting merge, a guard failure, or exhausted retries answer the existing 412 with the stored content untouched. Never an unconditional write. The client-supplied base is trusted without verification (a lying client could at most produce a write it could already produce with an unconditional save). This works on providers **without** `readAtVersion` — i.e. the memory provider and Azure blob — which is the whole point.
- **(Additive constraint)** The existing `readAtVersion`-based merge path and the GitHub backend keep working: no GitHub file is deleted, `server-merge-save.test.ts`, `server-github-*` tests and the GitHub e2e lane still pass. Removal is sibling issue #176.
- **(Req 9 — client)** `src/platform/hosted.ts` sends base on every conditional save of a document it loaded: it tracks per-path base text alongside the existing `etags` map — set on `readTextFile`, updated to what a save landed (including the merged text of a `merged: true` response), and dropped where the etag is dropped (invalidation, close, overwrite re-arm as appropriate). The `merged: true` handling is unchanged in behavior: buffer becomes the merged text, marked clean at that text, selection clamped best-effort, `MERGED_SAVE_NOTICE` shows, no dialog (`src/lib/mergedSave.ts` and `WriteResult` in `src/platform/types.ts` stay as-is). A 412 still raises `SaveConflictError` and the Cancel/Overwrite/Reload dialog.
- **(Req 10 — merge stays pure and covered)** `mergeThreeWay` and the structured-file guard remain a pure, unit-tested module with their existing coverage (clean merge, conflict, guard refusal — `tests/unit/server-merge.test.ts` intact), and unit tests now exercise the **blob** save path end-to-end: a stale conditional save with base against the memory provider (no `readAtVersion`) produces a merged 200; a conflicting one produces a 412 with stored content untouched; a save without base on a stale etag still 412s.
- **(Iteration discipline)** Iterate with `npm run typecheck` and `npm run test:unit` (or tests targeted at the changed code, e.g. `npx vitest run tests/unit/server-merge-save.test.ts` style invocations) after each change. Do **not** run the full gate per change and do not run it as a baseline; baseline with the quick tier only.
- **(Final gate)** `npm run validate:quick` has been run **once**, right before declaring the goal met, in the implementer's session, and printed `QUICK VALIDATION: ALL PASSED` (this includes the e2e suite — the existing suite, including the GitHub lane and E224/E225, is unbroken).
- A summary comment from the implementer exists on issue #175.

Existing tests to learn from: `tests/unit/server-merge.test.ts`, `tests/unit/server-merge-save.test.ts`, `tests/unit/merged-save.test.ts`. Read `.sandcastle/CODING_STANDARDS.md` before writing code; cite new behavior per the comment format (this area uses `PRD 016 Req <n>` style citations, matching the existing `PRD 010 Req <n>` precedent).

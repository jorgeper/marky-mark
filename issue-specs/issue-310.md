# Spec: do a pass at editor/preview sync (#310)

## Goal

All acceptance criteria in issue-specs/issue-310.md are satisfied for issue #310, with evidence visible in the session: in split edit with sync scrolling on, the preview follows the editor caret — a click, arrow/Page key, selection extension, typing, or a jump inside the editor realigns the preview within a frame so the caret's rendered cue (the word mark, else the head's rendered row) is vertically level with the caret's visual row, and each live re-render realigns it again, while the editor itself never scrolls for a caret move or keystroke; alignment compares row centres so a body-text cue lands within 10 px and a heading within 16 px mid-document; preview-originated caret moves stay scroll-neutral and sync-off disables all following; E57/E58/E128/E464 stay green untouched; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #310.

## Acceptance criteria

- **Caret moves lead (editor → preview).** In split mode with sync scrolling on (`settings.syncScroll`, issue #167), a caret move that originates in the editor — a pointer click, Arrow/Page/Home/End keys, Shift+Arrow selection extension (the head is the reference), typing or Enter that moves the caret to another visual row, and programmatic editor jumps (`goToLine`, `landSearchHit`) — realigns the **preview** within one or two animation frames so the caret's rendered cue sits level with the caret's visual row. The editor pane's scrollTop never changes as a result (the editor is where the user works: SPEC15 §1.5 keeps holding for the editor; only its "typing never re-syncs" leg is amended so the preview follows). The follower write goes through the existing quiet window in `editor/src/components/SplitView.tsx`, so the preview's own scroll event never re-leads (no oscillation: two consecutive frames agree within 2 px once settled).
- **Preview-originated caret moves stay scroll-neutral.** Caret changes that did not originate in the editor — the SPEC23 preview-selection mirror (issue #278, E464) and the non-reveal legs of SPEC44 §4 click placement — move neither pane; the `reveal: true` scroll of a preview click keeps leading exactly as today (E125). Implementer's choice how the origin is told apart (e.g. a CodeMirror `userEvent` annotation on the mirror's `selectSourceRange` dispatch, or the report carrying an origin flag), but the rule is observable: E464's "neither pane moves" holds with sync on and off.
- **Re-render realigns.** After the debounced live re-render replaces the split preview's DOM (`renderTick` in SplitView) and the SPEC44 cues are re-derived (`applyActiveCues` in `src/App.tsx`), the preview is realigned to the caret once (editor leads), so typing at the bottom of a long document keeps the preview level with the caret rather than drifting until the next scroll. The editor does not move.
- **Visual-row reference, centres compared.** The editor-side reference is the caret head's **visual row** — CodeMirror `coordsAtPos(head)` in content coordinates (wrapped rows land on the right row; `lineBlockAt` is the fallback when the head is outside the measured viewport) — replacing/extending `EditorSyncHandle.headTop()` in `editor/src/components/Editor.tsx`. The preview-side reference is the cue's first client rect: `mark.mm-active-word` when it exists; else the **head's rendered row** inside the tinted container (the selection case and the whitespace/punctuation-caret case, where SPEC44 clears the word mark and today's controller falls back to the container's top — several lines off in a long paragraph); only when neither resolves, the `.mm-active-block` container. The controller aligns the two rects' vertical **centres** (not tops), so heading/body font-size asymmetry no longer offsets the panes. How the head's rendered row reaches the controller is the implementer's call (e.g. a zero-width synthetic marker class painted beside the SPEC44 cues by the app, or a preview-side seam prop on SplitView); rendered text stays byte-identical, the sanitize schema and `data-mm-line` stamping are untouched, and the editor package imports nothing from `src/` (`editor/AGENTS.md`; the boundary check in `scripts/validate.mjs` is the arbiter).
- **Accuracy target.** Mid-document (cue inside the SPEC45 window, neither pane at an end clamp), after the leader settles: the caret row's centre and the preview cue's centre are within **10 px** for a body-text word and within **16 px** for a heading word, with either pane leading a scroll and after a caret move. Ends stay mutually reachable (SPEC15 §1.3): at either end the clamp wins and the tolerance does not apply. Far from the cue (outside the window) the SPEC15 block-anchored interpolation still applies unchanged.
- **Preview leads unchanged in mechanics.** Scrolling the preview still moves the editor to keep the cue level (SPEC45), now against the same visual-row/centre reference; scrolling far away still falls back to interpolation without jumps.
- **Entering split / turning sync back on aligns on the caret.** When split mode mounts or the sync toggle flips back on (issue #167's editor-leads realign), the first alignment is cue-anchored when the caret's block is in view, so both panes open level on the caret.
- **Sync off means off.** With sync scrolling off, caret moves, re-renders and keystrokes move the preview by nothing at all (the panes free-scroll as today).
- **Cost stays flat.** Caret-driven and render-driven alignment are rAF-coalesced (one write per burst of reports), read only geometry already in the DOM (no markdown re-parse, no per-frame `collectAnchors`), and add no listeners outside split mode. No `console.*` in `src/`.
- **Nothing regresses.** E57, E58, E128, E464, E124, E125, E83 and the rest of `tests/e2e/split-view.spec.ts` pass unmodified (no test weakened, skipped or renumbered). E128 may stay at its current tolerances; the new tests below carry the tighter ones.
- **Coverage.** New desktop e2e tests in `tests/e2e/split-view.spec.ts` (next free `E<n>` after E554; the `test-ID uniqueness` step in `scripts/validate.mjs` is the arbiter) pin: a click on a lower editor row with the preview mis-scrolled brings the preview cue level (centres within tolerance) while the editor scrollTop is unchanged; repeated ArrowDown / Shift+ArrowDown (word mark absent during the selection) keeps the panes level as the head walks rows; Enter + typing at the bottom of a long document keeps the preview level after the re-render with the editor unmoved; with sync off, the same caret moves leave the preview scrollTop untouched; a heading cue and a body-text cue each meet their tolerance with either pane leading. Any new pure helper (e.g. a centre-alignment target function beside `offsetForLine` in `editor/src/lib/scrollSync.ts`) gets `U<n>` unit tests (next free after U1269) in `editor/tests/scroll-sync.test.ts`, covering clamping at both ends and the no-op case. The e2e count floor in `scripts/validate.mjs` must not regress.
- **Citations and map.** Every changed behaviour site carries its citation comment in the repo's format (`// Issue #310: …`, alongside the SPEC15/SPEC44/SPEC45 citations already there), per `.sandcastle/CODING_STANDARDS.md`; `docs/MAP.md` is regenerated with `npm run map` if the gate's freshness check complains.
- **Test economy.** Iterate with `npm run typecheck` and `npm run test:unit` (or a single test via `npx vitest run <file>` / `npx playwright test -g '<title>'`). The full gate runs **once**, right before declaring the goal met — not after every change and not as a start-of-attempt baseline (baseline with the quick tier only).
- **`npm run validate:quick` passes**, run in the implementer's session, printing `QUICK VALIDATION: ALL PASSED`.
- **A summary comment from the implementer exists on issue #310**, describing what changed (including the amended typing-never-syncs leg and the new reference geometry) and carrying the validate:quick evidence.

## Context

The issue body (no comment thread) asks that the editor and preview be kept "as aligned as possible, specifically whatever I have selected or wherever the cursor is, should be aligned vertically". Today's controller is the SPEC15 leader/follower loop in `editor/src/components/SplitView.tsx` (~line 149) with the SPEC45 cue-anchored branch: it fires **only on scroll events**, so a click, arrow key, selection drag or keystroke that moves the caret without scrolling leaves the panes wherever they were, and a live re-render shifts the preview content under a fixed scrollTop. Its reference is `EditorSyncHandle.headTop()` (`lineBlockAt(head).top`, the whole wrapped source line's top) against the cue's `getBoundingClientRect().top`, and the cue is `mark.mm-active-word` else `.mm-active-block` — the word mark is cleared during any non-empty selection (SPEC44 §2.2) and on whitespace, so the selection case aligns on the container's top, not the head's row. E128 (~line 818) accepts up to 90 px of top-to-top offset.

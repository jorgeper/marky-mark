# Spec: a couple of bugs (#305)

## Goal

All acceptance criteria in issue-specs/issue-305.md are satisfied for issue #305, with evidence visible in the session: the fixed comment navigator pill (prev / count / next) never overlaps the word-count chip or the semantic-zoom control — when more than one of these bottom-right pieces is on screen they are stacked vertically, each fully visible; the semantic-zoom level control (the −/+ buttons, slider and level label) is absent from the document view in the hosted (cloud) and static web builds even when a roamed or persisted settings file carries `semanticZoom: true`, while the desktop build still shows it exactly as before; the citation-commented code and an e2e test per bug pin both behaviours; `npm run validate:quick` passes in the implementer's session; and a summary comment from the implementer exists on issue #305.

## Acceptance criteria

### Bug 1 — the comment navigator pill overlaps the word-count chip

- With a document open, the word-count chip shown (`showWordCount` on) and a comment active so the navigator pill (`data-testid="comment-nav"`) is visible, the bounding boxes of `comment-nav` and `word-chip` do not intersect. The pill sits **above** the chip (its bottom edge is at or above the chip's top edge), in the same bottom-right region, rather than on top of it.
- On the desktop build, when the semantic-zoom control (`semantic-zoom-control`) is also mounted, none of the three (`comment-nav`, `word-chip`, `semantic-zoom-control`) intersect any other. They are stacked vertically in the bottom-right corner; the screenshot on the issue shows the word chip covering the right half of the zoom control today, so the chip-vs-control overlap counts as the same bug.
- The pieces that are not on screen leave no gap: when the word chip is hidden (`showWordCount` off) or the zoom control is not mounted, the remaining pieces sit at the bottom edge as they do today — the stack collapses rather than reserving empty rows. (CSS `:has()`, a wrapping flex column, or an app-side class are all acceptable; the implementer picks.)
- SPEC14 §3's invariant still holds: while stepping with ↑/↓ the pill's bounding box never changes, and E54 in `tests/e2e/comments.spec.ts` (the `stableBox` + `boundingBox()` equality checks around line 483) still passes unchanged in its assertions. The pill still fades in/out (opacity + visibility) and stays mounted while the comments pane is mounted.
- The pill remains above document text and below overlays (it keeps a z-index between the document and `.overlay`), and all three pieces remain hidden in print (the existing `@media print` list in `src/styles.css`).
- The comment on `.comment-nav` in `src/styles.css` ("Centered over the 300px comment margin") and the JSX comments in `src/App.tsx` that claim the word chip is "bottom-left" and the zoom control "clear of the word-count chip" are corrected to describe the layout the code actually produces. The stale SPEC16 §5 "bottom-left" wording in the CSS/JSX comments should not be left contradicting the code.
- A new e2e test (next free `E<n>` in `tests/e2e/comments.spec.ts` or `reading-and-export.spec.ts`; check `docs/MAP.md` and `rg "test\('E[0-9]+"` for the highest number in use) opens a document, turns the word chip on, activates a comment, and asserts the `comment-nav` and `word-chip` boxes do not intersect and that the pill is above the chip. On the desktop shim (where `platform.semanticZoom` is `true`) it also enables the Semantic zoom experiment and asserts the zoom control's box intersects neither.

### Bug 2 — the semantic-zoom −/+ control shows up in the cloud build

- In the hosted build (`platform.kind === 'hosted'`) and the static web build (`platform.kind === 'web'`) — the flavors that declare **no** `semanticZoom` capability (`src/platform/types.ts` ~line 370) — the document view never mounts `semantic-zoom-control` (and so none of `semantic-zoom-out`, `semantic-zoom-in`, `semantic-zoom-slider`, `semantic-zoom-level`), and `semantic-zoom-view` / the zoomed read-only levels never activate, **regardless of the persisted `semanticZoom` flag**. Today `src/App.tsx` mounts the control on `settings.semanticZoom && docOpen` (≈line 8749) and computes `zoomActive` from `settings.semanticZoom` (≈line 5579); the fix gates the feature on the host capability (the existing `semanticZoomAvailable` / `platform.semanticZoom === true`), so a `settings.json` that roamed in from the desktop app with `semanticZoom: true` (the per-user layer behind `/api/me/files/settings.json`) or a localStorage value left over from before issue #247 produces no control. The mount decision stays a capability check, not a `platform.kind` branch (the platform layer's rule, stated in `types.ts`).
- The Settings → Experimental row keeps its current issue #247 behaviour in those builds: disabled, unchecked, with the "Not available in the web version" note — E246 (`tests/e2e/hosted.spec.ts`) and W14/W15 (`tests/e2e/web.spec.ts`) still pass.
- On the desktop build and the dev/e2e shim (`platform.semanticZoom = true`), nothing changes: the experiment toggles on and off, the control appears with a document open, and `tests/e2e/semantic-zoom.spec.ts` (E229–E245, E505, E506) passes unchanged.
- The zoom hotkeys/menu (`zoomIn` / `zoomOut` in `src/lib/menuSpec.ts`) are SPEC4 text zoom, not semantic zoom; they are untouched.
- A new hosted e2e test (next free `E<n>` in `tests/e2e/hosted.spec.ts`) signs in, writes a user `settings.json` carrying `semanticZoom: true` to `/api/me/files/settings.json` (the tests around line 955 show the request headers and the delete/get pattern), reloads, opens a document, and asserts `semantic-zoom-control` and `semantic-zoom-level` have count 0 while the Experimental row remains disabled and unchecked. Clean up the seeded file so later hosted tests are not affected.

## Context

**Bug 1 files.** `src/styles.css`: `.comment-nav` (~line 1640, `position: fixed; right: 150px; transform: translateX(50%); bottom: 18px; z-index: 60`), `.word-chip` (~1673, `right: 14px; bottom: 14px; z-index: 60`), `.semantic-zoom-control` (~3446, `right: 14px; bottom: 10px; z-index: 40`). All three are independently `position: fixed` in the same corner, which is the whole bug — the CSS comments claiming they are clear of one another are wrong. `src/App.tsx` renders them near lines 8749 (zoom control), 8799 (word chip) and 8867 (nav pill); the pill is inside `{commentsPaneMounted && …}` and gets `.visible` when `navIdx >= 0`. The issue screenshot shows the cloud build with all three colliding: the word chip covers the right half of the zoom control and the nav pill sits on top of both. Stacking order suggested by the issue: nav pill on top, then the zoom control (desktop only), then the word chip at the bottom edge — but any vertical stack with no intersections satisfies the criteria. Keep the pill's position stable across steps (SPEC14 §3, E54 at `tests/e2e/comments.spec.ts:~460`).

**Bug 2 files.** `src/App.tsx:~6139` already has `const semanticZoomAvailable = platform?.semanticZoom === true;` but only feeds it to `SettingsPanel`; the render at `~8749` and `zoomActive` at `~5579` read `settings.semanticZoom` alone. The capability is declared in `src/platform/tauri.ts:448` and `src/platform/browser.ts:558` and deliberately absent from `src/platform/hosted.ts` and `src/platform/web.ts` (issue #247). `EXPERIMENTAL_KEYS` in `src/lib/settings.ts:377` keeps the flag out of workspace pinning but it is still a `U`-scoped setting, so it roams per user via `/api/me/files/settings.json` in hosted and via localStorage in the web build; that is how a desktop user's `true` reaches the cloud UI. `SemanticZoomControl` lives in `src/components/SemanticZoomView.tsx`. "Cloud" in the issue means the hosted build (`platform.kind === 'hosted'`, `tests/e2e/hosted.spec.ts`, `signInTo(page, 'ada')` helper); the static web build (`web.spec.ts`) has the same gap and the same fix covers it.

**Verification.** Scripts that exist: `typecheck`, `test:unit`, `test:e2e`, `test:e2e:web`, `validate:quick`, `validate`, `map`. Run a single Playwright test with `npx playwright test -g '<title>'`. Never read `src/App.tsx` end-to-end — `rg 'SPEC14|SPEC16|PRD 011 Req 21|semanticZoom' src/App.tsx` lands on every site named above.
